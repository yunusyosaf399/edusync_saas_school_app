## 2. Approved subordinate DB-01 defaults and sensitive disclosure rule

1. **Business date:** **T-B School-local** is the approved desired contract. `school_profiles.timezone` exists in frozen Foundation `supabase/migrations/20260924122445_foundation_identity_school_files.sql` and is nonblank, but its exact supported timezone validity and synchronization across all D1 as-of consumers must be verified. Use a real server timestamp converted under a verified zone and one captured date per statement; no caller-controlled timezone or mixed School-local/UTC source policy selection. DB-02 RP-02 and integration owners must sign equivalent interpretation. No unilateral code change to shared `CURRENT_DATE` functions by DB-01.
2. **Temporal limitation:** exactly the DATE half-open interval behavior in RC-03. Same-key successful retry on the same date is idempotent, but no second distinct same-day correction effect. First release rejects correction of a Roll whose stored policy interval ended before School-local apply day.
3. **Academic reuse:** preserve existing exact revision + Class Offering **interval overlap** rule, without automatically reserving all historic academic numbers for life; automatic allocator high-water continues to restrict candidate generation independently.
4. **APPLY actor:** verified original requester or currently authorized final configured approver, not an arbitrary role. All prior reviewer grants and independence must still pass at APPLY.
5. **Checked request visibility:** only original verified requester, genuinely assigned OPEN reviewer, committed decided reviewer or configured final approver **with current active exact School/Student/Section scope**; never disclose raw old_snapshot, requested_payload, broad private reason or other requests. For historic old/new numeric details after MOVE/END, require current applicable `student.roll_history.view` scope and verified request participation; a former-Campus Principal cannot read old numbers solely because of historic participation. After END, authorization can be established through retained Student/School affiliation and current matching School/Student ACL; do **not** insist on a current ACTIVE Enrollment, which would make valid terminal receipts unverifiable. If there is no unambiguous supported current Student scope for a history read, deny disclosure **without** deleting the historical receipt. FAMILY/OWN history grants alone do not authorize staff correction or private request reads.
6. **Reason/data minimization:** nonblank bounded reason kept only in restricted typed evidence, hashed exactly as stored; public/participant checked read does not return free-text reason by default; additional view requires a separate later approval.
7. **Selected event/result literals:** choose `enrollment.roll_corrected` and `D1_STUDENT_ROLL_CORRECT` for successful correction, new corrected Roll UUID result-ref, strict API-gate 12-key/14-key exact result and minimal broad event safe identifiers. Submit/review result-kind candidates from the API gate must be validated against existing Foundation registration before use; this product approval does not authorize inventing new unrelated platform-wide event vocabulary.
8. **Test time:** choose **Q-A: authenticated corrections on different real School business days**, using a dedicated disposable local integration DB for three-correction chain; no privileged rewriting of successful Roll history. A trusted harness clock (Q-B) is **not approved here** and would need separate integration/security review, never a caller-exposed date override.

Authenticated can execute **only** properly reviewed protected `app` wrappers, never raw private helpers. Reviewer separate real Person; exact stored request/receipt policy version, source and amount binding; fixed replay after later lawful operations. Further implementation choices cannot weaken these approved requirements.
