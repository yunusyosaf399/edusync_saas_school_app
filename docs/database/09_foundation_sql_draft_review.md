## STATIC SQL REVIEW CORRECTION PASS — 2026-09-24

This pass edited the existing, unexecuted draft migrations directly. No ninth migration, database test, Supabase connection or schema application occurred.

- `guard_approval_step_templates()` no longer refers to nonexistent `OLD.state`/`NEW.state`. For INSERT, UPDATE and DELETE it locks the owning policy row with `FOR SHARE` and requires `DRAFT`; an UPDATE moving a template between policies locks both parents in ID order and requires both to be drafts. The parent activation UPDATE conflicts with that lock. The future protected activation command must lock operation/parent before validating templates, then transition the policy atomically; command-level completeness and authorization are still deferred.
- Policy lifecycle is `DRAFT → DRAFT/ACTIVE`, `ACTIVE → ACTIVE/RETIRED`, `RETIRED → RETIRED`. Direct draft abandonment into RETIRED is not in the reviewed lifecycle and stays disabled. New policies start DRAFT with no activation time. `activated_at` is assigned only on DRAFT → ACTIVE, is required for ACTIVE/RETIRED, and cannot change or clear. Effective terms stay frozen after activation.
- The twelve active catalog E fields were audited: three `revoked_at` markers plus `activated_at`, `submitted_at`, `opened_at`, `closed_at`, `withdrawn_at`, `delivered_at`, `validated_at`, `read_at` and `archived_at`. Their table guards now reject changes or clearing after a non-NULL value; insert guards start mutable rows without completed/end markers. Natural interval expiry still leaves `revoked_at` NULL. The two notification markers retain their separate one-way guards.
- Approval requests retain the reviewed states and terminality, with `submitted_at` introduced only by DRAFT → SUBMITTED and retained through cancellation. The request transition now also permits APPROVED → CANCELLED before execution, as [the approved workflow](../workflows/01_approval_engine_design.md) specifies. APPROVED remains distinct from EXECUTED; no FAILED or EXPIRED request state was added.
- Step transitions are WAITING → OPEN or CANCELLED, OPEN → APPROVED/REJECTED/CANCELLED, and terminal self-state only. WAITING → CANCELLED closes a stage never opened when its request is cancelled. `opened_at`/`closed_at` are set on those transitions, cannot change/clear, and CHECK constraints require state/timestamp consistency. Reviewer `withdrawn_at`, consumer `delivered_at`, and file `validated_at` are likewise one-way; delivered events cannot reopen, lease fencing remains, and AVAILABLE files require retained validation evidence.
- The `auth.users(id)` FK remains required. **Strategy A — rejected by local execution:** the original draft asked the trusted `postgres` deployment role to grant `USAGE ON SCHEMA auth` and `REFERENCES (id) ON TABLE auth.users` to `schoolos_schema_owner`, then declared the FK under that owner. Local Supabase emitted `WARNING (01007): no privileges were granted for "auth"` and `WARNING (01007): no privileges were granted for column "id" of relation "users"`; migration 2 failed at that FK with `ERROR: permission denied for schema auth (SQLSTATE 42501)`. Those grants are removed in the provisional correction below. This bullet records a later empirical result, not a finding from the original static pass.
- All 39 SECURITY DEFINER functions have fixed `search_path = pg_catalog, pg_temp` and an exact-signature REVOKE immediately after creation, including the three interval helpers and five RLS wrappers. The wrappers are granted only their exact authenticated EXECUTE in migration 8; `current_principal_id()` and `has_complete_grant(...)` remain internal. The checked SQL read receives its narrow source/helper privileges before creation, so owner-time body validation has the intended privilege path.
- Mechanical source checks found **zero nonexistent `OLD`/`NEW` field references** across 63 trigger declarations. All 90 FKs reference declared child columns; all application composite FKs target matching non-partial PRIMARY KEY or UNIQUE column tuples. The external managed `auth.users(id)` key remains a platform preflight. Counts remain 33 tables, 385 columns, 90 FKs including three late FKs, 49 policies, 49 indexes, 39 functions and 63 triggers. F28, business-domain tables and school tenant discriminators remain absent.

The six reviewed `principals`, `roles`, `permissions`, `login_aliases`, `campuses` and `academic_years` lifecycle columns were inspected. Their catalog states and current structural guards remain unchanged here because the reviewed documents do not specify a complete transition graph for them; protected commands must define and test any terminality before activation. ## FINAL STATIC SQL HARDENING PASS — 2026-09-24

This final narrow pass changed only authorization-read volatility/time semantics and default function privileges in the existing unexecuted migrations. `app_private.has_complete_grant(...)` now evaluates interval validity at `pg_catalog.statement_timestamp()` and is `STABLE`. Its five fixed RLS predicates and `app.read_own_principal()` changed from `VOLATILE` to `STABLE`; `app_private.current_principal_id()` was already `STABLE` and is unchanged. These eight application-authored read functions contain no mutation, DDL, advisory write lock or sequence operation; the managed Auth helpers still need the platform preflight below. Trigger functions remain at PostgreSQL's VOLATILE default and retain wall-clock checks where required for operational transitions. [PostgreSQL function volatility](https://www.postgresql.org/docs/15/xfunc-volatility.html) and [date/time functions](https://www.postgresql.org/docs/15/functions-datetime.html) distinguish a statement snapshot/start time from a clock that changes within the statement.

One direct SELECT therefore uses one server authorization instant and a consistent authorization snapshot across its rows. Under the supported READ COMMITTED request path, a later SQL statement re-resolves the live Principal, Auth binding, role, permission, scope and effective intervals. This is statement consistency, not authorization caching across statements. Protected mutation commands still require their separately reviewed post-lock wall-clock authorization check; none was added here.

Migration 1 now removes global default PUBLIC function EXECUTE for all nine potential application function owners: `schoolos_schema_owner`, `schoolos_bootstrap_executor`, `schoolos_authz_reader`, `schoolos_read_executor`, `schoolos_identity_executor`, `schoolos_access_executor`, `schoolos_workflow_executor`, `schoolos_platform_executor` and `schoolos_evidence_writer`. Migration 8 no longer uses its ineffective per-schema function-default REVOKE; its table/sequence defaults and exact grants remain. [PostgreSQL default-privilege documentation](https://www.postgresql.org/docs/15/sql-alterdefaultprivileges.html) states that per-schema revokes cannot cancel a global PUBLIC default. Every one of the 39 existing SECURITY DEFINER functions still has an immediate exact-signature REVOKE and fixed `pg_catalog, pg_temp` search path. The five RLS predicates and the checked read retain only their exact authenticated EXECUTE grants; the current-principal and complete-grant helpers remain internal.

The former schema-owner Auth grant path was disproved locally; the trusted deployment-role `ALTER TABLE` path and managed `auth.users(id)` key remain unproved.
