# Student photo — local durable opaque intent, signed private-service identity and one-time consumption

Date: 2026-10-18. **Status: isolated trial candidate; not a deployed trusted issuance/finalization endpoint and not a Student photo SET acceptance.** Baseline `main` `3a8666e56e25d6087dd98085a917fdf9ae987165` is the approved local ordering-test freeze from [PR #90](199_student_photo_atomic_finalize_ci_merge_freeze.md). This slice implements only the next **local private-intent boundary rehearsal**, not a production upload feature.

## Candidate scope and exact entry points

`tools/photo_validation/student_photo_durable_intent_candidate.py` subclasses the pre-existing test-only **Ed25519 snapshot verifier and persistent single-file SQLite revision cache**. It has two direct Python methods, both deliberately private/test-only, no route or authenticated RPC:

1. `issue_trial(signed_request, now_epoch)` verifies a **real Ed25519 signature** by a separate pinned *synthetic private file-service signer*, over an action-specific and domain-separated canonical payload. The payload names exact school, project, Student, Campus, initiating Principal, purpose `STUDENT_PROFILE_PHOTO`, unique request nonce, signed issue/expiry times and Boolean statements of verified Principal/current grants/Student binding/module/purpose. It only accepts stage `ISSUE`, never a caller-selected token or file owner. It holds `BEGIN IMMEDIATE` against the same SQLite file's active snapshot, rechecks **currently enabled/unexpired/not-invalidated photo entitlement and cache freshness**, and persists a random 256-bit opaque token **digest only** (domain-separated SHA-256), exact target binding, issued snapshot revision, expiry, state `ISSUED` and one private trial event. Raw token is returned only to the synthetic test caller; it is not persisted.
2. `consume_trial(token, signed_request, now_epoch)` requires a **new** signed `CONSUME` request, including the digest of that exact token. Inside a **single BEGIN IMMEDIATE transaction**, it independently rechecks current entitlement, fresh revision, exact Student/school/project/Campus/Principal/purpose binding, previously issued revision no higher than current, unexpired token and `ISSUED` state. It uses an atomic conditional state update to `CONSUMED` and exactly one `CONSUME` event. A second consume, mismatched token, revoked grant flag, cross-Student proof, expired intent, inactive subscription or revoked snapshot leaves no second receipt. The returned **revision integer is local evidence only**, not an upload/finalization grant.

Both actions consume a signed nonce inside the same DB transaction. A previously accepted service request cannot be replayed for another token; failed operations do not create a partial accepted intent or receipt. Token bytes are generated with Python's cryptographic `secrets.token_urlsafe(32)`, and the ledger stores a purpose-domain-separated SHA-256 **hash**, not plaintext bearer tokens. One-time consumption and event uniqueness are protected by local SQLite constraints, not by frontend state.

## What signed service identity actually means here

Tests generate ephemeral Ed25519 private keys for both the candidate SaaS control-plane signer and a *distinct* local service signer. The ledger pins the expected service issuer, service identity and a signing public key and checks the real signature over the exact stage, nonce, student and entitlement-related claims.

**The signer is not a real authenticated service or domain authorization resolver.** Its signed `principal_verified`, `file_upload_granted`, `photo_submit_granted`, `student_scope_verified`, `student_ownership_verified`, `module_enabled` and `registry_approved` fields are *synthetic signer assertions*. Any holder of the test private key can produce arbitrary 'true' claims. Real backend identity verification, current scope grants, Student PRIMARY placement, purpose registry, school membership, trusted service credential provenance, deployment key custody/rotation and impersonation boundaries are **not implemented**. Never accept a client-provided signer key, proof, file identity, school/Student ID or clock as verified authority; do not wire this class into a live route. This is a test of cryptographic binding and ledger semantics under **hypothetically trusted** server sources, not proof of authorization.

## Local integration and test boundaries

The standalone regression file `tools/photo_validation/tests/test_student_photo_durable_intent_candidate.py` runs real Ed25519 signing/verification with randomly generated test keys and a temporary file-backed SQLite database. Tests cover issue/consume across new connections, no raw token in stored metadata, wrong signing key and modified envelope, unsigned/duplicate JSON, false/forged signed scope flags, wrong service identity, cross-Student/Campus/Principal/school/project proofs, token substitution, duplicate request nonce, completed intent replay, signed subscription downgrade/invalidation and later entitlement upgrade, TTL/freshness refusal, and **two spawned processes simultaneously trying to consume the exact same bearer with different signed request IDs**, where only one succeeds and one receipt remains. The inherited 38 prior photo/security tests still run alongside this suite.

All trial tables are prefixed `photo_private_trial_`, reside only in a local SQLite file and do **not** modify Foundation/D1/PostgreSQL or a real upload File. The prior signed entitlement trial uses 300-second snapshot bounds/60-second freshness. This local ledger proposes provisional 30-second signed request lifetime and 40-second token lifetime, with **no product or production approval** of these timings, revocation SLA, server clock policy, key algorithm lifecycle or retention.

## Hard blockers remain

- The real control plane and real file worker must have reviewed, authenticated deployment credentials and auditable, non-client-controlled principal/permission/Student identity resolution. Verified subscriber and module/role/Student scope evidence must come from the actual backend transaction; a signed test Boolean does not prove domain membership.
- Separate service instances across different hosts/regions still do **not** share this single-file SQLite revision/nonce/intent fence. Genuine multi-instance shared durable authority, atomic plan-downgrade/intent mutation ordering and revocation propagation are mandatory.
- A real provider-neutral file service must issue storage credentials, accept/store **exact sanitized bytes** from the frozen JPEG/PNG decoder, bind measured byte count/hash to an immutable Student/school/owner/provenance record and controlled file purpose, support quarantine/retry/forensic audit/retention, and perform an actual protected `PENDING → VALIDATED → AVAILABLE` metadata transition with signed entitlement/one-time intent consumption in the same safe ordering.
- Student Profile photo DIRECT/P1 APPLY must independently recheck live protected eligibility and concurrency. This candidate cannot approve or activate `PHOTO_ENTITLEMENT_PENDING` rejection or any real photo SET.

**Simple example:** A fake admin A is issued a random upload token for Student A. No plaintext token is stored in the temporary database. A second process with the same token cannot consume it after the first process does; a signed request for Student B cannot consume it at all. Yet the code does not upload or authorize any real student's photograph.
