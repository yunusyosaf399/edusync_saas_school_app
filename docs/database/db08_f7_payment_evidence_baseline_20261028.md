# DB08 F7 — private bank/wallet evidence and official payment storage baseline

This inactive storage increment follows the accepted F1–F6 Finance drafts and D1 Student placement source. It separates (1) a parent/staff-submitted private bank or wallet proof, (2) one independent reviewer outcome, and (3) an official payment with a permanent School-scoped receipt serial. A submission and even an approved review are not themselves a payment or Admissions Finance clearance. Cash collection, allocations, invoice rendering, refunds, reversal and clearance follow separate contracts.

**28 October 2026 initial-flow clarification:** Parents transfer funds outside the app and submit only a bank transaction slip (PDF/JPEG/PNG) for a linked Student. An authorized school administrator verifies it. The F7 BANK_TRANSFER/WALLET_TRANSFER storage vocabulary is future-compatible; it does not activate wallet submission, cash collection, a payment gateway or in-app payment. The first F8 parent command must accept BANK_TRANSFER only. Administrator title is not a permission shortcut, and verification still requires an independent, currently authorized reviewer.

The three forced-RLS private sources are:

- finance_payment_submissions: immutable School, Campus, Student, submitting Principal, two-decimal School currency, positive integer minor units, payment date, normalized institution/reference, verified private PAYMENT_EVIDENCE file and SHA-256, and optional correction predecessor. Pending duplicates can coexist so an Accountant can investigate; indexed reference/amount/date and content hash support duplicate detection. A correction must follow a REQUEST_CORRECTION review for the same Student, School, Campus and submitter. It is a new record rather than overwriting the proof.
- finance_payment_reviews: one retained APPROVE, REJECT or REQUEST_CORRECTION decision per submission, a separate active individual reviewer and reason. An approval requires the original private file still available and matching its measured hash.
- finance_official_payments: bank/wallet only, exact composite foreign keys to the same submitted School/Campus/Student/currency/amount/method and an APPROVE review. The reviewer must be the payment's creator. Its institution/reference must match the submission, the source file must remain available at creation, and a verified institution/reference can appear on only one official payment per School/method. Each payment has a unique immutable School receipt serial; the later command will allocate it. Historical financial rows cannot be updated, deleted or truncated.

No authenticated, anon, service_role or no-login workflow executor role can directly read/write these three tables. F7 adds **no payment RPC** or default role/permission seeding. The schema-owner fixture can exercise structural checks inside a disposable rollback transaction, but it does not establish operational parent intake, actual private byte upload, independent authorized school administrator review, receipt-number allocation or ledger reconciliation. These must be tested before any payment can become official in a School project. It does not use a paid/waived client flag or alter S10's deny-only admission gate.

Release order after F7: typed family-linked submission permission and private upload entitlement; current-authorization review/correction workflow with duplicate investigation; atomic official payment issuance, exact receipt/audit/outbox and concurrent receipt/reference races; payment allocation/credit accounting; reversal; clearance with live Finance authority and a shared Admissions handoff fence. The exact receipt presentation format and payment reconciliation rules remain School configuration decisions. Do not infer admission clearance from a screenshot, review or unallocated payment.

Disposable CI injects failed F7 DDL to prove zero surviving tables, then tests forced RLS/ACL, two-decimal exact amounts, file purpose/hash/availability, independent review, submitted-versus-official separation, typed source FKs, duplicate reference protection, immutable rows and fixture cleanup. It reuses the pinned disposable Foundation+D1+F1–F6 candidate; no hosted data is changed. Exact-head results are recorded on draft PR #102.
