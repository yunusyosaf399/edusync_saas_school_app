# D1 Student Profile photo provenance and eligibility — local predicate candidate

Date: 2026-10-17. **Status: rollback-only SECURITY GATE EVIDENCE, not a real entitled photo SET or production operation.** Reads owner-approved SP-03 (docs/database/173), baseline storage policy (docs/architecture/05_storage_entitlements_and_document_purposes.md) and frozen D1 permission vocabulary (docs/security/08_domain_permission_disclosure_catalog.md).

## Physical gap verified

Existing Foundation `app_private.file_objects` carries `uploaded_by_principal_id`, optional `campus_id`, purpose, MIME, state, validation time, storage metadata, measured size and checksum — **but no Student owner ID or trusted domain object binding**. The D1 `d1_guard_file_purpose` trigger only enforces `STUDENT_PROFILE_PHOTO` and `AVAILABLE`; neither proves same-Student provenance or accepted school subscription entitlement.

The platform's `app_private.d1_file_domain_permission('STUDENT_PROFILE_PHOTO','UPLOAD',student_id)` expresses staff domain authorization, but docs/architecture/05 describes the upload handlers, purpose registry, effective SaaS `student_photo.upload` entitlement snapshots and validation as **DESIGN ONLY, NOT IMPLEMENTED**. The school profile table and uploaded-by column cannot substitute for the trusted upload issuance/finalization transaction.

## Safe testable slice

The quarantined, extra-local `supabase/proposals/student_profile_photo_provenance_trial.sql.draft` proposes a narrow `student_profile_photo_provenance_trial` file/Student/school/Campus/uploaded-by binding with immutable trigger, FKs, FORCE RLS and **no ordinary client read/write privileges**. Only the schema owner inserts **synthetic** bindings in the rollback-only test. These rows DO NOT prove there was a real accepted upload or subscription entitlement.

A no-login Student executor's private, Boolean-only `app_private.d1_student_profile_photo_provenance_trial(student_id,file_id,campus_id)` enforces the current JWT Principal, shared authorization lock, exactly one current PRIMARY student placement, verified affected Campus and school, current `student.profile.update` and separate `student.photo.submit` scope, matching file-to-Student binding and uploader, exact school/Campus ancestry, `STUDENT_PROFILE_PHOTO` purpose, `AVAILABLE` with validated timestamp, `PRIVATE` classification, PNG/JPEG/WebP format and Foundation 1 MiB/hash limits. No storage object key, URL or private metadata returns to the caller; no direct authenticated EXECUTE or provenance table DML is granted. Internal SELECT and temporary CREATE privileges are restricted to the no-login Student executor and the entire trial is rolled back.

The new extra local scenario reuses real authenticated P0 Student PRIMARY placement and existing P1 DIRECT grant from unchanged business suite #66, adds a separate *current* photo-submit permission grant, creates synthetic file rows through real `PENDING → VALIDATED → AVAILABLE` state transitions, then checks the conditional positive photo gate. Negative cases include unvalidated PENDING, BIRTH_CERTIFICATE purpose, missing Campus, false upload-owner evidence, wrong Student/Campus, nonexistent file, revoked photo-submit permission and later QUARANTINED state. It checks authenticated users cannot read this metadata nor invoke the private guard, schema-owner seal immutability, and independently verifies a full disposable BEGIN/ROLLBACK leaves no claim table or helper behind. Unchanged baseline 74 suites/3,124 business assertions still run separately.

## Activation remains blocked

1. **DO NOT replace the deliberate `PHOTO_ENTITLEMENT_PENDING` rejection** in the existing Student typed preflight or DIRECT/APPLY trials based on this predicate alone. No real upload issuance/finalization endpoint or control-plane verified `student_photo.upload` entitlement snapshot was implemented; synthetic `student_profile_photo_provenance_trial` rows are not real evidence. Do not use uploaded-by, object key or caller claims as a shortcut.
2. A production plan must link accepted upload intent/finalization atomically to exact Student and school, current purpose registry, verified subscription/module and measured bytes; ensure no client's chosen Student UUID can mint an ownership assertion. Clarify whether linking previously entitled AVAILABLE evidence remains allowed after subscription downgrade, consistent with preservation policy; verify both DIRECT and APPROVAL APPLY against fresh file state and current authorization.
3. External validators must verify decoded JPEG/PNG content and hash; the proposed MIME gate includes WebP for diagnostic robustness but WebP is **not** approved in the frozen IMG taxonomy. Before implementation align MIME allowlist with the frozen JPEG/PNG rule. Cross-school and real other-Student ownership, truly missing/ejected entitlement, file-finalization races and two-session APPLY conflicts remain untested.
4. Requires independently approved additive physical schema, purpose-specific executor ACL, audited forensic access and retention policy, and security review before use in a hosted database. No migrations, frozen D1 fragments, contracts or Foundation SQL are modified. `student.profile.update` is still a blocked protected operation (Issue #67).

**Baseline:** 31/35 protected operations accepted, 34 D1 relations, 228 Migration 10 `.sql.draft` fragments, 97 permissions, 322 scope alternatives and 36 operation contracts unchanged. No hosted Supabase change.

**Simple example:** In an isolated test, a correctly purposed and validated portrait with a Student-specific recorded binding passes the private predicate. The same file cannot pass for an unrelated Student, and a file pending validation or from a birth-certificate purpose fails. This does not yet authorize a real Student profile-photo update.
