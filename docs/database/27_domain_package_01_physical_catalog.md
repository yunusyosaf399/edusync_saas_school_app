# D1B1 — proposed physical table and column catalog

**Status: D1B1R PHYSICAL DESIGN PROPOSAL; NO SQL AUTHORIZED.** Source: [approved decisions and D1B1 review clarification](../decisions/DOMAIN_PACKAGE_01_APPROVED_DECISIONS.md), [D1A scope](24_domain_package_01_scope_and_invariants.md), [Foundation physical catalog](05_foundation_physical_catalog.md), and [physical-design gate](../decisions/DOMAIN_PACKAGE_01_PHYSICAL_DESIGN_GATE.md). Names and types below are exact candidates for independent D1B2/D1B3 review, not deployed schema. There are **34 proposed D1 relations**, all in `app_private`. No new `app` base table or anonymous surface is proposed; later `app` read interfaces must be explicitly checked and field-limited. The existing 33 Foundation tables, 12 roles, 49 policies and 39 application definers are unchanged.

## Notation and shared complete column sets

To make 34 relation definitions readable, every relation's **complete** column set is the explicitly named standard set below **plus** every field in its own column table. No implicit `etc.` or metadata column exists. Each relation section names its standard set. All `id` values are UUID v4 generated by `pg_catalog.gen_random_uuid()` in a protected server path. `created_by` is the verified `app_private.principals.id`, never a client claim. The D1B2 trigger/command review must enforce these defaults, versions and actor values. In per-relation tables, `—` means no default; `NULL` is the explicit nullable default. `I` immutable, `C` controlled mutable, `E` one-way effective end marker, `H` history/append identity, `V` server row version, `S` server-maintained timestamp, `D` derived (not stored). All actual D1 FKs are `ON DELETE RESTRICT ON UPDATE RESTRICT`; none references `auth.users`.

| Standard set | Complete common columns (name · type · null? · default · mutability · reference) |
|---|---|
| **M** mutable record | `id uuid NO gen_random_uuid() I —`; `created_at timestamptz NO server transaction time I —`; `created_by uuid NO verified actor I app_private.principals(id)`; `row_version bigint NO 1 V —`; `updated_at timestamptz NO server transaction time S —` |
| **H** retained history / immutable event | `id uuid NO gen_random_uuid() H —`; `created_at timestamptz NO server transaction time H —`; `created_by uuid NO verified actor H app_private.principals(id)` |
| **HE** retained effective history / one-way end | all **H** columns plus `ended_at timestamptz YES NULL E —`; `ended_by uuid YES NULL E app_private.principals(id)`; these two are set together with the relation's `effective_until` by a protected end command |

Every table below has PK `id` from its standard set. An **HE** relation's listed `effective_until` plus common `ended_at`/`ended_by` is the sole protected E completion exception, never a generic edit; adding a correction creates a successor/superseding row. All other H/HE fields remain immutable. Mutable records reject ordinary DELETE and use expected `row_version`; history is retained after archive/close. Configuration code/number uniqueness does not imply gapless sequences. Event words in this document are **candidate** dotted domain vocabulary; registration and payload redaction belong to D1B3/D1C. No table is directly client-writable. Index notes are query patterns, not the final index budget. No file upload purpose is activated by these relations.

## Cross-cutting physical boundaries and testability

**Schema/exposure:** all 34 D1 base relations are proposed in `app_private`; **zero** new D1 base relations in `app`. Even low-risk Class/Subject catalogs are private because their current availability and campus/permission context differ by viewer; a later checked `app` projection may expose only `id/code/label/order` to authenticated, scoped callers after D1B3 RLS/security review. No anonymous reads. Every insert/update/end uses a protected command; no direct authenticated DML. Field-limited Student and Employee read surfaces are mandatory, never broad base-table SELECT. Foundation `file_objects` is reused via optional typed FKs for Student/Employee photo and birth certificate; no new file metadata or active upload purpose, and employee document links beyond photo wait for approved purpose/domain relationship. Foundation audit/outbox/receipts/approval are reused; no parallel engine.

**History:** M catalog archive/revision never deletes referenced identities; H/HE relations append or one-way close with reason, verified actor and recorded timestamp. Student restricted/special and Employee restricted identity fields use actual HE snapshot histories: correction closes the old row, appends the successor and retains old sensitive facts inside their narrow private relations. Qualification and external-experience corrections use retained per-record lineages. Student/Employee current status projections are synchronized with their history in protected transactions. Capacity changes preserve domain revisions; roll manual correction preserves allocation lineage; family relationship and access are independent histories. Broad audit/outbox carries identifiers and safe action evidence, never raw sensitive old/new values. No generic `deleted_at` or ordinary history DELETE.

**Employee boundary:** current-school joining and rehire dates derive from `employment_periods`; external professional experience is separate. Person name is not copied into Employee. The optional photo FK activates no upload purpose. D1 adds **no** employment contract, contract compensation, salary, payroll, leave, employee attendance, performance review/score, broad employee document folder or placeholder JSON for them. Contracts and contract documents await later HR and storage-purpose approval.

**Numbering boundary:** `student_id_allocator_states` is Student-owned. Admission Number allocation/reservation belongs to the *later Admissions package* and is not fabricated as D1 generic allocator; D1 Student creation requires a verified final number/serial from that handoff (direct intake uses the same contract). If Admissions is not yet available, no Student-creation command activates. `roll_policy_revisions`, `roll_allocator_states` and `roll_allocations` are D1-owned for both approved modes. Foundation `setting_revisions` may hold UI defaults but is not the authoritative allocator state or editable JSON sequence. Exact allocator transaction/isolation and public Student-ID formatting are D1B2/D1C gates.

**Race-sensitive invariants for D1B2:** Student ID and Admission Number reservation, roll namespace/correction, single active PRIMARY placement, both capacity limits and override, one class teacher, one PRIMARY Subject teacher, SUBSTITUTE interval, family-principal/child access revocation, and employee ACTIVE/teacher eligibility changes racing assignment. This document does not choose lock order, isolation or index budget.
