# 01 - Database Conventions

**Status:** PROPOSED technical baseline, 2026-09-22. No SQL or deployment authorization.  
**Authority:** [AGENTS.md](../../AGENTS.md), [master specification](../requirements/School_OS_SaaS_Master_Specification_v0.2.md) sections 3, 9, 55-58 and 64-78, and [database guardrails](SAAS_AND_DATABASE_GUARDRAILS.md).

CONFIRMED means an existing product constraint. PROPOSED means a design recommendation in this package. TBD means the choice remains unresolved. Unless explicitly marked CONFIRMED, standards below are PROPOSED. Field and entity names are design vocabulary, not an approved physical schema. [ADR-001](../decisions/ADR-001-foundation-database-principles.md) records decisions, alternatives and open questions.

## 1. Isolation and ownership

CONFIRMED: one customer school has one Supabase project. Campuses are scopes inside that school. Do not spread organization_id or tenant_id across operational records. A school-profile reference expresses business ownership where useful; it is not a shared-database tenant discriminator. The control plane owns routing/deployment metadata only and has no cross-project foreign keys into school records.

PostgreSQL owns authoritative business facts. Domain services enforce commands; Flutter does not become the only permission or integrity boundary. See [domain boundaries](../architecture/01_domain_boundaries.md).

## 2. Identifiers, relationships and naming

| Topic | Proposed standard | Important limit |
|---|---|---|
| UUID strategy | UUID v4 for internal identities; server-generated by default. Accept cryptographically generated client UUIDs for explicitly supported offline creates. | Validate authorization independently of possession of a UUID. Reject collisions; never silently overwrite. UUIDv7 is an alternative, not a requirement. |
| Primary keys | Stable UUID primary identifier for independently referenced entities. Relationship records needing history/revocation also get identities. | Composite uniqueness still protects their business relationship. |
| Foreign keys | Explicit FKs to authoritative parents; index referencing columns used in joins/policies. Restrict deletion of referenced business/history anchors. | No cascading deletion from Auth to people, enrollment, finance, requests or audit. Cascades are considered only for disposable subordinate data. |
| External identifiers | Keep admission, roll, student, invoice and receipt numbers distinct from UUIDs. Allocate permanent numbers server-side. | No MAX-plus-one allocation; no claim of gapless numbering. Scope/reset rules remain domain decisions. |
| Naming | Lowercase snake_case physical names, plural entity collections, singular *_id references; stable nonlocalized codes and separate display labels. Use domain-qualified permission codes. | Physical schema namespaces and identifier lengths remain TBD; do not modify Supabase-managed schemas. |
| Constraint names | Consistent readable prefixes such as pk, fk, uq, ck and ix plus entity/purpose. | Final convention selected with the physical-schema package. |

UUID generation capabilities must be checked against the actual project's PostgreSQL version before implementation; the proposal does not assume that version. [PostgreSQL UUID functions](https://www.postgresql.org/docs/current/functions-uuid.html).

## 3. Time, actors and record versions

| Concern | Proposed convention |
|---|---|
| created_at | Server-recorded creation instant, immutable. |
| updated_at | Server-recorded last successful business mutation for mutable records. Immutable events do not need artificial updates. |
| created_by / updated_by | References to the stable actor/principal, where attribution matters; assigned from verified execution context, never trusted from client input. |
| System activity | Explicit system principal, with initiating principal, correlation and causation where applicable. No unexplained null actor on sensitive writes. |
| Business dates | DATE for DOB, academic-year boundaries and leave dates; do not turn calendar dates into midnight UTC instants. |
| Event instants | TIMESTAMPTZ for creation, review, capture, application and audit instants. Retain captured_at separately from server received_at for offline events. |
| Timezone | Store school IANA timezone; render instants for the relevant user/school context. Derive an attendance business date using the applicable school's rules, not the device's clock. |
| Scheduled local times | Model local date/time plus IANA zone and an explicit DST policy in the later timetable/automation design. Never schedule recurrence by a fixed UTC offset alone. |
| row_version | Server-maintained increasing integer per mutable aggregate; increment on each accepted change. Clients submit expected_version. |
| Effective history | Preserve both when a fact was effective and when it was recorded. Use immutable revisions with effective intervals where the domain needs them. Backdated changes retain the original knowledge. |

TIMESTAMPTZ represents an instant; it does not retain the original named timezone. Preserve a zone identifier separately when reconstructing a schedule requires it. [PostgreSQL date/time types](https://www.postgresql.org/docs/current/datatype-datetime.html).

## 4. Lifecycle, archive and historical integrity

Use explicit finite state machines, not independent booleans whose combinations are undefined. Mutable configuration can move through draft, active and retired states; domain states are specified per domain, not one universal enum.

Archive/soft delete is PROPOSED for eligible mutable reference data: archived_at, archived_by and reason, with normal operations excluding archived parents while authorized historical reads retain access. Do not add soft-delete fields to every record. Business identifiers used in permanent history should not be recycled after archive unless a specific design permits it.

CONFIRMED: financial facts use reversals/adjustments, published results use controlled revisions, finalized payroll is locked, and attendance/enrollment/status history survives corrections and year changes. Audit records and approval reviews are append-only to application users. Retiring an account or campus must not erase history.

Current-state projections may be updated for efficient reads, but retain the immutable revisions and transitions that explain them. For mutable foundation profile data, audit captures meaningful changes. Configuration/authorization changes that affect past decisions also retain effective versions or ended grants; audit alone is not a substitute for reconstructable business history.

## 5. Exact quantities and constraints

- Money: PROPOSED bounded NUMERIC(20,4) plus explicit currency code for future monetary facts; the Finance design must validate precision/range and currency minor-unit rounding before use. Do not silently equate all currencies with two decimals or round implicitly at arbitrary intermediate steps. Never use binary float or locale-dependent money formatting as business truth.
- Percentages: PROPOSED NUMERIC(7,4) expressed in percentage points, so 12.5 means 12.5%, not 0.125. Apply 0-100 bounds where that business concept requires them; other rates need a separate rule.
- Reject NaN/infinite quantities. Model allowed sign, maximum and scale explicitly per amount/rate. Rounding method and allocation reconciliation remain TBD for Finance.
- CHECK constraints enforce local invariants such as positive capacities and start_date <= end_date. Cross-record, overlap and balance invariants require appropriate unique/exclusion constraints or transactional validation; a simple CHECK is not a cross-table rule.
- Unique constraints express real scopes: campus code within the school, room code within campus, permission resource/action, normalized login alias within a school project. Nullable scope uniqueness must handle school-level null values deliberately.
- Index from query and authorization patterns: principal/active grants, campus/status, target/time, request/state, recipient/read-state. Avoid speculative indexes or broad JSONB GIN indexes without measured queries. FKs do not remove the need to review referencing-side indexes.

Exact NUMERIC is appropriate for monetary arithmetic; declared scale can round inputs, so input validation and the business rounding policy must be explicit. [PostgreSQL numeric types](https://www.postgresql.org/docs/current/datatype-numeric.html).

## 6. JSONB and configurable values

Use relational fields and FKs for identity, money, scope, relationships and critical lifecycle state. JSONB is limited to versioned, validated configuration payloads, small event envelopes and allowlisted audit differences. Each has an owning validator, schema version, size bound and redaction policy. Never hide role grants, arbitrary foreign keys, a financial ledger or an entire school record inside JSONB.

Use lookup/configuration records for school-editable labels and options. Use checked codes for small application-owned states; PostgreSQL enums are an alternative only for genuinely stable sets after upgrade analysis. Schools cannot create new permission semantics or executable workflow handlers by editing a label. Configurable choices reference an application-owned registry of supported actions.

## 7. Transactions, retries and concurrent commands

A protected business command commits its authoritative change, domain revision, approval application result, successful audit evidence and outbox event in one database transaction. External email, push or object-store calls occur outside that transaction and use recoverable delivery/finalization states. Auth creation and application provisioning also require reconciliation; do not assume cross-service atomicity.

Use expected_version comparisons for mutable updates. Lock affected aggregates and revalidate state/permissions when committing approvals or multi-record invariants. Choose stronger isolation where required and retry serialization failures as whole idempotent commands. Default Read Committed alone is not a concurrency strategy. [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html).

An idempotency key is scoped to school project, authenticated principal and command kind, with a canonical payload hash and durable result reference. Same key/same input returns the existing authorized result; same key/different input is a conflict. Permanent irreversible operations retain a uniqueness link independent of retry-cache expiry. UUIDs alone do not deduplicate repeated commands. See F25-F26 in the [entity map](02_foundation_entity_map.md).

A denied/rolled-back action is recorded separately as a failed security attempt, never as a committed business change. Required audit-write failure aborts a sensitive mutation; asynchronous notifications failing do not undo it.

## 8. Offline and synchronization contracts

CONFIRMED: sensitive caches are encrypted and critical conflicts are not resolved by silent last-write-wins. PROPOSED metadata for eligible aggregates: UUID, server version, client operation UUID, expected server version, captured_at, received_at, actor/device claims with provenance, and tombstone/archive state where needed. Device identifiers do not prove a human's identity.

Offline operations are proposals until server authentication, current permission, assignment, state and version checks pass. Cache membership is not authority. Partition local caches by school and account/context; recheck before downloading/exporting. Permission loss needs a scoped invalidation/purge design.

Do not use client clocks or updated_at alone as a lossless synchronization cursor. Cursor ordering, tombstone horizon, maximum offline duration and scope-change behavior are TBD (T09). No sync journal or device registry is designed here.

## 9. Supabase Auth, Provider-Neutral Object Storage and RLS

Use a stable application principal independent from a person and from the current Auth UUID. Reference only the managed auth.users primary key for the live binding. Deprovisioning disables application access first and preserves historical actors; account relinking is a protected, audited operation. [Identity design](../security/01_identity_auth_model.md) covers shared family access. Supabase recommends referencing the managed user's primary key. [User management](https://supabase.com/docs/guides/auth/managing-user-data).

File metadata stores a private logical storage location/object key, content type, validated byte count, uploader, immutable controlled purpose_code and lifecycle; a signed URL is not a permanent identifier. Typed domain links are added with their domains, not unchecked target IDs. Current initial upload class is server-verified 1..1,048,576 bytes inclusive (1 MiB). Generated PDFs are normally on demand; only underlying facts and permanent document identifiers persist. Protected provider-neutral file service authorizes bounded temporary private access. See [storage architecture](../architecture/04_provider_neutral_object_storage.md).

PROPOSED RLS posture: default-deny for exposed sensitive data, explicit grants, verified principal and current assignment checks, separate read and write rules, and protected command interfaces for sensitive mutations. Do not treat a nullable campus as unrestricted school visibility. No anonymous access to school operations. SQL role names are not application roles.

Service/owner connections can bypass RLS and require separate least-privilege execution and audit controls. Views, functions, exports and workers require explicit review; no assumption that a table policy secures every access path. [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html). Implementation placement and exposed/private namespaces are TBD (T02, T04).
