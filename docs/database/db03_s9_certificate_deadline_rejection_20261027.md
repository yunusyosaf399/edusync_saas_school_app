# DB03 S9 — automatic missing-certificate deadline rejection

The owner selected application rejection with retained history when required certificates remain missing after their deadline, and permanent certificate retention. S9 implements that rule as a private periodic server worker. It follows the inactive S1–S8 candidates; no executable migration, hosted writes, worker credentials, production catalog or enabled schedule is introduced.

## Due-date and missing-document rule

The application must be DRAFT with a recorded grace grant and live School/Campus/AcademicYear context. The database supplies its current clock and School time zone. The complete local due date is inclusive: rejection requires local today strictly greater than the effective due date. No caller may supply an evaluation time, deadline, actor, rejection reason or desired state. No grace means no invented deadline from application creation.

Effective dates reuse S7's `db03_document_due`: the earlier of the latest applicable kind deadline and the original application-wide cap of first grant plus two calendar months. Neither the worker, replacement nor rejection resets grace. A later authorized shorter-date extension within the original cap is respected if it commits first. If expiry commits first, the terminal application cannot receive a new grant.

Required kinds include birth certificate for every applicant, leaving certificate for declared transfers, and additional required published-policy documents. Before collection is prepared, the mandatory birth certificate still applies. A first-time applicant is never rejected for a leaving certificate merely because a grant mentions it. A retired/unavailable policy or unsupported required kind is skipped for repair rather than guessed by destructive automation. Archived/closed parents are skipped. Relevant skipped/error states require operational monitoring; the worker does not silently alter policy or restore a parent.

A current link received by its effective due date counts as received while awaiting principal review, even after the date passes. Quarantine/archive invalidates availability and forwarding but does not erase historical receipt; it does not by itself trigger automatic missing-document rejection. An explicit principal REJECTED decision means the required certificate needs replacement. If no acceptable current replacement was received within the original window, the application becomes eligible for deadline rejection. Optional documents do not gate this rule. Existing S7 late-upload prevention and S8 independent review remain intact.

## State, history and evidence

Four ordered `09_*.sql.draft` fragments add REJECTED to the application root and terminal transition shapes. DRAFT can become REJECTED only through the protected deadline worker; human intake commands keep their existing create/grant/withdraw limits. Terminal rows cannot be reopened or amended. Existing source rows and uploaded bytes remain. No Person, Student, enrollment, admission number or Finance clearance is created.

One immutable forced-RLS `admission_deadline_rejections` source per application links the exact terminal transition, current application-wide grace head, optional kind-specific grant, intake and any rejected current document link using typed composite FKs. It stores the triggering kind, effective due date, evaluated local date/time zone, server timestamp/version and SYSTEM actor. The transition uses controlled reason `MISSING_REQUIRED_CERTIFICATE_DEADLINE`. A single triggering required kind is sufficient; the worker selects a deterministic kind and preserves its basis. This is not a general application rejection/correction API.

Root change, transition, source, successful receipt, audit and outbox commit atomically. The receipt has a deterministic application-bound key; retries and simultaneous deliveries return the one historical terminal result after current worker authorization. A revoked/replaced worker assignment cannot duplicate a terminal effect. An authorized replacement SYSTEM principal may read the original historical result; its earlier actor provenance remains unchanged. Outbox/audit bodies contain only source ID, application ID and application version. Reasons, object keys and document contents are absent. Outbox delivery itself remains the existing separately accepted platform responsibility; no external messages are sent here.

The existing administrator checked status returns REJECTED. A new `read_admission_deadline_rejection` checked read uses the current S7 domain-view permission/scope and returns the retained triggering kind, due/evaluation dates, time zone and controlled reason; a role name alone grants no access. The private grace view returns REJECTED for terminal applications and DOCUMENT_RECEIVED for current timely links; receipt is distinct from VERIFIED and document clearance. The principal queue already excludes non-DRAFT roots. History/private-file access follows its existing checked routes; retention does not invent a new historical download permission.

## Worker authorization and execution

Only the existing `schoolos_event_login` can invoke the two fixed private worker entry points: `db03_deadline_candidates(after UUID, limit)` and `db03_expire_admission_certificate(application UUID)`. It has no table DML, executor membership or public domain RPC. The actor is the unique ACTIVE SYSTEM principal with purpose `admission-certificate-deadline`, resolved by the database, never JWT/client metadata. It also needs a current exact ADMISSION_DEADLINE_WORKER role and complete explicit `admission.certificate.expire` ALL/DIRECT grant/assignment/scope/permission/operation chain with SYSTEM context. Operation version/handler/schema must match, be enabled and require no additional approval. File workers, signed-in administrators/principals and broad service role do not acquire this private authority. No actor, role, grant or operation is seeded outside disposable tests.

Both paths require READ COMMITTED. Mutation follows the accepted shared prefix: authorization fence, deterministic command key, School, Campus, AcademicYear, application; eligibility and worker authority are checked after waits. File metadata and S1–S8 mutations retain their fences. Deadline history and transitions permit only the designated executor and purpose-bound session; direct UPDATE/DELETE/TRUNCATE is denied. Migration rehearsal restores the preceding guard, queue and view if installation fails.

`services/admission_documents/deadline_worker.py` supplies a concrete periodic runner. `CertificateDeadlineWorker.run_once()` discovers a 1–100 row keyset page, then processes each application in its own transaction. Each mutation rechecks live facts: discovery is never an authorization or decision token. A failed item rolls back completely while other items continue. The cursor advances past failures and wraps; the next pass retries eligible failures. A restart can repeat discovery safely. One-shot supervisors can persist the returned `next_cursor` and supply `--after-id` to avoid repeatedly starting at the first page. An unrecoverable discovery/authority/connection failure stops the run for supervisor recovery. Errors expose SQLSTATE or a fixed failure code, never exception text or credentials.

Deployment supplies `DB03_DEADLINE_DATABASE_DSN` through private server secret management and chooses a finite positive `--interval-seconds`. The CLI can run once with `--once`, or periodically with an explicit interval; it prints bounded counts, cursor and failed opaque IDs/codes. There are no default credentials or inferred schedule interval. Deployment needs catalog/credential provisioning, supervisor restart/monitoring and a reviewed cadence; this task does not activate a production process or pg_cron job. Upload entitlement downgrade does not authorize deletion or prevent the deadline worker from applying an already recorded obligation.

Example: the admin gives until 30 November for the missing leaving certificate. The student remains pending throughout that date. On the next local day, the enabled worker rejects an application that is still missing it and records why. A certificate received on 30 November can still be reviewed by the principal later. The existing birth certificate and application history are kept permanently.
