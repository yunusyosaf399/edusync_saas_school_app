# DB03 S7 — private certificate collection and forwarding to the principal

Owner-authorized database-first implementation of the next task: administrator certificate attachment; missing required documents stay pending; complete timely attachments allow forwarding for principal review. This remains an inactive candidate outside executable migrations, without hosted changes, worker credential provisioning, production activation or merge.

## Behavior and boundaries

Three checked staff APIs prepare the document collection, forward the completed collection, and read its queue status. Preparation records the published policy and the administrator's previous-school statement; transfer applicability derives from that retained statement. It is an administrator attestation for later principal review, not government truth or verified identity. Configuration revisions retain old facts and invalidate unfinalized old upload intents. Birth is always required; leaving certificate is additionally required for transfers; all additional applicable REQUIRED policy documents also gate forwarding. A first-time applicant needs no leaving certificate. Core obligations cannot be skipped.

The initial controlled document-kind registry supports BIRTH_CERTIFICATE, SCHOOL_LEAVING_CERTIFICATE and TRANSCRIPT under ADMISSION_DOCUMENT. Other policy kinds fail closed until their semantic purpose/validator mapping is reviewed; arbitrary medical/Finance/payroll material cannot be smuggled through an uppercase custom kind. The initial byte allowlist is single-frame PNG/JPEG, decoded server-side, 1..1,048,576 bytes and at most 20 million pixels. PDF and other formats are not accepted by this initial validator. This is format/content validation, not certificate authenticity or malware-product certification.

Required missing, quarantined, archived, replaced, wrong-version or wrong-purpose files block forwarding. Current policy retirement also invalidates readiness; administrators can record a successor configuration for the current published policy. Matching retries preserve the accepted source; changed intent conflicts; a second key cannot forward the same effective snapshot twice. After an effective forward, collection amendments/new uploads are blocked. Source quarantine/archival, policy retirement or changed configuration invalidates the effective forward; retained forward history is never rewritten.

The root application stays pre-submission DRAFT. Forwarding is a real immutable source plus an authorization-checked derived AWAITING_PRINCIPAL_REVIEW queue state, not a SUBMITTED flag. Principal identity attestation can advance the root without fabricating submission; final review will need to compose that identity source with this exact current document snapshot. No Student, enrollment, roll, admission number, Finance clearance or certificate verification is produced here.

## Commands and source records

| Surface | Authority and effect |
|---|---|
| `app.prepare_admission_documents(application, expected_version, policy, previous_school, key)` | Exact current ADMINISTRATOR/CAMPUS_ADMIN permission/scope; immutable intake revision and root evidence advancement |
| server-only `AdmissionDocumentService.upload(token, application_id, expected_version, document_kind, data, idempotency_key)` | Current server-verified Auth identity, domain permission and `file.upload`, signed school capability/module, measured bytes, purpose-bound worker and immutable private storage |
| `app.forward_admission_to_principal(application, expected_version, key)` | Exact current administrator forwarding permission; complete valid timed roster and immutable snapshot; root advances, no submission |
| `app.read_admission_document_queue(application)` | Exact current document-view permission/scope on administrator or principal role; only app ID/version/status, no names, keys, URLs or byte access |

Four new private sources have forced RLS, restrictive FKs, immutable provenance and denied UPDATE/DELETE/TRUNCATE: admission_document_intakes; admission_document_upload_intents; admission_document_links; admission_document_forwards. Intake/link/forward effects have deferred real receipt FKs and atomic minimized receipt/audit/outbox evidence. Upload intents reserve identity/key before object publication and retain actor, exact application/intake/version, type/size/hash, expiry and issuance revision/digest. Intents are not AVAILABLE metadata and cannot satisfy the roster.

Metadata is inserted PENDING only after actual measurement and permanent private object sealing. The trusted worker transitions it through VALIDATED to AVAILABLE, creates the typed link and commits the root/version/evidence effect in one PostgreSQL transaction. Uploader is the real staff initiator; created_by is an active purpose-bound file-validation SYSTEM Principal. The dedicated schoolos_file_login receives only the fixed private allocation/finalization/entitlement-audit functions, no table DML or executor membership. Anonymous, authenticated and service_role callers cannot call these worker functions. Even a raw SQL owner session fails the session-user guard; privileged deployment operators can, of course, change database code and are outside the application threat boundary.

## Storage and commercial authority

No provider/purpose/entitlement/billing table is added to the school database. ADMISSION_DOCUMENT and its capability/module/validator mapping are fixed code policy; prices, package membership and total quotas are not invented. No permission, operation, role, SYSTEM Principal, storage location, entitlement, credential or provider is seeded/activated. Such configuration exists only in disposable tests.

SupabaseAuthenticator calls the configured current Auth get-user endpoint before decoding the token; checks subject, issuer/audience, expiry/iat, authenticated role and nonanonymous identity; ignores user metadata. It refuses redirects and caller-selected endpoints. PostgreSQL additionally checks current Auth binding/cutoff, active individual, complete current role/permission/assignment/scope and operation contracts at both issuance and finalization. No client acting Principal or capability flag is authority.

Ed25519 signed, canonical, audience-bound snapshots require an allowlisted issuer/key, schema/types, positive monotonic revision, finite configured TTL/maximum age and current effective/expiry bounds. Unknown/missing/stale/suspended/disabled state denies new use. Audit commits before opening a new accepted revision. Durable trusted SQLite state holds the shared high-water mark/signature outside the operational database; no in-memory fallback. BEGIN IMMEDIATE orders activation and SQL finalization across processes sharing the same private persistent local file. The cache is revalidated and locked at issuance and after external object I/O for finalization. Downgrade during I/O leaves sealed private bytes retained but prevents AVAILABLE/link effects.

This coordinator supports **one trusted storage/backend host with a shared private local state file**, including multiple worker processes. Multi-host/NFS coordination is unsupported and must not be enabled using independent caches. Control-plane push/periodic snapshot delivery, key rotation, finite freshness settings, persistent deployment paths and recovery are activation responsibilities. No claim of instant revocation on disconnected servers is made; finite freshness bounds apply.

LocalPrivateArchive is a functioning provider-neutral single-host adapter: private 0700 directory, complete fsynced staging then atomic write-once link, 0400 source object, hash-derived confined path, no overwrite/delete/public/listing API. Same-object retry must match exact bytes. Server reads back and decodes/hashes the stored object before finalization. Deployments must persist/back up its isolated per-school root, protect it from public serving and lifecycle deletion, and protect host administrators/credentials. Other providers can implement the same strict interface only after adapter/IAM/retention parity tests. Database state is not atomic with object storage: failed finalization preserves intent and sealed bytes for safe retry; no retained source is silently purged.

Permanent retention now also denies metadata DELETE/PURGED for ADMISSION_DOCUMENT and TRUNCATE of the shared file catalog. Quarantine/archive preserve source bytes and provenance. The adapter exposes no deletion. Trusted OS/provider operators remain responsible for durable preservation; a SQL trigger cannot stop them deleting disks. The Foundation migrations and original guards are unchanged; additive triggers enforce this stricter admission-purpose rule.

## Deadline interpretation

Collection allocation and finalization enforce the retained current per-kind due date and original application-wide two-calendar-month cap in School-local time. Received-on date and timezone are stamped server-side on the immutable link. A later timezone change cannot backdate a receipt or turn a timely received document into a late one. Forwarding may happen after that deadline when all required documents were actually attached in time; the deadline concerns collection, not principal processing time. Attachment after the allowed window is denied. Automatic REJECTED processing for applications still missing documents is the next separate lifecycle task; this implementation does not claim it runs a scheduler or changes late applications into rejected records.

## Concurrency, privacy and verification

New document commands and file mutation statements acquire the existing authorization fence EXCLUSIVE before any row locks. They then take command key, School, Campus, Year, application and private history/source locks. Publication, role revocation and existing Person writers share the same fence. File quarantine/purge writers cannot overtake a checked forward unnoticed. Current snapshot re-evaluation ensures quarantine after a forward removes it from the effective approval queue. This conservative serialization needs performance/populated-scale testing before release; mixed higher-level transactions must preserve the authorization-first lock prefix.

General receipts/events contain only source/application ID and application version. Previous-school statement, document contents, object keys, entitlement payloads, Auth tokens and signed/private URLs never enter broad evidence. Private status reads do not authorize raw byte download; the later principal document-review implementation must add a checked byte-access surface and enforce different uploader/verifier.

Prepared verification: 25 backend unit/security tests; 25 new rollback-only pgTAP assertions (302 total DB03); 220 frozen Foundation regressions; retained 24 true races; real Auth + signed entitlement + actual sealed-file end-to-end checks; five additional observed PostgreSQL schedules (quarantine before forward, forward before quarantine, same-key forwarding, withdrawal before forward, administrator revocation before forward). The service checks transfers/first-time/extra required documents, idempotency, immutable provenance, permanent retention, outbox-failure rollback/recovery, downgrade during storage I/O, timely/late receipts and privacy. Installation failure must restore the prior application guard and remove all new sources/APIs/file triggers. Exact results will be recorded from the published commit; prepared tests alone are not a pass.

Example: Ali is transferring. Admin records the previous school and attaches a birth certificate; the queue remains PENDING_DOCUMENTS. Once the leaving certificate is attached in time (and any additional required document is present), admin forwards it and the queue becomes AWAITING_PRINCIPAL_REVIEW. Ali is still not a Student, and the principal must independently verify the certificates and later approve the complete admission.
