## Why this next gate is different

The PR #91 signed private-service **synthetic** `principal_verified`, `student_scope_verified`, `student_ownership_verified`, `file_upload_granted` and other Boolean assertions were never authenticated from live PostgreSQL records. A signer willing to assert `true` cannot establish that Principal A still has access to a Student in Campus B. This proposal adds an actual live-D1 resolver **for the eligibility component only**; it is **not yet connected** to issuance/consumption by the Python test ledger. This avoids promoting test-signed fixture claims to real authority.

The existing [rollback-only photo provenance SQL](188_student_profile_photo_provenance_current_entitlement_trial.md) and [authenticated suite #66](../../supabase/tests/domain/66_student_profile_p1_direct_history_authorization.sql) were independently accepted as local evidence. The suite uses an actual local Auth fixture user and genuine protected P0 Student INITIAL enrollment, resulting in the Student's current ACTIVE PRIMARY placement to an OPEN Class/Section Offering. The profile role/grant/policy is real local PostgreSQL evidence, not a caller-created Boolean. Reusing this fixture preserves the frozen same-school/permission context and its 33 pgTAP assertions.

## Explicit unresolved security gates

**Positive return is only a private local permission-and-placement predicate, not an upload/intent permission or Student photo SET.** It does not yet verify an actual trusted service identity, connect to the signed opaque ledger, enforce `file.upload` and control-plane capability `storage.student_photo.upload`, resolve a production-safe school/project identifier for the file service, or prove atomic actor/grant/placement reconciliation with issuance across two systems. Real Principal binding/role revocation needs a reviewed production integration and authenticated worker, including scope-aware current grant reads on finalization. It does not validate exact stored sanitized image bytes, provider storage, file ownership immutable evidence, `PENDING→VALIDATED→AVAILABLE`, retention, cross-host signed-entitlement revocation or true Student DIRECT/P1 APPLY. A standalone private Boolean must never authorize any real upload or file link. Any old synthetic signed `true` claim is still unsafe and no runtime route may accept it.

**Frozen contract unchanged:** **31/35** accepted protected operations; Issue #67 Student Profile Update P1 open; Student photo SET **DENY**; Migration 10 remains 228 inactive `.sql.draft` fragments, 34 relations, 97 permissions, 322 scope alternatives and 36 operation contracts, with no hosted deployment.

**Simple example:** An administrator has a current CAMPUS/DIRECT photo-submission grant for Campus A. The real Student is currently enrolled in Campus A, so the private local resolver can return true. If the administrator's photo permission is switched to Campus B, the same Student A returns false—even if a request still says `student_scope_verified=true`.

**Next recommended isolated task after acceptance:** Review a trusted server-to-PostgreSQL actor context and exact policy/entitlement-to-ledger handoff that fails closed when snapshots, Principal binding, placement or rights change. Do not enable file mutation or true photo SET until that integration and provider lifecycle are independently approved.
