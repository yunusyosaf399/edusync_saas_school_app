# Student Profile P1 typed APPROVAL integration — disposable candidate

Date: 2026-10-17. **Status: REVIEW-ONLY LOCAL ROLLBACK PROPOSAL. NOT installed, not operationally accepted, not production-ready.** Built after PRs #79–#82 and owner-approved SP-01–SP-08 / ADR-005 B.

This slice uses the **existing** D1 protected SUBMIT/independent REVIEW/APPLY engine rather than duplicating reviewer roles, participant enforcement, request transitions, receipt hashing, policy checks or stale invalidation. All new SQL is separately quarantined under `supabase/proposals/`, not an executable migration or the frozen D1 package.

The Student-only SUBMIT adapter `app.d1_submit_student_profile_typed_approval_trial` invokes the approved six-field `UNCHANGED / SET / CLEAR` private planner against the currently locked Student, after authenticated current Principal, actual PRIMARY campus, live `student.profile.update` grant and P1 APPROVAL policy checks. It passes a **fully materialized six-key after-profile** to the existing `d1_profile_submit` to create an authentic PENDING request, selected independent Person reviewer, approval-step assignments, submit receipt and preimage. No Student change/history occurs on SUBMIT or REVIEW.

The existing `app.d1_review_profile_request` remains the only reviewer decision entry point; it checks the eligible different Person, live reviewer role, permission and scope. The trial APPLY adapter delegates to the existing protected `app.d1_apply_profile_request`; this independently rechecks authorization/reviewer evidence and invalidates stale requests. Only when APPLY becomes EXECUTED, an application and receipt chain is verified, the Student final row is compared with the approved requested profile, and a private typed before/after `app_private.student_profile_revisions` row is inserted with original request reason **in the same transaction**. Failure of history insert causes the legacy apply and its receipt/event to roll back. APPLY replay requires its original receipt/application and does not insert duplicate revisions. The proposal adds narrowly scoped **disposable-only** history/receipt/application read privileges for its executing no-login Workflow role, which are removed automatically by the outer transaction rollback.

The new acceptance fixture is an *extra*, rollback-only copy of existing authenticated suite #67, preserving the original 41 pgTAP assertions and all other 74 baseline suites untouched. The fixture performs authenticated typed SUBMIT and replay; confirms no early Student/history mutation; rejects requester self-review and pre-review APPLY; switches JWT to a separate eligible reviewer; approves via real REVIEW; checks revoked-reviewer APPLY INVALIDATES without history; restores the grant; executes a successful authenticated APPLY and historical replay; asserts exactly one restricted old/new history linked to its successful apply receipt/request plus privacy-safe outbox; then rolls back to a SAVEPOINT and allows the unmodified baseline suite to run. A separate connection verifies no trial table or RPC survived.

**Known product acceptance gap requiring a later sealed typed-intent implementation:** The existing approval request/receipt stores a fully materialized six-field projection, not the caller's original tri-state actions. Two different action sets which resolve to identical full projections can hash to the same receipt intent. This trial intentionally does **not** claim full owner-approved SP-02/SP-04 canonical action binding and cannot be used for a real school until that is corrected and independently reviewed. Positive photo SET remains blocked pending same-Student ownership, purpose and entitlement. No zero-placement ALL shortcut is added.

Additional blocked gates: dedicated post-D1 additive versioned history migration; retention/erasure and forensic read design; final purpose-scoped history writer ACL; complete field-by-field tests; current role/grant/policy switching, two-session APPLY/DIRECT races, and acceptance of real production typed SUBMIT/APPLY/replay. The old six-positional public Student Profile RPC remains unchanged and disabled. The new test-only interfaces have no production footprint; **31/35 accepted protected operations, Issue #67 still open**, Migration 10 remains .sql.draft, original 34 D1 relations and 228 frozen fragments unchanged, and no hosted Supabase database changed.

**Simple example:** a school clerk requests to update the student's previous school, but no field changes until an independently authorized reviewer approves and the request is applied. If the reviewer's permission is revoked, APPLY invalidates the request instead. Only a successful APPLY can add one private, immutable old/new history row.
