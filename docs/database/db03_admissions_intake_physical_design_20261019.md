## 2. Domain boundary and lifecycle

An Applicant/Application is not a Student. Registration creates an Admissions application only; no Student ID, Enrollment/roll, Family membership, Principal, Auth account, entitlement or provisional D1 enrollment is created. The proposed application lifecycle is **DRAFT → SUBMITTED → IN_PROGRESS → ACCEPTED → CONSUMED**, with independent retained **REJECTED / WITHDRAWN / CANCELED** terminal outcomes where approved. Cancellation after CONSUMED does not erase Student; use D1 protected Student/enrollment lifecycle instead. Do not equate ACCEPTED or an accepted offer with a committed student.create. Only a READY final handoff can be consumed.

**Candidate stage flow:** register draft → resolve Person safely → submit against exactly one published policy version and allocate an application number → record document verification / admission test / interview / approval / admission fee outcomes as required or configured skips → issue offer (if approved as a distinct business step) → accept application and issue final, unused handoff with admission number → invoke future D1 protected student.create atomically → CONSUMED. Each stage has immutable revisions. The policy's configurable list is deployment-owned: ordered known kinds, explicit REQUIRED or SKIPPED, versioned effective publication and no executable SQL/configuration injected by schools. A policy-allowed skip creates an explicit SKIPPED outcome; a required stage cannot be skipped from a client flag.

**Proposed separate exception path:** an exceptional bypass of a REQUIRED *non-financial* stage must be authorized by a policy-listed exception kind, exact application/stage and Foundation independent approval. This is *not* the same as a configured SKIPPED stage and must never create Finance clearance, identity verification or a generic student.create override. Until the owner approves exception kinds/reviewer routes, required-stage exceptions **deny**. A final admission.accept decision is always an authorized protected action even where an optional approval stage is SKIPPED. A failed assessment can only be overturned by retained approved correction/exception, not by editing a score or boolean.

**Offers:** Proposal only: ISSUE creates an immutable offer revision for the exact application version/policy/placement, expiry and conditions if those are explicitly approved; ACCEPT/DECLINE/WITHDRAW/EXPIRE records a new outcome rather than overwriting the original offer. Offer acceptance is not fee verification or D1 placement/capacity reservation. Letter/document is rendered on demand from historical offer identity and facts, not stored as a default PDF. Whether an offer is mandatory, expires and can be reissued is an SC-01 owner choice.

**Cross-record invariants:** composite keys/constraint triggers validate same-school policy, profile, year, section→class/campus/year ancestry; stage belongs to application's snapshotted policy; document/assessment/outcome references point to same application and stage kind; no cyclic or cross-application supersession; predecessor revision < successor; no duplicate active branch heads; timestamps of subsequent business states monotonic and sensitive changes never mutate historical facts. Retained application amendments to person/destination/policy invalidate affected stage approvals, fees, offers and unconsumed handoff, preserving old snapshots. Immutability guards and indexed locking must enforce these under concurrency, not only application checks. Two deferred FKs (application→handoff and handoff→application) require a documented create/order and validated constraints; preferably simplify by removing redundant reverse pointer if owner review permits.

**Person source conflict:** #79 requires Person on initial application row while saying uncertain identity may remain DRAFT. Recommended candidate: allow NULL Person on DRAFT (with appropriately restricted draft contact kept only in typed restricted intake evidence), require canonical Person and a current same-application admission_identity_resolutions head before SUBMITTED or final handoff. Alternate: create a provisional Person through an approved server identity process before DRAFT. Neither is frozen. Duplicate matching must use authorized canonical identifier lookup and manual ambiguity workflow; name/photo alone does not auto-merge or disclose unrelated Persons. Existing D1 UNIQUE(students.person_id), UNIQUE(school_student_id) and UNIQUE(admission_number) are independent final defenses.

**Application/Admission number contract:** application number allocated at first successful SUBMIT; admission number allocated only when issuing a final approved handoff (#79 candidate). Both use school-scoped, kind-specific rendered UNIQUE ledger and atomic series locking; exact format is versioned, 1–8 digits, full/two-digit academic session, no recycle on rejection/cancellation, no MAX()+1, no promise of gapless display. A numeric serial is not globally unique independently of its rendered number. D1 permanently allocates school_student_id at consumption, and roll per selected D1 policy/namespace. Never use an Admissions sequence as D1 Student ID/roll allocator. Concurrent same-Person applications are serialized on canonical Person and constrained by a nonterminal key; rejected/withdrawn attempts retain old identifiers and may be re-attempted only by authorized new application.

## 4. Protected command boundaries, permissions and disclosure

**Proposed (not registered) Admissions permission families:** admission.policy.manage / admission.policy.publish; admission.application.create / view / amend / withdraw / decide / export; admission.identity.resolve; admission.document.upload / view / verify; admission.test.record / admission.interview.record; admission.stage.record; admission.offer.issue / respond / view; admission.exception.request / approve; admission.accept; admission.handoff.view. Exact codes, scope sets, route classes and approval policy registration are **pending product/security owner sign-off**; do not seed role grants, reuse D1's catalog count or assume a Principal title grants permissions. Prefer ALL/CAMPUS with exact placement CLASS/SECTION only where existing Foundation D1 typed resolver supports it. Distinguish all-application status summaries from identity, applicant contact, document bytes, test score/remarks, protected reasons and Finance clearance. Exports require their own permission and an explicit column allowlist. No applicant/FAMILY/student portal read from an unactivated relationship.

**Proposed operation boundaries:** fixed typed register-draft; resolve-identity; submit; amend/withdraw/cancel; record stage/test/interview/document verification; publish policy; request/review exception; issue/respond to offer; decide accept/reject; issue/invalidate handoff. Direct RPCs are default-deny unless separately enabled. No arbitrary JSON patch, caller actor/role list, policy status flag, assessor impersonation, custom table name or arbitrary client-supplied clearance. Protected functions derive current active Principal, current complete permission/scope/relationship and expected versions server-side, acquire Foundation (71001,1) SHARED before business verification and use Foundation receipt/approval engines. P1/P2 route and independent reviewer class for acceptance/exception/policy publication are **unfrozen**; do not guess them from stage count. Workflow SUBMIT, REVIEW, explicit APPLY remain separate transactions when approval applies, with requester/reviewer Person separation and current grant/step rechecks. Deterministic stale approval invalidates without a domain effect; infrastructure failures roll back/retry rather than being converted to approved success.

**RLS:** ENABLE + FORCE on every proposed app_private relation, deny anon/authenticated/service_role raw read/write. Dedicated narrow NOLOGIN executor(s) after architectural review, not schema owner as a runtime shortcut; internal grants column-scoped where feasible, no role membership chain, explicit private EXECUTE only for trusted executor. Expose only allowlisted typed app checked reads to authenticated, each with server-derived Principal, exact scope and object ancestry, current protected participant authority and no generic row JSON. Storage cannot leak through file URL, access token or object key. File purposes for applications are not installed: register exact deployment-controlled document kinds/purposes only after classification, entitlement and relationship review. Private uploaded bytes remain Foundation file_objects/provider-neutral; no generic files/attachments engine.

**Audit/receipt/outbox:** same-transaction Foundation typed receipt, immutable request/decision evidence, domain history and identifier-only audit/outbox after each accepted command. #79 proposes admission.policy.created/published/retired, application.created/submitted/amended/withdrawn/rejected/accepted/consumed, identity.resolved/corrected, document.linked/verified/rejected/superseded, assessment.recorded/corrected, stage.recorded/invalidated, fee.cleared/invalidated, number.allocated/canceled and handoff.issued/invalidated/consumed event *candidates*; none is claimed registered. New offer/exception/cancellation event names require deployment registration decision rather than invention. Receipts bind actor, command, application, snapshot versions, typed intent and immutable resulting IDs. Broad evidence must exclude person identifiers of restricted class, DOB/contacts, document digest/key/URL, payment proof/amount, test answers/remarks and private reason text. Authz-sensitive reads and downloads reauthorize even for exact terminal replay.

## 5. Finance-owned clearance bridge — no invented payment truth

The published policy explicitly says fee is NOT_REQUIRED or REQUIRED. NOT_REQUIRED generates a validated policy-anchored clearance with no Finance refs. REQUIRED **cannot issue a final READY handoff** until a separately deployed Finance-owned typed verification identifies the exact payable admission obligation, currency/amount, verified payment allocation/settlement/current obligation version and nonreversed status *for this application*. A bank/wallet screenshot, staff-entered paid=true, a payment receipt number string, direct D1 insert or school administrator waiver is never financial proof.

Finance must define authoritative interface and reversal/change fence: which obligation identity, charge version, settlement/credit application, amount due, effective reversal version and locked verification semantics are returned. Admissions persists only a typed, versioned clearance evidence reference/decision, not ledger balances, allocations, payment transactions, refunds or invoice/receipt numbers. Subsequent Finance reversal **before consumption** invalidates or prevents consumption of READY handoff after serialization/recheck; Finance reversal **after consumption** leaves Student/Enrollment/history intact and Finance owns outstanding debt and remediation. There is no automatic Student deletion. If Finance bridge is missing, REQUIRED stays blocked. Any exemption is a separately approved Finance policy, not Admissions free-form override.

## 6. Final durable handoff and D1 read-only dependency contract

Proposed handoff identifier is **server-issued admission_handoffs.id** plus canonical revision. Issuance occurs only after current acceptance, verified Person/version, exact published policy and latest required stage/exception/offer/approval evidence, current Fee clearance and valid same-school year/campus/class/section ancestry. Admission number allocated in the issuance transaction, not by a client. Handoff is durable, immutable in identity/placement/number/approval/fee snapshot, single-use, with READY→CONSUMED or READY→INVALIDATED terminal transitions, never reopened. A corrected accepted application must invalidate its unused READY handoff and issue a new revision through a newly reviewed command; a CONSUMED handoff cannot be reissued, and later moves use D1 enrollment commands.

**Handoff validated input for future D1 student.create** (only after independent approval): handoff UUID, expected application_version and expected handoff revision/state binding, D1 typed idempotency key and current actor derived server-side. No caller-supplied Person ID, student ID, admission number, section override, fee boolean or client-approved snapshot determines truth. D1 reads the locked stored handoff and verifies current application/identity, current unexpired policy/offer/stages/approval/clearance, destination ancestry and lack of any Student for the resolved Person. Actor must independently have **both** enabled student.create and student.enrollment.place for the destination, not only admission.accept.

**Atomic result** must be one D1/Admissions same-database transaction: consume READY handoff, allocate D1 permanent school_student_id; create Student using verified Admissions admission_number and admission_serial, initial status event/projection, PRIMARY initial Enrollment, authoritative roll policy/allocation, approved capacity override evidence if needed, Foundation receipt and one identifier-only student.created outbox/audit. The handoff records resulting Student ID, receipt, actor and time, and application projection becomes CONSUMED. Any failure rolls back *all* effects, including allocator advancement/consumption. Same-key replay after current authority verification returns the retained result, without another Student/number/roll/event; changed intent conflicts. Competing keys cannot consume the same handoff.

**No seats are reserved by an offer or READY handoff.** Class and Section capacity are rechecked against actual accepted/future PRIMARY placements at intake, including every effective interval breakpoint per D1 #31. Full capacity denies unless the existing separately authorized student.capacity_override contract passes, with typed immutable evidence. The provisional destination may need an Admissions amendment/new handoff if the Section fills. The D1 Student ID allocator, roll_policy_revisions, roll_allocator_states and roll_allocations are solely D1-owned; RP-01–RP-07 (DB-02) or RC-01–RC-08 (DB-01) decisions cannot be inferred here.

**Cross-package lock plan requires independent integration proof (SC-06):** begin with Foundation authorization SHARED lock → canonical command-key receipt lock → ordered Foundation Principal lock; discover immutable ancestry/Person before taking rows, then respect D1's established school/config/Student-ID + roll-policy/allocator rank → Person/Student → Academic Class → Campus → Academic Year → Class Offering → Section Offering → child history. Add Admissions application/handoff/numbering and Finance verification locks at a **jointly approved, rank-safe position**, never taking an earlier-ranked counter/Person after a locked Section, and never letting FK/trigger locks invert the hierarchy. Recheck authorization/versions/policy and Finance evidence in new statements after lock waits. This is a proposed dependency plan, not a falsely frozen executable lock schedule. READ COMMITTED and full-transaction rollback are the D1 contract. Finance reversal and handoff consumption must share an exact serialization fence in their respective implementations; a stale clearance cannot be cached as authority.

## 8. Positive, negative and two-session acceptance matrix (future; none executed now)

**Intake (A34–A46):** genuine Admissions-issued READY handoff → authenticated dual-permission student.create → one Student UUID/ID/admission number/status/PRIMARY enrollment/roll and one receipt/event; wrong Person/year/campus/class/section/version/policy denies; used/invalidated/withdrawn/expired handoff denies; nonexistent preseeded student ID denied; existing Student for Person denies; stale app/identity/approval/Finance/authorization denies; capacity full denies; approved full-capacity override emits exact evidence; changed-intent replay denies; exact terminal replay returns stored ID without duplication; mid-transaction abort rolls back handoff/counter/status/enrollment/roll/evidence; later legitimate Student enrollment MOVE does not change consumed intake result.

**Real two-session observed-lock races (R01–R12, not mocked):** same Person simultaneous SUBMIT; series allocation cross-policy collision; submit versus withdraw; document correction versus final acceptance; assessment correction versus final acceptance; revised policy/exception versus issue; competing offer response versus acceptance; two keys consuming one handoff; authorized intake versus cancel/invalidate; Finance reversal versus intake under shared fence; capacity last-seat intake versus competing placement; roll-policy boundary replacement/roll allocator or permission revocation versus intake. Assert observed blocking order, committed single winner or deterministic retry/invalidated result, no orphaned partial effects and exact retained history/receipt counts. Test at READ COMMITTED, force deferred constraints immediate before rollback. Includes failure injection and crash/lost-ACK replay.

**Security/build gates:** anonymous, FAMILY, unrelated campus, student portal, role-name-only and disabled-operation callers denied; FORCE RLS and SQL grant audit; source/target sensitive reason/identity/payment omitted from broad events; no D1/Finance/Foundation mutations by Admissions package; local clean-install + populated upgrade + versioned migration compatibility + repeatable regression are required before any implementation readiness claim.
