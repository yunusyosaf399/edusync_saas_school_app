## 1. Verified Foundation behavior — exact source and safe limits

Read these existing, unmodified `main` artifacts:

- `supabase/migrations/20260924122448_foundation_receipts_events_settings.sql`: actual `app_private.command_receipts` physical DDL. Receipt columns include `id uuid PK`, `principal_id`, `operation_id`, `command_kind`, `idempotency_key`, `canonical_payload_hash`, `canonicalization_version`, `expected_target_version?`, `request_id?`, `expected_request_version?`, terminal `state`, `result_kind?`, `result_ref? uuid`, `result_summary? jsonb`, `error_code?`, `completed_at`, `created_at`, `created_by`. **None is a dedicated Student, accepted D1 Enrollment, Curriculum Revision, effective interval, aggregate generation, selected-group-set or finalized-empty field.** Source has uniqueness `(principal_id,operation_id,idempotency_key)`, `(id,operation_id)` and `(id,operation_id,request_id)`. `result_ref` is not a database FK to a DB-04 finalization row; `result_summary` has only an object-type guard.
- `supabase/migrations/20260924122451_foundation_structural_triggers.sql`: `command_receipts_immutable_guard` invokes `app_private.deny_evidence_change` on UPDATE/DELETE. Immutable receipt history is credible **command evidence**, not intrinsically a per-Student/current-set materialized state table.
- `docs/database/05_foundation_physical_catalog.md` and `06_foundation_constraint_matrix.md`: terminal `SUCCEEDED`/`REJECTED` outcomes, server-canonicalized idempotency, read-authorization on replay, typed domain result objects; Foundation receipt state excludes a generic `FINALIZED` enum.
- Existing D1 canonical Student and Enrollment remain externally owned, and Enrollment has no `row_version`. No DB-04 selection table/SQL currently exists.

**Conclusion [SOURCE + INFERENCE]:** Foundation receipts can prove **a successful specifically registered command** occurred, but they do **not by themselves provide a normalized indexed key** for `(student_id,enrollment_id,revision_id,valid_interval)`, a unique “current finalization head,” or an authoritative accepted empty choice set. A receipt's broad `result_summary` and generic `result_ref` must not be treated as a free-form cross-domain JSON query or unrestricted typed target. Reusing them as complete DB-04 state would require a separately owned, reviewed key/lineage/projection and narrow authorized reads.

## 2. Three non-approved physical choices

| Option | Exact implementation idea | Benefits and missing evidence | Required decision |
|---|---|---|---|
| **BF-1 (recommended if queryable finalized state is required): domain-owned eighth relation** | Introduce `student_subject_selection_sets` as an **append-only accepted finalization fact**. It records an accepted choice set even when the set has **zero** elective members, and provides authoritative version/supersession of finalized batches for one Student+accepted Enrollment+published Revision/applicability and valid interval. Existing `student_subject_selections` remain the individual member-history relation; candidate `selection_set_id` FK links each accepted member to its set. | Relational keys, exact interval/head constraints, zero-member proof and historical correction/Exam replay. **Entity count becomes eight** and needs CUR-08 owner approval, privileges/constraints, local race tests and downstream signoff. | Owner approves adding one DB-04 entity and versioned set membership; Foundation owns receipt contract, DB-04 owns state. |
| **BF-2: existing Foundation receipt + DB-04-owned narrow projection** | Accept a typed `curriculum.selection.finalize` command with immutable Foundation `SUCCEEDED` receipt and `result_ref` denoting a reviewed domain identifier. Build an authorized **domain-controlled projection/read** that can locate the winning finalization generation by exact Student/Enrollment/Revision, including empty accepted sets and supersession. | May avoid a separate **physical table only if** the current seven relations already contain enough indexed, immutable linkage or an approved existing domain aggregate key. **Current seven-table proposal does not prove such a key exists for the empty set.** Foundation `result_summary` as arbitrary JSON is **not** a sound substitute. | Independent SQL/schema/ACL proof and Foundation receipt/executor owner signoff; if it cannot prove empty and current head, reject BF-2 and use BF-1 or BF-3. |
| **BF-3: no queryable finalization state in v1** | Treat accepted elective subjects as the only persisted eligibility evidence. An empty selection is simply “no elective selected,” **not proof of finalized empty**; only per-command acceptance might be observable in own receipt response. Do not display `FINALIZED` state or impose a separate completion policy. | Keeps seven-table design plausible and minimal, but **weakens the meaning of approved CUR-03-B1 finalization** and cannot distinguish unanswered from deliberate zero choices. Product owner must explicitly accept this limitation; no silent downgrade. | Owner product change to B1 or explicit confirmation that independent status is unnecessary. |

**BF-1 minimal *candidate* row shape, NOT proposed SQL/approval:** `id uuid PK`; `student_id uuid NN FK D1 students(id)`; `enrollment_id uuid NN FK D1 enrollments(id)` bound to same Student via existing `enrollments(id,student_id)` candidate; `revision_id uuid NN FK DB-04 curriculum_revisions(id)`; `applicability_id uuid NN FK curriculum_applicabilities(id)` matching Revision and exact D1 School/Year/Class/Section ancestry; `effective_from date NN`; `effective_until date?` original upper-exclusive; `supersedes_id uuid?` same Student+Enrollment+Revision; `accepted_at timestamptz NN`; `accepted_by uuid NN FK principals(id)`; `command_receipt_id uuid NN FK command_receipts(id) UNIQUE`; `set_content_digest text NN` including **empty** selected set; `recorded original and one-way correction closure evidence`. Exact data types/temporal close names, unique current-head and overlap constraints remain design review. This relation contains **no copied D1 Subject/Enrollment authority**. Member history must be tied to a set ID (candidate new FK on selection rows), with mandatory **cross-row exact group min/max and set membership reconciliation** at apply and downstream checked read.

**Avoid false history:** If a finalized 0-choice set is later amended to 1 choice, retain the original BF-1 row and create a linked successor; receipt and content digest remain immutable. Do **not** turn previously published Exams into a new as-known election by searching the latest Student set. Exams consumes immutable source set/revision/Rule/Section/Enrollment and its own `valid_at` and `observed_at` snapshot (CUR-07 signer).

## 3. Verification requirements before committing any physical model

1. **BF-1:** a finalized zero-member set emits one reviewed receipt and a new immutable finalization row, with **zero** `student_subject_selections` members. A later valid new finalization supersedes head without deleting initial evidence; checked read returns exact status under Student SELF/FAMILY CHILD/academic admin restrictions, and no unverified PII leaks.
2. Two physical connections finalize two different sets for the same Student+Enrollment+Revision and business interval; the common Foundation→School→Student→D1 Enrollment→Curriculum applicability/set lock **and unique current head** allow one winning result. Same-key replay after fresh authority returns the same set ID, not another row; changed intent conflicts.
3. A Student moves/ends D1 Enrollment concurrently with finalization. No set may become the destination Enrollment's set; old set remains auditable.
4. Publication of a revised group cannot orphan accepted future finalizations; calculate date-segment impact without acquiring a Student row late and rerun live state/version checks after lock waits.
5. BF-2, if selected, **must supply equivalent proofs** despite no new relation, including empty set, exact indexed source/provenance and multiple revision/correction heads—not merely a `result_summary` JSON query.
6. BF-3 must be explicitly owner-approved as changed product behavior, with no false FINALIZED UI state or misleading enrollment/elective completion report.

**No current tests have been executed; no Supabase project has been changed.** Authorization/operation catalog deployment, release-ready D1 and CUR-04–CUR-08 approvals remain implementation prerequisites.

## 4. Owner recommendation and next stage

**Recommended physical direction: BF-1** if EduSync is intended to distinguish “choices submitted—even zero” from “not submitted”; it is a straightforward queryable invariant and does not abuse Foundation's idempotency receipts. This **would raise the candidate Curriculum entity count from seven to eight**, only after CUR-08 approval. If owner prefers a seven-entity v1, BF-3 is possible but must be explicitly approved as a reduced completion requirement; BF-2 requires an independent physical proof that is **not yet available**.

Separately, **B-M1** is the originally approved-as-proposed strict availability check `max≤Section offered members`; **B-M2** cap-only `max` can exceed available members when `min≤available`. The latter might be more flexible for campuses offering fewer electives, but the owner **has not approved this change**, so keep B-M1 as baseline until asked.

The replies will govern the final CUR-08 schema and G/GI acceptance outputs. Do not seed a new relation, status field or SQL before explicit product and schema-owner approval.
