## 2. DB01 ↔ DB02 Roll policy / allocator handoff

**Approved common semantics:**
- Initial Roll generation follows owner Option A: **automatic only during accepted initial Enrollment/placement**, never a manually entered initial Roll at Admissions/Student creation; authorized correction after placement is a separate route.
- A School has its own Supabase project and may contain multiple Campuses. Namespace depends on immutable `PERSISTENT_STUDENT` or `ACADEMIC_CONTEXT` policy mode. Do not infer current namespace from a displayed Roll number or choose `MAX(number)+1`.
- DB01 carries `student_id`, immutable current Enrollment/source allocation, source stored `policy_revision_id`, School-local date and current Student version; retains `supersedes_id` and inherited `origin_allocation_id`, protects allocator high-water and checks historic reservation collisions.
- DB02 I03 locks School and exact current source/future accepted Enrollment/Roll before REPLACE; DB02 I04/I05 atomically closes the old policy, appends a revision and creates applicable persistent/academic allocator pools, preserving historical Roll allocations. Current I05 supports only private draft INIT/REPLACE; **I06 receipts/events, authenticated DIRECT/APPROVAL, two-backend cutover, non-author security review and G02 future Class Offering pool hook remain OPEN**.
- DB01's P1 APPROVE/REJECT and APPLY are separate authenticated commands; DB02 replacement cannot re-use their request/approval receipt or their `enrollment.roll_corrected` event. DB02's separately selected proposed outbox `student.roll_policy_changed` belongs to DB02 I06 evidence, not DB01. No cross-domain event alias or forged broad event may be installed.

**Critical handoff R10-01 (OPEN): post-cutover current Roll on retired source policy.** The actual DB01 `effect41_01_db01_correct_source_prelock.sql.draft` locks the **stored** revision but currently returns an invalid source when `policy.effective_until IS NOT NULL AND business_date>=policy.effective_until` (and also rejects not-yet-effective sources). DB02 I04/I05 today-only REPLACE explicitly closes the old revision yet intentionally retains existing Roll allocations. Consequently an old current Roll following REPLACE can remain retained/current while a later DB01 correction referencing its source policy is denied. This **fail-closed code behavior is supported by source inspection**, but **whether to keep it or provide a separately approved post-cutover correction path is a product/DB01+DB02 owner decision**. No silent rebasing of old Roll onto the new policy and no mutation of historical allocation is authorized. Must be exercised with **both latest implementations in one database**, including PERSISTENT_STUDENT→ACADEMIC_CONTEXT and reverse transition, high-water and collision proofs.

**Critical handoff R10-02 (OPEN): new academic offerings.** DB02 I05 creates revision-specific academic pools for eligible Class Offerings existing when INIT/REPLACE commits; its [I05 contract](https://github.com/yunusyosaf399/edusync_saas_school_app/blob/db/db-02-i05-atomic-allocator-pools/docs/database/db02_i05_atomic_allocator_pool_provisioning_20261023.md) explicitly leaves the *later* Class Offering create/reopen provisioning hook G02 open. Do not install a policy that leaves later enrollment placements without a required pool. Requires Academic/D1 and DB02 owner signoff, then exact two-backend Class Offering/PLACE/REPLACE acceptance.

**Critical handoff R10-03 (OPEN): shared command context and lock order.** DB01 SOURCE/DIRECT/P1 APPLY locks Foundation auth→School→stored policy→allocator→Student→Enrollment/Roll; DB02 I03/I05 obtains Foundation auth→School→source revisions/pools→sorted Campus→Academic Year→Class→Offering before commit. Existing **separate** CI proves local races, **not** inter-owner PLACE/CORRECT/APPLY versus REPLACE (including both arrival orders, source retirement, policy version revocation and replay after cutover). Cross-domain concurrency must observe backend blocker PIDs, compare precise rollback/evidence counts and revalidate current School-local date and actor grants after waiting. An unexpected deadlock or mismatched lock rank blocks promotion.

**Critical handoff R10-04 (OPEN): pool eligibility and retention.** DB02 has one persistent NULL-Class Offering pool or per-eligible academic Offering pools for the **new revision**, while DB01 correction reads its source's **stored revision pool**. Combine tests for no reuse of any historical persistent number, no number-collision or reservations being lost across REPLACE, no partially installed pools, exact inherited Roll origin, one current Roll, canonical old receipt replay only where current authorization permits. Do not assume successful separate branch tests establish these mixed behaviors.
