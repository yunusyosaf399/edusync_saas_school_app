# DB03 S4 — recorded inspection of original identity documents

**Implementation candidate, 26 October 2026.** The owner selected original-document staff inspection, staff-only certificate attachment during unresolved drafts, and a different authorized verifier from the certificate uploader. Exact questions/answers are in [the decision record](db03_owner_decisions_original_inspection_draft_files_20261026.json). The earlier one-staff identity-verifier choice remains. These are product choices, not deployment or code acceptance.

This slice implements the manual original-inspection source for an **existing canonical Foundation Person**. It does not create/merge People, automatically match names, claim government verification, upload files or mark a certificate authentic/VERIFIED. File collection and independent digital-document verification remain a distinct next integration. The manual source can be recorded before a digital copy exists; the later mandatory-certificate completion gate must still require administrator submission and independent file review. The database cannot establish that a human actually saw a physical original; it records the accountable staff attestation and its precise meaning.

## Typed source and command

`app.attest_admission_original_identity(application_id uuid, expected_application_version bigint, person_id uuid, expected_person_version bigint, original_reference text, reason text, idempotency_key text)` returns resolution ID, application ID, resulting application version and inspected Person version. There is no client-supplied verified boolean, actor, time, resulting state, source UUID or government-service result.

One current Auth-linked active INDIVIDUAL must have the exact enabled `admission.identity.attest` operation/permission chain with current ALL/DIRECT or exact CAMPUS/DIRECT scope. The operation handler, contract/payload version 1 must match; configured approval fails closed. No operation/permission row is seeded or activated. Public EXECUTE is authenticated only. The existing NOLOGIN identity executor owns the fixed definer command with fixed search path and no BYPASSRLS; auth and evidence retain their dedicated roles. No raw Person/history privilege is granted to clients. Input Person lookup happens only after application-scope authorization, with the same denial for unauthorized-campus probes regardless of whether a Person UUID exists.

The private `admission_identity_resolutions` relation (#07) is the actual staff-attestation source, not a placeholder external-verifier table. It stores method `ORIGINAL_BIRTH_CERTIFICATE_INSPECTION`, original reference/reason privately, selected Person and server-read version, actor/time, application version/evidence epoch, receipt and a linear immutable revision/predecessor chain. No national-ID/DOB index, document bytes, signed URL or arbitrary external source pointer is invented. Reference/reason limits (200/1000 characters) are engineering bounds, not quoted owner selections; they are not a prompt to copy national identifiers into the reference. Sensitive original documents remain subject to the future approved private-file purpose/retention contract. No automatic destruction policy is invented.

## Application binding, staleness and history

S4 replaces only DB03's own intake guard and NULL-only Person constraint. DRAFT initially remains unresolved; only the identity executor may bind a Person and increment `stage_epoch`. The workflow executor retains create/grace/withdraw behavior and cannot change identity or its evidence epoch. Same-Person reinspection appends a new revision. Switching or clearing a bound Person needs a separately reviewed correction route and is unavailable. The policy binding stays NULL and only DRAFT/WITHDRAWN states exist; SUBMITTED, numbers, READY and enrollment are unavailable.

The command locks authorization shared fence → actor/operation/key → School → existing Person → Campus → Year → application; it rechecks current authority, exact root and Person versions, active Person and open destination after waits. The common School lock serializes supported S2/S3/S4 writers. Raw Foundation Person changes are protected by the actual Person row lock. These local tests do not approve the future complete D1/file/Finance lock graph, whose writers need integration before submission/consumption.

The private security-invoker `admission_identity_current` projection reports CURRENT_STAFF_INSPECTION, REVERIFICATION_REQUIRED or WITHDRAWN. A Person state/version change, including an unrelated display-name correction, makes the old inspection stale until fresh authorized inspection of that same Person. Stored Person versions are historical snapshots, never composite FKs to mutable versions or cascading rewrites. No final gate may rely on the projection label alone without rechecking the actual source under its integrated locks.

Withdrawal keeps any previously bound Person and all inspections. Unresolved withdrawal still retains NULL Person as already selected. Grace neither verifies identity nor changes inspection history. The earlier original two-month certificate cap remains unchanged.

## Evidence and replay

One atomic effect updates the Person projection/application version/evidence epoch, appends inspection, and writes one receipt/audit/outbox via the dedicated evidence writer. The deferred receipt FK must resolve at commit. Output failure rolls back every part. Raw history UPDATE/DELETE/TRUNCATE and arbitrary inspection inserts are denied.

Canonicalization version 1 hashes a fixed JCS array of application/version and Person/version strings plus SHA-256 digests of private reference/reason. Receipt namespace is actor + operation + key. Result kind is `ADMISSION_IDENTITY_ATTESTATION`, with exactly four keys: resolution ID, application ID, application version and inspected Person version. Audit/outbox event is `admission.identity.attested`, with only resolution ID/application ID/application version. No Person UUID, name, original reference or reason enters broad event payloads.

Matching retries reauthorize current action/scope and verify retained immutable history and matching evidence before returning the original response. Changed private evidence conflicts. Historical replay after a Person change or withdrawal returns the old inspection result; it does not refresh current verification or reopen a draft. A fresh key/version and a new actual inspection are required for reinspection. Revoked authority cannot replay. Person creation, matching discovery and correction are not smuggled into replay or selected merely by UUID.

**Example:** a qualified staff member inspects Ali's original birth certificate against Ali's existing canonical Person record and records a private reference. If the Person record changes later, that inspection becomes stale; the original entry remains, and a fresh inspection appends a successor. Ali's admission is still not complete, and his uploaded certificate must later be checked by a different authorized member of staff from its uploader.
