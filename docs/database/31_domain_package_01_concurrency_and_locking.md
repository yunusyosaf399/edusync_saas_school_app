# D1B2 — transaction, serialization and deterministic lock order

**Design only.** This extends, and does not change, [Foundation execution security](../security/04_foundation_execution_security.md). Foundation migrations/tests, authorization lock and command-receipt protocol remain frozen. D1B3 will define entry points and permissions; D1C will implement and execute the contracts.

## Transaction contract

Use `READ COMMITTED`, one transaction per protected command. Reject unsupported higher-isolation invocation before business mutation; `REPEATABLE READ`/`SERIALIZABLE` are not claimed safe for this design. The first lock is Foundation's transaction-scoped school authorization lock `(71001,1)` in **SHARED** mode for a D1 mutation. D1 never upgrades it and never writes Foundation authority. Next, for a registered idempotent command, take Foundation's namespace-`71002` command-key advisory lock and compare any existing receipt with the canonical intent. A matching terminal receipt returns the prior result without allocating another ID, roll, Student or enrollment; mismatched intent fails. Then lock Foundation actor/target principals in UUID order, perform the Foundation operation/policy/request/step portion where applicable, and enter the D1 typed-row order below. Recheck verified identity, complete grant, business state and server time in a **new statement after every wait**; do not trust a pre-lock snapshot. Write domain data, terminal receipt, typed evidence, audit and outbox in the same transaction. No second D1 receipt table or global authorization lock exists.

Every D1 writer, including restricted defensive triggers on direct privileged fixture DML, must participate in the same serialization protocol or fail closed. The trigger may enforce row-local immutability/ancestry itself, but a cross-row overlap test must lock the declared parent before scanning. SQL owners able to disable triggers are explicitly outside this application invariant and require deployment controls. A transaction that fails PostgreSQL deadlock, lock timeout or serialization-style conflict rolls back **all** rows/evidence. The caller may retry the whole registered idempotent command using its same key and canonical intent; never retry an unregistered, non-idempotent mutation blindly. Unique/FK/CHECK failures are business rejections unless a separately demonstrated contention retry rule applies.

## Global D1 typed-row hierarchy

After Foundation's own lock/receipt/principal/operation/request/step order, acquire only the categories needed, in this fixed order:

1. **School/config/allocator:** `school_profiles` school row for school-wide catalog/policy/namespace changes, then D1 Student ID allocator, roll policy, roll allocator rows. A new allocator row is serialized by its existing school/policy parent before insert. This school's row is a deliberate coarse anchor, never an alternate tenant key.
2. **Person, Student, Employee:** Foundation Person rows when involved, then D1 Student rows, then Employee rows. Within each relation sort UUID ascending. Creation without a D1 row locks the existing Person and required school/allocator anchor first.
3. **Family:** Family rows sorted UUID; the relevant Student row is always acquired first. FAMILY principal rows belong to the earlier Foundation-principal phase, including the target principal on membership change.
4. **Academic catalog and target:** Academic Class → Department → Designation → Campus → Academic Year → Class Offering → Section Offering → Room → Subject, in that fixed relation order; UUID ascending within each. A target from both source and destination is collected before locking; no direction-dependent order. Catalog archive takes its own row and does not lock all existing children because existing accepted facts remain valid.
5. **Child current/history rows:** sorted by relation name then UUID when existing; insert new rows only after all parent anchors. File/receipt/outbox writes follow the applicable Foundation order, and a command that requires a Foundation workflow target must enter D1 only at the Foundation-declared typed-target point.

No D1 command acquires a lower category after a higher one. In particular, promotion does not lock source Section before destination Class; it locks **all** affected Class Offerings UUID-ascending and then **all** affected Sections UUID-ascending. Section room assignment locks Class Offering → Section Offering → Room, so Room follows its Section. Teacher assignment and capability end share Employee as the anchor; any required Campus/Year/Class Offering precedes Section/Subject, and a room target precedes Subject. Family access revocation and a FAMILY-authorized child mutation share Student then Family after the Foundation authorization lock and principal locks. Discover the complete immutable FK/ancestry parent set before taking D1 typed-row locks, acquire required parent/key-share locks in this same order, and revalidate after waits; do not let an FK check or defensive trigger acquire a lower-ranked parent afterward. If a required parent is discovered only after taking a higher category lock, abort/restart from the beginning with the complete sorted set rather than acquiring it out of order. The D1B3 command implementation must prevent hidden FK-trigger lock inversions; a detected deadlock retries the whole idempotent command, never skips validation. All commands share this increasing rank and UUID-within-rank rule, so their declared D1 lock edges cannot form a cross-command cycle; the separate Foundation prefix remains unchanged.

**Row lock strength:** protected aggregate mutation takes `FOR UPDATE` on its serialization anchor; related immutable catalog/ancestry rows may use `FOR KEY SHARE` after the anchor in the declared order. D1B2 chooses `FOR UPDATE` for capacity parents, Student, Employee, Family and the school/policy allocator anchors because these coordinates must serialize writers. Historical read-only queries do not take these locks, except Foundation-sensitive checked reads/materialized exports under its own authorization contract.

## Temporal and aggregate algorithms

For each temporal parent/logical key, lock its anchor, then query **all retained relevant intervals**, including future and closed rows, in a fresh statement. Reject strict overlap; allow adjacency (`old.end = new.start`). A backdated correction may be accepted only if it does not change an already accepted incompatible interval or require destructive rewrite; otherwise reject and request an explicit reviewed correction path. `supersedes_id`/predecessor must refer to an earlier row with the same logical parent and stable lineage, not itself; correction appends successor after protected one-way close. Parent/archive/end mutations recheck dependent intervals while holding the same anchor. Current/as-of queries use the half-open predicate in the matrix; current means the server evaluation instant/date, not `effective_until IS NULL` alone.

**Student status stream.** The Student row lock serializes server allocation of a positive immutable `sequence_number`, strictly increasing per Student; the initial event receives the first number. This is separate from recorded `created_at`. After factual supersession, authoritative business order is `(effective_on ASC,sequence_number ASC)`; same-date transitions are ordered by sequence, and status as of a date uses the maximum `(effective_on,sequence_number)` at or before that date. An ordinary append must not insert before an existing authoritative effective transition and its `previous_status` must equal the immediately prior authoritative `new_status`. A backdated factual correction instead appends a numbered `supersedes_id` successor, leaves prior rows intact, and revalidates the affected ordered chain and synchronized current projection under the same Student lock; reject a correction that would leave an inconsistent successor. Neither event insertion time nor a client-supplied number is a business tie-breaker.

**Enrollment and capacity.** Under Student lock, reject any overlapping PRIMARY interval, including future starts and backdated overlap, and validate predecessor Student/chronology. A future-dated accepted promotion may set the predecessor's exclusive end to the successor start now; the predecessor remains in today's roster until that date. Its COMPLETED/ENDED label records the committed bound, while effectiveness comes from the interval, not the label alone. Collect source and destination Class Offerings and Sections, lock all Class rows then all Section rows in UUID order. Re-read their capacities, state and ancestry, and count accepted PRIMARY intervals covering the candidate business date(s) under these locks. For an interval that spans more than one day, evaluate occupancy at candidate start and at every existing accepted placement start/end breakpoint inside the candidate interval; the count is constant between breakpoints. Check both class and section limits at every segment. ACTIVE, COMPLETED and ENDED placements count **only while their effective interval contains that date**; a future accepted ACTIVE row reserves future capacity but is absent from today's roster. Admissions pending/reserved/waitlist and special programs never count. The target Section's capacity never overrides its Class Offering's capacity. If a capacity is zero, an ordinary new placement cannot pass. Lowering a current capacity may leave existing accepted occupancy above it; it does not eject anyone, but later new placements must not increase occupancy at a segment already at/above the limit without explicit authorized override. A capacity update locks the same offering/section, appends typed `capacity_revisions` and changes the parent/version in one transaction; it rechecks future accepted commitments but preserves existing ones. An over-cap placement requires exactly one immutable `enrollment_capacity_overrides` row with both actual counts/limits, flags, reason, actor and receipt; within-limit placement has none. Override bypasses only the full limit, never ancestry, status, overlap, archive or authorization. A move closes old placement, creates successor/roll/override evidence and updates both aggregates atomically. No unprotected count-then-insert exists.

**Student ID and Admissions handoff.** Lock school/allocator, reserve `next_value`, advance it and insert permanent `school_student_id` in the same transaction; UNIQUE identifiers and Person key provide final defense. Rolled-back reservations can be reused, committed IDs cannot. No gapless promise and no `MAX()+1`. A duplicate handoff/receipt returns the prior Student, not a second ID. D1 validates final nonblank unique Admissions number and distinct serial; Admissions owns allocation/reservation.

**Roll policy and allocation.** School row serializes policy interval replacement and persistent numeric ownership across revisions. For `roll_allocator_states`, the two stable partial UNIQUE predicates distinguish NULL persistent pool from non-NULL Class Offering pool; a protected trigger verifies mode and school/context. Under school/policy/allocator then Student/offering locks, persistent mode checks the **school-wide persistent lineage across all PERSISTENT_STUDENT revisions** for another Student's numeric claim, and preserves one Student's numeric component for later placements. Academic mode checks collision within `(policy_revision_id,class_offering_id)` at the candidate effective interval; a different namespace may reuse the number. One effective allocation per enrollment is checked under Student lock. Manual correction closes old allocation and inserts a same-Student successor with reason; it cannot collide or rewrite prior display. A persistent correction establishes a new current number for later placements while earlier allocations remain historical; active placements for the same Student are reconciled in the same command or correction is rejected if that cannot be done atomically. The display is always derived from numeric value, policy and offering. No policy change rewrites old rows. Direct privileged DML is protected by a restricted trigger following the school/Student anchor or rejected.

**Family.** Relationship, membership, child access and primary display use half-open intervals. Same relationship identity (including NULL adult Person as a meaningful equivalence), one effective FAMILY membership per Family, Family+Student access, and primary Student display each reject overlap under Student/Family locks. The primary context's `(relationship_id,student_id)` composite FK is structural; locked validation requires context interval containment within selected relationship interval. An access interval may be accepted only if its entire interval is covered by the union of approved effective relationship intervals for that Family+Student; a relationship ending must close/reselect dependent primary context and any child access segment losing its final basis in one transaction, or reject. Emergency Contact is never a basis. A FAMILY-authorized child mutation obtains Foundation SHARED authorization lock, current FAMILY principal, Student then Family locks, and rechecks current membership, child access and complete grant before acting. Revocation uses the same anchors; if mutation wins, it commits before revoke, and if revoke wins, the mutation denies. A read statement begun before revoke commit may return its earlier `READ COMMITTED` snapshot; a new statement after commit must deny. No cached visibility is continuing authority.

**Employee and teaching.** Employee lock serializes employment periods, restricted snapshots and capability changes. Qualification/experience create and correction first lock the school row, then Employee: this serializes the global lineage-ID ownership lookup across different Employees, which separate Employee locks alone could not protect. Ending ACTIVE employment or teacher capability must atomically close affected open teaching assignment intervals at a valid bound or reject if a future assignment cannot be closed without an invalid interval. Retained rows remain historical. An assignment creator waits for the Employee lock then rechecks current eligibility; protected action also checks current eligibility and effective assignment. Section/Subject locks serialize one Class teacher per Section, one PRIMARY Subject teacher per Section+Subject, and duplicate CO_TEACHER/SUBSTITUTE keys. A CO_TEACHER is an explicit additional kind; a bounded SUBSTITUTE does not automatically end PRIMARY and may be recorded without requiring an overlapping PRIMARY, because presence of a primary is **not** an authorization predicate here. Actual actions still need the complete grant and current effective assignment. Assignment interval must fit active employment, capability and Section/year bounds; archived Subject cannot be selected anew. Existing assignments remain historical on catalog archive. Department/Designation and campus affiliation never grant permission. External experience may overlap different employers; only same-lineage snapshot overlap is prohibited.

**Ancestry.** Composite FKs prove Class/year school, Section/offering campus, Enrollment/Student roll, primary relationship/Student and FAMILY principal kind. For frozen Foundation campus/room keys that lack reviewed composites, restricted triggers and protected commands lock and compare `campuses.school_id=class_offerings.school_id`, `rooms.campus_id=section_offerings.campus_id`, Subject school against offering school, roll policy/offering school and Employee-campus school. All parent key changes are frozen or guarded. A row-local CHECK is never described as enforcing these joins.

## Cross-command lock and revalidation matrix

Legend: `A` Foundation SHARED authorization lock; `K` Foundation idempotency advisory key for registered mutation; `S` school/allocator/policy; `P` Foundation Person; `T` Student; `E` Employee; `F` Family; `C` Class Offering; `X` Section Offering; `Q` Subject; `H` child history. Campus/Year and Room are written by name to show their exact position. All commands begin `A→K` when idempotent, then Foundation principal/operation/request/step locks, then the displayed D1 classes in global order. Multiple rows in one class are UUID-sorted. A named parent is acquired only when involved, but any involved lower-ranked ancestry parent must be locked **before** C/X/Room/Q. `R` means fresh authorization, current-state, temporal/ancestry and expected-version revalidation **after waiting**. Failure `D/L` means whole idempotent command can retry after deadlock/lock timeout, not an automatic local statement retry.

| Command family | D1 parent locks in order | Post-wait revalidation and protected result | Failure/retry |
|---|---|---|---|
| Student create / direct intake | S allocator → P → T(new) → H | R handoff, Person uniqueness, IDs, initial status; receipt/evidence atomic | UNIQUE or bad handoff deny; D/L whole replay |
| Student restricted/special correction | T → H | R scope/version, same-Student snapshot, no overlap, approved correction | overlap deny; D/L whole replay |
| Student status transition / factual correction | T → H | R server sequence allocation, effective-date order, immediately prior authoritative status, supersession chain, then append and projection/version | invalid edge/order deny; D/L whole replay |
| Class offering creation | S → Academic Class → Campus → Year → C(new) → H | R class/year school, campus school, state and capacity; initial revision atomic | ancestry/capacity deny; D/L whole replay |
| Section creation / configuration | S when school config involved → Campus → Year → C → X(new or existing) → H | R composite campus ancestry, state/order/capacity/version; revision when capacity changes | ancestry/stale version deny; D/L whole replay |
| Enrollment create / capacity-override placement | T → Campus/Year → C(all) → X(all) → H | R PRIMARY interval, state, ancestry, all breakpoint counts, roll, override iff full | full/overlap deny; D/L whole replay |
| Promotion / repeat / section change / campus transfer | T → Campus/Year(source+target) → C(source+target) → X(source+target) → H | R predecessor, future/old intervals, both aggregate counts, roll lineage; atomic close+new | overlap/full deny; D/L whole replay |
| Enrollment end | T → Campus/Year(source) → C(source) → X(source) → H | R current effective placement, one-way close and reason | stale close deny; D/L whole replay |
| Capacity change | Campus/Year when involved → C → X if section target → H | R parent version/ancestry, accepted future occupancy, typed revision; no retroactive eject | stale version deny; D/L whole replay |
| Roll policy change | S → H | R policy interval, mode/start, successor; old allocations fixed | overlap deny; D/L whole replay |
| Roll assignment / correction | S policy+allocator → T → Campus/Year → C → X → H | R namespace collision, origin/Student, current enrollment; successor and derived display | collision deny; D/L whole replay |
| Family relationship add/end | T → F → H | R duplicate fact, current basis/access/context containment; close dependents or deny | invalid basis deny; D/L whole replay |
| FAMILY membership add/revoke | Foundation target Principal → F → H | R structural FAMILY kind, one interval, binding/grant/current state | invalid kind deny; D/L whole replay |
| Child access add/revoke | T → F → H | R approved effective relationship, membership and access interval; revoke serializes child writes | unrelated child deny; D/L whole replay |
| Primary family selection | T → F → H | R selected relationship composite/interval, one display row; no access mutation | mismatch deny; D/L whole replay |
| Emergency contact correction | T → H | R same Student/contact lineage, no access side effect | duplicate deny; D/L whole replay |
| Employee creation | P → E(new) → H | R Person/code uniqueness, initial employment period/projection | duplicate deny; D/L whole replay |
| Employment state change | E → Campus/Year/C → X → Q → H when teaching rows affected | R periods/projection and dependent assignment containment; collect all affected Sections/Subjects, close dependents atomically or deny | ineligible outcome deny; D/L whole replay |
| Employee identity correction | E → H | R restricted snapshot/version, same Employee lineage | overlap deny; D/L whole replay |
| Qualification / experience add/correction | S → E → H | R global lineage UUID ownership, stable per-record lineage, interval/date validity | invalid lineage deny; D/L whole replay |
| Job assignment | E → Department → Designation → H | R target active/same school, duplicate interval | duplicate deny; D/L whole replay |
| Campus affiliation | E → Campus → H | R campus school and duplicate interval; no later Section/Room lock, no grant | mismatch deny; D/L whole replay |
| Teacher capability change | E → Campus/Year/C → X → Q → H when teaching rows affected | R eligibility and dependent assignment containment; collect affected Sections/Subjects, close dependents atomically or deny | stale eligibility deny; D/L whole replay |
| Class teacher assignment | E → Campus/Year/C → X → H | R effective Employee/capability/Section and year bounds, one teacher/time | overlap deny; D/L whole replay |
| Subject teacher assignment | E → Campus/Year/C → X → Q → H | R Subject school/state, section/year bounds, kind-specific overlap and eligibility | overlap/ineligible deny; D/L whole replay |
| Section room assignment | Campus/Year/C → X → Room → H | R room campus, offering/section state, one room interval; no timetable inference | mismatch/overlap deny; D/L whole replay |

The matrix covers every requested command, including source/target moves and capacity override. Catalog create/archive, family archive and allocator initialization follow the same hierarchy: S then **all involved lower-ranked ancestry targets before the changed target**, with R after waiting. Section create/configuration and room assignment do not discover Campus or Year only after C/X; teacher assignment and eligibility end precollect those parents before Section/Subject; promotion/campus transfer collect both sides and sort every class of target. Capacity update and placement share C/X anchors; a relationship end and child mutation share T/F; employment/capability end and teaching create share E. These common anchors and monotonically increasing lock rank are the cross-command race and cycle proof. Exact operation codes, approval registration, RLS and Definer ownership are D1B3, not invented here.
