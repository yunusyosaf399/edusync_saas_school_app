### Candidate keys and backstops

- Definition `UNIQUE(school_id,code)`; revision `UNIQUE(curriculum_id,revision_no)`, predecessor must belong to same definition and precede revision. No silently reused identifiers.
- Applicability candidate `(revision_id,academic_year_id,academic_class_id,campus_id,effective_from,effective_until)` with nullable `campus_id` meaning *school-wide candidate coverage*, **not automatically higher/lower priority**. - Rule `(revision_id,subject_id)` unique for a given active content version in baseline; section offering must resolve an exact rule of its applicability revision; duplicate overlapping `(section_offering_id,subject_id)` denied irrespective of distinct underlying rules.
- Choice group `(revision_id,code)` unique, `0 <= min_choices <= max_choices <= count(distinct eligible group subjects)`, evaluated at validation and revalidated at selection. No two accepted overlapping choices for one Student/enrollment/offering and no group overflow. All FKs `RESTRICT`; composite FK only where upstream candidate key actually exists, otherwise protected locked ancestry checks. No parent/archive destructive cascades.
- Half-open business intervals `[effective_from,effective_until)`. For an academic-year bounded schedule: `academic_years.starts_on <= effective_from <= ends_on` and exclusive end no later than the day *after* `ends_on`; handle calendar limit and no implicit “current year” inference. Consumer accepted-at timestamps are separate from business effective dates.

## 2. A — Typed curriculum publication lifecycle and state machine

**Proposed revision statuses:** `DRAFT` → `VALIDATED` → `PUBLISHED` → `SUPERSEDED` or `RETIRED`. `DRAFT`/`VALIDATED` may go to `ABANDONED` before publication; no reactivation of terminal statuses. An approval request belongs to **Foundation workflow**; `PENDING_APPROVAL` is **not** a second mutable curriculum status. Definition `ACTIVE → ARCHIVED` is independent of revision terminal state.

`CREATE_DEFINITION` (recommended P0): new `ACTIVE` definition with unique school code; no revision published, no Student changes. `CREATE_REVISION` (P0): new DRAFT with server-issued strictly increasing revision, optional prior *published* revision, copy-on-draft only; predecessor/reference check. `DRAFT_EDIT` (P0): typed, field-allowlisted insert/update/delete of unpublished rules/groups/applicability; increment revision `row_version`, return to DRAFT and invalidate earlier validation evidence. No arbitrary JSON patch.

`VALIDATE_REVISION` (P0 candidate; no publication): freeze a validation verdict bound to exact revision version + content digest + intended year/class/campus/section coverage, approved Subject states, boundaries, group semantics, and affected existing selections. Missing/ambiguous applicability or unknown prerequisite semantics is **FAILED**, not a best-effort warning. Stale draft requires fresh validation.

`PUBLISH_REVISION` (**P2 REQUIRED_REVIEW recommendation**): submit exact validated revision version/digest and effective applicability plan to Foundation review; approved reviewer has independent, currently valid `curriculum.revision.publish` review authority (exact reviewer code TBD) with actor/Person separation; FINAL APPROVE leaves workflow `APPROVED`, a separate explicit apply transaction locks/revalidates before publication. No final-review auto-apply. Result: append/freeze published version and applicability, create/activate derived section offering records under one transaction; success receipt+safe audit+outbox atomic. No in-place edit of accepted rules or published history. Reviewer cannot approve own request via another role.

`REPLACE_PUBLISHED` (**P2 candidate**): publish a **new** validated revision with an explicit old→new context/effective cutover; predecessor remains published *historically*, its **future applicability** may be end-bounded with one-way closure and status tagged SUPERSEDED, never rewritten retroactively. Avoid status-ledger confusion: `SUPERSEDED` describes no longer current applicability, not loss of past published truth. At cutover, same context has exactly one applicable revision. Existing enrollment stays unchanged; existing Student selections remain retained with source revision. **Default proposal:** reject cutover if unresolved active selections would become invalid; require an explicit, approved selection transition plan as a separate command rather than silently dropping or migrating them. Old-term assessments and Learning retain old basis.

`RETIRE_REVISION` (**P2 candidate**): future end-bounds remaining applicability only if no orphaned enrollment/selection/downstream obligations; no hard delete, no retrospective expiry. `ARCHIVE_DEFINITION` (**P2 candidate**): one-way only after no required active/future applicability, but retained revisions/read references survive. `ABANDON_DRAFT` (P0 candidate): no published footprint; still audit. Whether retired revision can be re-published is **NO** under recommended baseline; new revision required.

### Transition table (all statuses and review levels are proposals)

| Action | Permitted start | Result | Suggested gate | Essential denial |
|---|---|---|---|---|
| CREATE_DEFINITION | absent | ACTIVE definition | P0 | duplicate school code |
| CREATE_REVISION | valid definition | DRAFT vN | P0 | archived definition / ambiguous predecessor |
| DRAFT_EDIT | DRAFT/VALIDATED | DRAFT v+1 | P0 | published, stale version, untyped patch |
| VALIDATE_REVISION | DRAFT/VALIDATED | VALIDATED digest | P0 | wrong year, empty/invalid group, overlap |
| PUBLISH_REVISION | VALIDATED | PUBLISHED dated mapping | P2 proposed | missing approval, stale digest, competing publication |
| REPLACE_PUBLISHED | VALIDATED + published predecessor | new PUBLISHED; prior SUPERSEDED for affected future context | P2 proposed | historic back-edit / orphan selections |
| RETIRE_REVISION | PUBLISHED with controlled future end | RETIRED (history retained) | P2 proposed | current obligations, retrospective disappearance |
| ABANDON_DRAFT | DRAFT/VALIDATED | ABANDONED | P0 | referenced published snapshot |
| ARCHIVE_DEFINITION | ACTIVE without future obligations | ARCHIVED | P2 proposed | effective/future published mappings |

**Effectivity recommendation:** publication can be approved in advance but **not** effective before its approved `effective_from`. Default first version starts on explicit year start; mid-year replacement must carry a P2 reviewed cutover date, conflict-free old end/new start, affected-section roster/selection impact, and downstream acknowledgement before apply. No automatic revision switch from a label change or a later publication date. **Owner must approve** timing, retroactive correction exception, and disposition of current choice registrations (CUR-01/05/06).

## 3. B — Exact proposed applicability resolution (no presumed override)

**Input**: server-verified `school_id`, **explicit** D1 `class_offering_id` and optional `section_offering_id`, `business_date`, optionally subject and Student/enrollment. Derive `year_id,class_id,campus_id` from class offering, and section membership from D1. Reject forged or contradictory caller-provided year/class/campus.

**Recommended baseline = SINGLE UNAMBIGUOUS MATCH, NO INHERITANCE PRIORITY.** A school-wide applicability row (NULL campus) covers all campus offerings of that class/year. An exact campus row covers that campus only. If both cover the same offering/date, **deny AMBIGUOUS_APPLICABILITY**; do not quietly choose campus-specific, newest or highest revision. For an applicable section, offer only subjects with an eligible same-revision section subject offering effective that date; availability cannot broaden the revision's Subject set.

| School-wide row | Matching campus row | Date/year/class/section match | Outcome |
|---|---|---|---|
| none | none | — | NOT_CONFIGURED; no acceptance/write |
| one | none | yes | resolve school-wide revision (candidate) |
| none | one | yes | resolve campus revision (candidate) |
| one | one | yes | **AMBIGUOUS**; deny (no implicit precedence) |
| two overlapping any scope | any | yes | **AMBIGUOUS**; deny, publication blocked |
| one | none | wrong `academic_year_id` or class | WRONG_CONTEXT; deny |
| one | none | date before start/at-or-after exclusive end | NOT_EFFECTIVE; deny |
| one | none | valid class but `section_offering` from another campus/class offering | SECTION_MISMATCH; deny |
| one | none | no section-level subject offering for requested Subject | SUBJECT_NOT_OFFERED; deny |
| prior and successor | — | adjacent half-open endpoints | resolve prior before boundary, successor at/after; never both |

**Alternatives requiring owner signoff:** explicit campus override with shadowed school-wide interval, scope-based ordered precedence, class-offering-only applicability (one row for every campus offering), or section-level curriculum variations. Baseline avoids arbitrary precedence; section-specific *availability* is supported, but section-specific *alternate revision selection* is **not** implicitly supported by the seven-entity schema. A genuine section-specific revision would require a typed section target or separate applicability association and a new non-overlap rule (CUR-01). **No year inference by calendar alone**: Foundation permits overlapping academic years, so the offering's year FK is decisive.

**Timing / history:** selection at time `t` requires intersection of: D1 accepted PRIMARY enrollment interval, matching D1 offering academic-year dates, active applicability, exact section-subject offering interval, and any accepted Student elective selection interval. Invalid/archived *current* Subject or closed offering disallows **new** assignments subject to frozen D1 rules; retained facts remain eligible for separately authorized historical reconstruction, not contemporary creation.

## 4. C — Subject and elective semantics

| Rule category | Recommended baseline behavior | Student selection materialization |
|---|---|---|
| COMPULSORY | Required for every accepted Student enrollment in the covered Section; no family/student opt-out without reviewed policy. | **Derived obligation from published rule + effective D1 enrollment**; **no fake elective selection row** |
| OPTIONAL | Subject may be chosen, not required individually; if a configured group has a positive min, its *group* obligation applies. | Explicit accepted `student_subject_selections` if selected |
| ELECTIVE | Group-governed alternative selection, e.g. choose one from Biology/Computer Science; enforce all limits at accepted group/time, not only client picker. | Explicit accepted selection lineage for each chosen subject |

Existing spec also lists `Practical`, `Extra-curricular` and `Custom` subject types. They are **not proven mutually exclusive** with obligation category; practical is often an assessment mode, not another choice obligation. Do **not** collapse the approved spec into only three Subject catalog types or implement Exams components here. Whether another applicability dimension is needed is CUR-02.

**Groups:** recommended one rule→at most one group in each revision; unique group code per revision; bounded `0<=min<=max<=distinct available group subjects`; count DISTINCT accepted subjects, not duplicate history rows. Selection accepted only when the *resulting accepted set* respects max. For min, recommend **DRAFT choice-cart** may be incomplete but **FINALIZE_SELECTION** requires min and all compulsory obligations; if no draft state is approved, atomic batch initial selection must meet min in one commit. Group constraints must be rechecked for all affected time segments, including scheduled future choices; a future ending cannot strand a min-choice violation without an explicitly approved exception.

**Prerequisites:** baseline **unsupported/deny when a revision declares prerequisites that cannot be enforced**. Do not parse arbitrary text, rely on marks, or invent Exam pass grades. If prerequisite enforcement is approved, add the potential eighth typed graph relation with same-revision Subject edges, cycle rejection and an Exams completion/proficiency dependency owned by Exams. Pure “requires concurrently selected Subject” can be implemented as a separate explicitly approved co-requisite type, not a hidden universal prerequisite.

**Archived Subject:** D1 archive stops **new use**, not history. Old revision rules/selections/Exams snapshots keep FKs. Publishing a new revision with an archived new-use Subject is rejected; whether grandfathered students retain previously selected offerings without a new enrollment action is an explicit CUR-06 exception, not assumed.

**Student transfer:** Section, Campus, Class or Year change is D1 Enrollment MOVE/END+PLACE, not a rewrite of the old `enrollment_id`. New Section requires its own revision and offerings; old selection lineage remains in old enrollment. **No automatic reattachment**; if business requires equivalence, issue a separately authorized cross-enrollment choice mapping with retained evidence, never repoint historical rows.

## 5. D — Fixed typed Student selection commands (candidate, not installed RPCs)

**Request envelope required for every externally retriable command:** operation-specific command code; client `idempotency_key`; server-derived acting Principal; typed target `student_id`; `expected_student_row_version`; exact `enrollment_id` and **expected immutable enrollment snapshot** (`student_id, section_offering_id, effective_from, effective_until?, placement_state, predecessor_id?`); expected `section_offering_id` and offering `row_version` where meaningful; expected `curriculum_revision_id, applicability_id, section_subject_offering_id, curriculum_digest/version`; intended effective date; exact source selection ID/interval/state for amendments; reason and approved exception ID only when applicable. **Do not invent `enrollments.row_version`**; if needing stronger compare, use a locked snapshot signature of existing D1 fields. Server derives Subject/category/group/academic year/campus, ignores forged claims. Hash the canonical typed payload including nulls/arrays and reason; changed intent with same idempotency key conflicts.

| Fixed candidate command | Proposed typed arguments beyond common envelope | Mutation / guard | Suggested route |
|---|---|---|---|
| `curriculum.selection.initial` | explicit sorted eligible offering IDs, expected group-set digest | atomic accepted set for current D1 enrollment; reject duplicate, missing required group minimum at finalization, max overflow | **P1** school policy DIRECT or APPROVAL (owner decision); no self-service grant baseline |
| `curriculum.selection.change` | source selection IDs, replacement offering IDs, boundary, exact before-state | close old accepted choices at exclusive boundary; append new choices preserving all old history; no cross-enrollment mutation | **P1** current/future candidate, P2 if retroactive (owner decision) |

| `curriculum.selection.exception` | typed exception kind, affected group/rule, bounded interval, reason, reviewed request ID | **P2 recommended**, only for explicitly frozen exception taxonomy; no broad “ignore all eligibility” flag | **P2** candidate; otherwise NOT IMPLEMENTED |

**Actor eligibility proposal:** ordinary Student/FAMILY/teacher have **READ-only baseline** until owner approves and registers a specific submit/change permission, route and exact scope. Academic staff need a live *complete* scoped permission for this action, **not** role label. A teacher's D1 teaching assignment is only contextual eligibility and never standalone choice administration. Student self reads require current INDIVIDUAL Principal `D1_STUDENT_SELF`; FAMILY reads require current FAMILY Principal + membership + child-access relationship basis + live family-safe grant `D1_FAMILY_CHILD`. No old assignment or parent contact becomes current authority. Current checked reads and separate history reads use distinct permission codes.

**P1/P2 operation behavior:** no inferred fallback DIRECT, no generic Administrator reviewer, configured exact reviewer role/scope and requester/reviewer Person separation. SUBMIT, REVIEW, and explicit APPLY are distinct transactions. Final APPROVE does **not** apply. At APPLY, lock same aggregate and re-evaluate requester, reviewer, policy, enrollment, revision, group, source and target states. Deterministic stale/ineligible APPROVED request → `INVALIDATED` + one **REJECTED** apply receipt and safe audit, no mutation, no application record or success event; unexpected SQL/deadlock/infrastructure failure rolls transaction back for retry. Replay of a terminal success requires current authority and retained result identity; receipt never grants permission.

**Effective dates:** baseline accept current or explicitly permitted future within the accepted Enrollment + published offering interval; retroactivity **P2 only** if approved and no incompatible downstream published Exam/learning snapshot. `selected_until` must exceed `selected_from`. Future choice starts must not be treated as effective “now” merely because end is NULL. Scheduled choice boundary requires D1 Enrollment to cover entire intended interval; if it does not, reject or require bounded choice. **The exact enrollment end/change integration is CUR-06**.

**Checked read candidates (no base-table-shaped JSON):** `app.curriculum_read_available_subjects(section_offering_id)` returns IDs+safe labels, effective revision and group min/max subject to exact current scope; `app.curriculum_read_my_selections()` derives current Student; `app.curriculum_read_family_child_selections(student_id)` validates current child access; staff scoped Section/Student read separately; `app.curriculum_read_selection_history(student_id,interval)` requires separate current *history* permission. No broad Student cohort membership to FAMILY or unrelated teacher; no arbitrary resolver text, role name, hidden private reasons or cross-campus inference.

## 6. E — Read-only downstream contract with immutable dated snapshots

**Two distinct clocks are essential:** `valid_at` = the academic event's business date; `observed_at` / `knowledge_cutoff` = when a consumer accepted the immutable eligibility decision. An as-of re-query alone is **insufficient** if later approved factual corrections change the accepted historical interval. A downstream consumer must persist immutable provenance at its own creation/publication boundary. No dynamic lookup of “latest revision” may reinterpret a previously conducted exam.

**Server-internal candidate response shape** (conceptual typed record; not deployed signature):

`CurriculumEligibilitySnapshotV1 { decision_version, allowed, safe_denial_code, school_id, academic_year_id, academic_class_id, campus_id, class_offering_id, section_offering_id, student_id?, enrollment_id?, curriculum_definition_id, revision_id, revision_no, revision_content_digest, applicability_id, applicability_effective_from, applicability_effective_until, section_subject_offering_id, subject_rule_id, subject_id, rule_category, choice_group_id?, accepted_selection_id?, accepted_selection_state?, selection_effective_from?, selection_effective_until?, valid_at, observed_at, consumer_snapshot_id?, authority_check_id? }`

`consumer_snapshot_id` is the **consumer-owned immutable record reference** to be generated when that consumer freezes the response, not a new asserted DB-04 entity. Reject old/incompatible `decision_version`. Field access is purpose-minimized. If no Student identity is needed (timetable offerings), Student/Enrollment/selection fields are NULL and no Student row list is returned. If a Student-specific consumer requires eligibility, selected OPTIONAL/ELECTIVE must have an accepted selection effective at `valid_at`; COMPULSORY derives from the rule/enrollment. No positive response authorizes writing marks, publishing Learning work or editing timetable by itself.

**Fixed private endpoints, not arbitrary client-supplied `purpose`:**
- `private.curriculum_exams_student_subject_eligibility(student_id,enrollment_id,subject_offering_id,valid_at)`: internal restricted EXECUTE for Exams owner; returns exact student+subject snapshot, never names/marks. Exams enforces its own permission and determines the **assessment conducted/published freeze point** with owner signoff.
- `private.curriculum_learning_assignment_eligibility(section_offering_id,subject_offering_id,valid_at)`: internal section/subject/eligibility descriptor; recipient-target evaluation via separate checked per-Student access (no unrestricted student roster). Learning decides assignment, submission deadlines and teacher rights.
- `private.curriculum_timetable_section_subject_eligibility(section_offering_id,subject_offering_id,valid_at)`: no Student identity; confirms subject is offered and effective, optional group rules as constraints; Timetable still checks staff/room/period collisions.
Names are **candidate interface labels**; actual `app_private` placement and executor grants require downstream owner/security signoff. No public arbitrary-target callable bypass or SQL dynamic resolver dispatch.

**Consumer persistence requirements:** store immutable decision schema version + `valid_at` + `observed_at` + all relevant IDs and exact revision digest + allowed decision and selection basis in consumer-owned history; optionally hash canonical typed evidence for integrity but a digest **cannot replace retained facts or permission checks**. Exams must retain assessment date/time and original snapshot even if revision N+1 published next year or a P2 election correction is later accepted. Exams result revision/locks remain Exams-owned. Learning records content/recipient decision at assignment publish and again at Student submission where needed. Timetable snapshots section offerings and interval, not mutable live category labels. No DB-04 direct write to these consumers; published legacy facts are never auto-rebased.

**Boundary decisions:** historical Exam eligibility re-evaluation for late-arriving corrections, existing assignment audiences after elective withdrawal, and timetable effectivity after group change need Exams/Learning/Timetable signoff **CUR-07**. Pending that, new incompatible publication/retroactive correction must fail closed (not silently reinterpret already-published records). This is a *design rule*, not a claim the other domains already implement snapshot storage.

## 7. F — Lock ordering and genuine two-session acceptance

**Candidate command lock prefix (aligned to D1, no new engine):**
1. Foundation `(71001,1) SHARED` for domain change/checked principal authority; Foundation `71002` idempotency namespace/key; sorted Principal(s) and workflow/request rows according to Foundation contract.
2. **School/config row first** for Curriculum publication/revision/selection serialization, including Subject-archive interaction when D1 takes this same School ancestor. This is a deliberate conservative school-wide anchor to serialize publish/selection without locking every Student.
3. When Student-specific, lock Student UUID next (same D1 anchor used by Enrollment MOVE). Then known affected D1 ancestry in frozen order: Academic Class → Campus → Academic Year → Class Offering → Section Offering → Room if needed → Subject (sorted UUIDs within relation).
4. DB-04 owned parents in fixed order `definition → revision → applicability → choice_group → subject_rule → section_subject_offering → student_selection_history`. Exact child FK lock ordering must be reviewed; **all immutable parent IDs must be discovered before row locks**, including source/destination and future effective rows. Defensive trigger must use same order or fail closed, not acquire an earlier D1 parent after later child.
5. After every wait use a fresh statement under `READ COMMITTED` to re-check Principal/grants, policy, business date, Student enrollment effective state, D1 Subject archived/new-use state, published revision content/version, group occupancy across all relevant effective intervals, source head and expected snapshots. Unexpected deadlock retries **whole** canonical-idempotent command only.
