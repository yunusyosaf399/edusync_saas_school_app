### Tri-state field representation requirements

The public transport must be **fixed-purpose and typed**, not arbitrary table/column JSON. A SQL/internal canonical representation may carry a fixed six-element array of action-and-value pairs in the frozen field order, with each action exactly `UNCHANGED`, `SET` or `CLEAR`; validate SET value type, allowed codes, text limits, dates and photo provenance server-side. Preserve explicit `NULL` separately from unchanged in hashes and immutable approval snapshots. Deny an empty or normalized no-op update. A direct change **must** include a validated private reason, not just an implicit/default reason. Existing positional RPCs accepting all fields without presence flags must not be treated as implementing this contract.

All six present physical Student columns are nullable, but that does not replace typed validation or permission limits. Normalization, max lengths/allowed code catalogues, date bounds and file ownership must follow authoritative installed constraints; any remaining product-level value-boundary disagreement must be separately documented before accepting final SQL. It is forbidden to invent a new generic profile mutator.

## Version/history transaction and security boundary

The accepted business outcome is one transaction: validated, authorized typed intent → verified old Student PROFILE snapshot → versioned core mutation → restricted immutable before/after value history → typed receipt → minimized audit and selected outbox. If any step fails, all effects roll back. No history write occurs on SUBMIT, REJECTED, INVALIDATED, no-op or unsuccessful DIRECT; a review is not a profile change. Historical replay reads original retained evidence and requires current authority rather than re-mutating or requiring the original Student version still be current.

The additional stored history is a **separate additive package** described in [ADR-005](../decisions/ADR-005-student-profile-restricted-history.md). D1's frozen 34 base relations, 97 permissions, 322 alternatives and 36 operations are **not** retroactively reinterpreted. Any additional relation/permission or change to Migration 10 requires its own approved migration/design review and exact-head acceptance; no relation should be silently added to the frozen 34 count. No FAMILY/Student default history disclosure is approved.
