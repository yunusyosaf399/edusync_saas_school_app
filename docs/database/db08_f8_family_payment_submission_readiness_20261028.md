# DB08 F8 — family payment evidence submission readiness

**Status: inactive F8 candidate.** F7 provides private storage. F8 adds a server-only bank-slip validator and a private `schoolos_file_login` command that creates one pending submission, file metadata, command receipt, audit event and outbox event atomically. No payment, review, official receipt or admission clearance is issued. This is a draft, not a deployed upload route.

## Purpose and prerequisites

An authenticated FAMILY principal may submit a measured bank transaction slip (PDF, JPEG or PNG) for a currently linked Student after paying outside the app. The stored submission remains pending for a different, specifically authorized school administrator to investigate. There is no in-app payment or payment gateway in this flow. Staff-assisted intake requires a separately reviewed permission and actor contract; it must not impersonate a family account. The initial parent command accepts BANK_TRANSFER only; F7's WALLET_TRANSFER storage capacity does not activate a wallet intake path.

F8 depends on Foundation identity, grants, receipt/audit/outbox contracts; D1 Family membership, child-access and primary enrollment; and F7's private payment tables. The existing DB03 admissions document worker remains restricted to `ADMISSION_DOCUMENT`. The candidate payment service uses the shared verified-claims, measured PDF/JPEG/PNG validator, private object adapter and durable entitlement verifier with `storage.payment_evidence.upload` and the Finance module. The private SQL command rechecks the current FAMILY principal, `payment.evidence.submit` and `file.upload` family-safe permissions and D1 child relationship after locking, then stores the measured file as AVAILABLE and creates a pending bank submission. No permission, role, operation, entitlement, storage location, HTTP route or provider credential is seeded by this draft.

## Candidate command boundary

1. Derive the principal solely from verified Auth context. Require active FAMILY kind, an enabled family-safe `payment.evidence.submit` operation and complete current scope/grant. A direct service-role call, an expired JWT and a stale role or scope deny. The authorization code and scope alternatives need deployment-owned registration before the command is exposed.
2. Resolve active Family membership and active Family→Student access at the School-local current date. Require an active Student and a primary enrollment covering the declared payment date at the selected School/Campus. A historical relationship alone does not authorize a new submission. Staff, another family and an emergency contact cannot borrow this path.
3. Recheck the relationship and permission **after waiting on the same D1 Student and Family mutation fences** used by relationship and access revocation. Follow the Foundation School shared authorization lock and canonical D1 lock order; a revocation that commits first must deny the waiting submission. Obtain the command-key lock before its source insertion and keep all checks and writes in one transaction.
4. Require a PAYMENT_EVIDENCE AVAILABLE private file belonging to this principal and Campus, with the verified content hash bound to a trusted payment upload intent for this Student and this request. File UUID, content hash, entitlement revision and caller-provided school/capability flags are not authority by themselves. The file worker and submission command must serialize intent consumption so one file cannot support two submissions.
5. Accept BANK_TRANSFER, one positive amount in the School's configured two-decimal currency, a finite payment date, normalized bank and transaction reference. Preserve the originally submitted values and proof. Flag possible duplicate reference/amount/date or identical hash for authorized school administrator investigation; do not silently mark a pending submission official. A correction is a new submission linked to the prior REQUEST_CORRECTION review, with fresh evidence and current authorization.
6. Return a stable pending submission ID for an exact retry under the same principal/key/payload. A changed payload under the key fails. Before returning historical success, verify its submission and exact retained command receipt, audit and outbox evidence; recheck present principal authority. A successful command never writes `finance_payment_reviews` or `finance_official_payments`.

## Data, privacy and history

F7 `finance_payment_submissions` is the immutable source. The candidate service stores private bytes using a deterministic, non-overwritable key for exact retry; a changed-byte retry is denied before database write. It then invokes the private command in one database transaction while holding the durable entitlement activation lock. Failed SQL after an object write may leave private orphan bytes; provider reconciliation is an activation gate. No `anon`, `authenticated` or `service_role` direct DML/SELECT grant on the payment sources. The audit/outbox event contains identifiers and status, not bank proof bytes, signed URLs or secret entitlement material. Generated receipt PDFs remain on demand after a later official payment command.

## Acceptance gates before operational claim

- Install failure rolls back all new objects; existing F1–F7 and frozen Foundation checks remain green in a disposable project.
- Real family Auth succeeds with a current membership, child access, enrollment, permission and finalized entitled private file. Another family, staff role, service role, expired JWT, absent entitlement, wrong purpose/Campus/Student/uploader, changed hash, stale intent and unverified file fail without a submission.
- Genuine two-backend revocation races cover Family membership, child access, permission/scope and School entitlement activation. Check both commit orders and absence of partial receipts, files or submission rows.
- Exact replay returns the same ID and one audit/outbox pair; a changed-key payload or reused file fails. Concurrent same-key requests produce one submission. Suspected duplicate transactions remain pending and visible only to authorized Finance review.
- F7 approval/receipt storage is not invoked by F8. Independent school administrator review with a specific permission, official receipt serial allocation, payment allocation and Finance clearance have their own later acceptance gates. Wallet and cash paths are not enabled by this parent command.

**Activation gaps:** deployment-owned family-safe permissions and scope configuration, real verified Auth and private worker credentials, provider retention/IAM and orphan reconciliation, configured finite entitlement freshness, staff-assisted intake authorization, two-backend revocation races, and populated upgrade/restore acceptance. The disposable candidate must pass its exact-head CI before even its draft database behavior is considered validated. No hosted School has been changed.
