# DB-02 T04 — two-backend School policy races (disposable local)

`tools/supabase/domain_db02_policy_race_ci.py` runs after the existing D1 two-session trials on the disposable local PostgreSQL stack. Before each of four cases, the harness resets the local database, reapplies the frozen migrations and unchanged D1 draft chain, and prepares five local Auth fixtures. Its committed fixture creates two distinct verified authenticated Principals against the product's one singleton School, grants each School ALL authority, and creates one global DIRECT P1. INIT starts without a policy; REPLACE seeds an older revision and allocator. The operation and grants are enabled only in this disposable fixture. Each case uses a fresh database, so prior committed policy history and evidence remain intact until the database is discarded.

For each action, two independent `psql` backends use distinct actors and idempotency keys against the **same** School. A holder completes its protected command and sleeps while retaining its transaction locks. The observer requires the second backend to wait on a PostgreSQL tuple/transaction lock with `pg_blocking_pids` identifying that holder, which also holds a granted `school_profiles` relation lock. The harness tests both holder COMMIT (second command denied after the wait) and holder ROLLBACK (second command succeeds after the wait): four observed races total.

After every race, it checks exact winner revision and predecessor, no loser revision/receipt, one winner allocator/receipt/audit/event, and source closure only for a committed REPLACE. No synthetic rows or operation enablement are sent to hosted Supabase. The disposable stack is stopped by the existing local CI workflow. This establishes T04 School serialization; Enrollment placement, grant/P1 revocation, and allocator ownership races have their own later gates.
