## 1. Current frozen facts and concrete blocked technical observations

1. `student.roll.correct` is a registered **disabled** P1 operation and distinct `student.roll.approve` permission; the D1 ACS model has ALL/CAMPUS/CLASS/SECTION non-FAMILY-safe scopes. A P1 request selects either DIRECT or independent APPROVAL, not both. Existing protected Enrollment PLACE, MOVE and END do not implement correction.
2. `roll_allocations` retains UUID, Student/Enrollment/policy, BIGINT numeric, DATE half-open effective interval, `supersedes_id`, **different** `origin_allocation_id`, correction reason and one-way end markers; no Roll row-version/receipt FK. `students.row_version` is an existing snapshot token. The preexisting Foundation `command_receipts` identity is (Principal, operation, idempotency key), and approved applies have a unique request/application binding.
3. **Persistent safety discrepancy (source-level, no claimed exploit):** final `effect35_15_enrollment_place_allocator_server_version.sql.draft::d1_enrollment_place_allocate_roll` filters out superseded rows in its *different-Student persistent candidate* loop. Final `effect30_32_crossrow_campus_local_rename.sql.draft::d1_guard_crossrow` checks **all retained** historic different-Student School-wide persistent allocations. A candidate can therefore be selected only to be rejected by its guard. Corrected-away historic numbers are **not presently proven reusable**, and #31 describes School-wide persistent ownership.
4. **Concurrency dependency:** final `effect30_33_qualification_experience_lineage_guard.sql.draft::d1_guard_effective_history` locks School→source policy→source allocator→Student on Roll INSERT/UPDATE. MOVE prelocks its destination policy/allocator but may not prelock a *different historical source*; END currently locks Student before source Roll update trigger acquires the source policy/allocator. Integration owner must unify and prove full lock order; DB-01 does not change shared MOVE, END, allocator or triggers.
5. **Temporal dependency:** `d1_guard_crossrow` requires a Roll successor's `effective_from` fall within its **stored** source policy revision interval. If an existing Enrollment's old policy has ended, blindly appending a correction retaining the old policy at today's date violates that guard. There is no owner-frozen policy-crossing correction rule.
6. Existing [#65](../../supabase/tests/domain/65_remaining_student_commands_fail_closed.sql) retains disabled-operation expectations; accepted P0 [#61](../../supabase/tests/domain/61_student_enrollment_place_p0_initial_roll.sql), MOVE [#63](../../supabase/tests/domain/63_student_enrollment_move_p1_direct_section_history.sql), and END [#62](../../supabase/tests/domain/62_student_enrollment_end_p1_direct_history.sql) are **other operations'** acceptance, not permission to claim correction runtime acceptance. ## 4. Correction-date product recommendation and testability tradeoff

**Problem:** D1 `roll_allocations.effective_from/effective_until` and policy revision boundaries are DATE, half-open `[from,until)`. In a correction R0→R1 effective day D, R0 must satisfy `R0.effective_from < D`; a second correction of R1 on D would close `[D,D)`, a zero-length interval, so the first-release proposed model **cannot** allow repeat same-day corrections. Review approval and actual APPLY may happen on different days; DATE is a business-effective boundary, not the time of approval. `CURRENT_DATE` in PostgreSQL follows the session's effective timezone; separate School timezones complicate consistent policy/Enrollment/roll boundaries.

### Four explicit owner options

| Choice | First-release behavior | Strength/risk; who approves |
|---|---|---|
| **T-A: server-fixed SQL DATE** (closest to DB-02 RP-02 A) | Trusted SQL executor uses one documented DB timezone (recommend UTC if selecting this option) and `CURRENT_DATE` consistently for policy, placement and correction boundaries. No client-provided date. At most one correction per source-positive-day; source policy must cover that date. | Least intrusive to present final SQL; **UTC midnight is not School midnight** in non-UTC Schools. DB-01 and DB-02 owners must freeze exact timezone and Session TZ invariants, test UTC± Schools, not merely say CURRENT_DATE. |
| **T-B: verified School-local SQL DATE** (**DB-01 recommended product UX**, pending integration review) | Compute authoritative `(statement_timestamp() AT TIME ZONE school_profiles.timezone)::date` from verified School once per protected apply, propagate same date through the complete current/as-of policy, Enrollment and Roll validation; no caller timezone. Still no same-day second correction. | Matches School calendar/business day, but **requires D1/DB-02 integration proof/changes** where current `CURRENT_DATE` is used. Requires reviewed time-zone database values, clock-boundary isolation and consistent NOW versus TX timestamp selection. Do not implement in DB-01 alone. |
| **T-C: multiple corrections per day** | Change physical model to timestamps or append independent intra-day correction sequence/versions and revise row guards, history reports and replay semantics. | Major new migration/product/security/history/retention choice; neither existing schema nor frozen interval contract implements it. Must not be smuggled through a current-date helper. |
| **T-D: backdated/future-scheduled correction** | Use requested date with explicit changed past/future effectiveness and reconciliation of all accepted downstream Enrollment/roll/report history. | Large retroactivity/approval/time-of-truth contract and concurrency risk. Not recommended first release. |

**Recommendation:** approve RC-03's **no same-day second correction**, no back/future updates, source policy must cover apply date. Product owner should **prefer T-B only if DB-02 and integration explicitly approve synchronized School-local policy/placement/correction dates**; otherwise **use T-A (UTC-pinned)** for first release and clearly document its user-visible boundary. Do **not** build DB-01-only School-local correction with DB-02 UTC current-policy selection, because this can cause a policy revision/roll guard mismatch at a School midnight. If no joint date choice exists, **RC-03 remains blocked and executable SQL must stop**.

### Test design choices (distinct from product DATE choice)

- **Q-A: multi-day real-clock tests (recommended trustworthy baseline):** on disposable local/CI environment, create a genuine P0 Enrollment dated D−20 and perform one authenticated R0→R1 correction today. Across three real server business days D1, D2, D3, run protected R0→R1→R2→R3; after D3 do a genuine MOVE on D4, then replay C1 key. Persist only a **dedicated disposable** test database for the series and hard reset/delete it at completion; a standalone test suite's rollback transaction cannot persist across days. This is slow and needs a specialized integration schedule, **not an automation or a claim that it has been run**.
- **Q-B: deterministic trusted test-clock seam** (faster but **requires separate signed security/integration approval**): only in an isolated disposable local test service, pass a server-generated fixture business-date from an integration-owned, non-client-exposed clock into all protected source-policy/Enrollment/roll functions. Must be physically absent from deployed production function signatures/rights (or cryptographically/test-harness isolated to a disposable instance with explicit never-deploy guard). It must not be caller-supplied through public RPC, JWT metadata, SQL timezone/session GUC or request JSON. Validate both boundary crossings, time-zone coverage, rollback, and result-hash stability. No existing approved clock seam is assumed.
- **Q-C: synthetic owner edits of R1.effective_from or successful Roll inserts** are **not accepted** as protected multi-day command acceptance. A structural-only trigger test may use owner fixtures but must be labeled such; never inflate DIRECT/APPROVAL pass counts.

**Safe immediate single-day suite:** genuine authenticated P0 place on CURRENT_DATE−20, one approved-mode DIRECT/APPROVAL correction today; inspect source close/successor/receipt, deny an attempted second same-day correction, test same-key replay on the same day, real MOVE/END tests only in a logically valid timeline, and concurrency on independent Students/commands. Next-day replay or three-correction chain requires Q-A or approved Q-B. This is a **future acceptance plan**, not an executed fixture.

**Illustrative school example:** The School day turns to October 20 at local midnight but a fixed UTC database could still be on October 19. A registrar approving a correction at 12:30 a.m. School-local time should not unknowingly create a Roll whose effective date disagrees with the currently selected School policy. Conversely, a second correction on that same School day must be denied under option T-B with the present DATE interval model.

## 5. Frozen API, receipt and security choices to attach to approval

The new DB-01 API gate provides *proposed* precise signatures. Required owner sign-off is to retain them as a coherent package or specify exact revisions:
- **DIRECT & SUBMIT:** `(student_id uuid,expected_student_version bigint,source_enrollment_id uuid,expected_source_section_id uuid,expected_enrollment_effective_from date,source_roll_allocation_id uuid,expected_source_roll_effective_from date,expected_source_policy_revision_id uuid,expected_old_numeric_value bigint,requested_numeric_value bigint,reason text,idempotency_key text)`; 12 arguments, one immutable `roll_allocations` source ID.
- **REVIEW:** `(request_id uuid,decision text,expected_request_version bigint,reason text,idempotency_key text)`; `APPROVE|REJECT`; no Roll change.
- **APPLY:** `(request_id uuid,expected_request_version bigint,idempotency_key text)`; explicit later protected effect under fresh auth and source locks.
- **Checked READ:** `(request_id uuid)` returns bounded participant fields only, no raw JSON or private reason until separately approved.
- **Canonical caller intent:** fixed 11 typed fields (the idempotency key is separate in envelope), stable across midnight; `request.review` fixed four fields, `request.apply` two. Foundation SHARED auth lock `(71001,1)` and keyed `(71002,...)` protocol retained.
- **Successful result:** `result_kind=D1_STUDENT_ROLL_CORRECT`, `result_ref=<new corrected Roll UUID>`, strict 12-key original source→successor result, APPLY extends to 14 with request state/version. Forensic helper proves actual stored predecessor/successor/E1/policy/old/new/source date/effect date, and approved APPLY binds requested value and reason; no successful receipt may claim a mismatched corrected Roll, and no duplicate receipt may claim a single corrected result.
- **Outbox/audit:** exactly one `enrollment.roll_corrected` success event and bounded non-sensitive audit for successful DIRECT/APPLY; never broad raw old/new numeric/reason or request JSON. Deterministic approved stale APPLY returns a rejected receipt, `APPROVED→INVALIDATED` transition and no successful correction event; unexpected SQL exception rolls back.
- **Replay:** after later CORRECT, MOVE or END, original success remains verifiable via original R0/R1 and immutable receipt (successor need not still be open); return only if *current approved* participant/School disclosure permits. Same key/changed intent conflicts. No implicit reopening, update or new event.

**No decision automatically enables operation, changes grant, makes a migration executable, or approves a new relation.**
