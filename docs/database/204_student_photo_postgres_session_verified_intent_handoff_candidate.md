# Student photo — DB-session-verified Principal to signed opaque intent handoff (isolated rehearsal)

Date: 2026-10-18. **Candidate only: local security contract rehearsal, no actual PostgreSQL/Python cross-process integration or production file service.** Baseline: frozen `main` `10b5dbf3f7061daa6f1de21cc7515783c1279ac4` ([PR #92 freeze](203_student_photo_real_actor_scope_ci_merge_freeze.md)). This is the next *non-activation* boundary: prevent a forged or stale signed request from substituting for the currently authenticated Principal and Student PRIMARY placement.

## The two real previously accepted facts being composed

The [PR #92 PostgreSQL trial](../../supabase/proposals/student_photo_private_actor_scope_resolver_trial.sql.draft) **actually ran against local authenticated PostgreSQL** and verified a verified Principal, one current active Student PRIMARY placement, exact Campus, and independently live `student.profile.update` and `student.photo.submit` scoped permission. Its `app_private.d1_student_photo_private_issue_resolver_trial(uuid,uuid)` is a **disposable, no-login-Student-executor-owned private function** and is rolled back after the test, not a deployed API. It obtains the Foundation shared authorization lock which serializes Foundation authority changes against a current operation. Separately, PR #91's **test-only** `LocalPrivatePhotoIntentCandidate` verifies genuine private-service Ed25519 request signatures, pinned control-plane entitlement revision, school/project/Student/Campus/Principal/purpose, nonce, token hash, expiry and once-only use under the same **local SQLite** file. Its legacy `issue_trial` and `consume_trial` accept synthetically signed Boolean permission assertions as test fixtures, **not** actual authorization.

## New bounded Python handoff

`tools/photo_validation/student_photo_postgres_verified_handoff_candidate.py` subclasses only the **quarantined** Python intent ledger in a *separate* class, with no app endpoint or service integration. The new `LocalPostgresPhotoHandoffTrial`:

1. Requires a **trusted test-only DB-API connection factory**, pinned service signer/key ID, pinned school/project and three explicit **test-only** operator gates (file-upload/module/purpose). It never takes those flags from an upload request; they are not genuine production file.upload, module, or registry assertions. Its constructor and `db_connect` are **not** safe to expose to a client.
2. `issue_verified_trial(student_id,campus_id,now_epoch)` and `consume_verified_trial(token,student_id,campus_id,now_epoch)` each open a separate database transaction, query `app_private.current_principal_id()` from that session, and execute exactly `app_private.d1_student_photo_private_issue_resolver_trial(student,campus)` expecting an actual Boolean `true`. The Student and Campus are strict canonical UUIDs; **the Principal comes from the database**, not from a caller-supplied `principal_verified` or `principal_id`. No result from a missing/expired credential, SQL error, NULL Principal, wrong Student/Campus, false/string-true resolver or malformed UUID can create an intent.
3. After private SQL authorization succeeds it generates a fresh signed **test-only Ed25519 service envelope** with the actual verified Principal, exact Student, Campus, school/project and a fresh unpredictable per-stage nonce. The envelope's legacy Boolean flags are **compatibility fixture values constructed inside the controlled rehearsal** and never constitute independent real proof of `file.upload`/purpose entitlement. The existing SQLite ledger performs the usual fresh signed-subscription revision read, one-time opaque digest issuance/consumption and replay defense.
4. Holds the **PostgreSQL transaction open across** the SQLite intent transition in an attempt to preserve the PostgreSQL Foundation shared authorization lock during issuance and consumption. Revocation of a PostgreSQL permission before the new transaction causes denial. If the Principal, Student placement or Campus changes before consumption, the old intent cannot be consumed. The subclass expressly **overrides and denies** both original `issue_trial(signed_request)` and `consume_trial(token,signed_request)`, removing the old direct signed-Boolean bypass on this new class.

`tools/photo_validation/tests/test_student_photo_postgres_verified_handoff_candidate.py` uses **synthetic DB-API connection doubles** and real Ed25519 keys/a temporary durable SQLite file to verify exact private SQL invocations, identity/Student binding, revoked permissions, Student Campus movement, Principal change, wrong UUID, malformed SQL results, policy gate off, signed entitlement suspension, raw signed-envelope bypass denial, DB transaction held across SQLite commit, persistent reopening, and once-only consumption. These Python tests **do not connect to the real PostgreSQL service**; that limitation is deliberate and must be retained in status reporting. The separately running D1 local runtime workflow still proves the independently accepted rollback-only SQL helper's real-domain behavior, **not an end-to-end handoff**.

## Explicit hard stops / cross-database atomicity gap

This is **not a safe production two-phase commit**. PostgreSQL and local SQLite **do not share a transaction**: a PostgreSQL rollback/commit error or role/placement change racing between systems can leave an orphaned test intent or stale state; a held Foundation grant lock does not magically serialize all Student placement/domain changes or signed entitlement revision updates. Production needs one shared durable, reviewed authority and a checked Principal/Campus/Purpose/grant snapshot revalidation fence at actual storage FINALIZE, with tested revocation ordering across real instances. Also missing: a deployed resolver accessible under a reviewed purpose-specific private worker identity, real credential/JWT-to-Principal binding inside a trusted session, `file.upload` scope verification, actual module and purpose registry state, genuine signed subscription publisher/rotation/multi-host propagation, exact sanitized provider bytes/hash, immutable file/Student provenance and protected `PENDING→VALIDATED→AVAILABLE` metadata transitions.

**Never wire this test class or client-supplied `db_connect`, signer, system clock, service keys, policy flags, school/project or Student/Principal context into an operational worker.** `issue_verified_trial` returns a simulated opaque token that cannot grant real storage access. No deployed SQL, application endpoints, public RPC, new role grants, photo uploads, hosted Supabase migrations or Student Profile photo SET are changed.

**Frozen unchanged:** **31/35** protected operations accepted. Issue #67 Student Profile P1 remains open and Student photo SET DENY. Migration 10 stays `.sql.draft` (228 fragments, 34 relations, 97 permissions, 322 scope alternatives, 36 operations).

**Simple example:** A staff Principal has an issued fake Student A photo token when Campus A permissions were active. Their real PostgreSQL permission is revoked before consumption. The next private database check must fail, so the token remains unconsumed, even if someone independently signs a `photo_submit_granted=true` request. This specific Python handoff is tested with a DB-API simulation and still needs genuine cross-database integration and atomicity acceptance.
