# DB03 S8 — independent principal document review

The next increment after S7 collects private certificates, records independent principal decisions and clears the document stage. The owner requires administrators to prepare applications and principals to verify and approve them. The existing P3 design distinguishes certificate rejection from application rejection. This implementation preserves that distinction.

## Scope and source of truth

Five inactive `08_*.sql.draft` fragments depend on S1–S7, in lexical order. No executable migration, production seed, entitlement, permission activation or hosted change is added. Three immutable forced-RLS sources record confirmed byte accesses, document review revisions and document clearances. Composite foreign keys bind each read to its application/forward/link/file, each review to the same reader and exact file version, and successors to their original stream. Clients and the worker login have no raw table access. Protected executors insert their designated sources; update, delete and truncate are prohibited.

The protected commands are `review_admission_document`, `approve_admission_documents`, `read_admission_principal_checklist` and `read_admission_document_feedback`. Reviews accept `VERIFIED` or `REJECTED` with a private reason. Reasons never enter general audit/outbox payloads. All effects have atomic receipts, audit and outbox references; failures roll back the source and root version. Same-key retries authenticate and authorize again before returning historical results; they never reapply the effect.

The principal checklist covers required document kinds from the current published collection policy: birth certificate, transfer leaving certificate and additional required policy documents. Optional attachments may be read but this increment does not decide them or make them clearance gates. Published policy/required-link changes, unavailable files, withdrawal and stale application versions fail closed. Clearances produce `DOCUMENTS_APPROVED`; they leave the application root `DRAFT` and create no Student. Cleared bundles leave the effective principal queue.

## Authority and private bytes

Exact `PRINCIPAL` role, action permission, active whole-chain assignment/grant/scope contract and School ALL or matching Campus scope are required. Read additionally requires `file.view` on the same principal role basis. Review and clearance must be independent of the actual uploader, including users who hold both administrator and principal roles. A review references that reviewer's own confirmed read of the exact forwarded link and file version. Read proof identifiers are references, not bearer authorization.

`AdmissionDocumentService.read_certificate` authenticates through the trusted adapter and calls worker-only descriptor/confirmation functions through the restricted `schoolos_file_login`. It loads bounded original bytes using the server's allowlisted storage mapping, revalidates MIME/size/hash and checks current database authorization and target state after external I/O. The response contains bytes, MIME and a read proof ID; it exposes no provider credentials, object key or public/signed URL. Confirmed access proves server validation for a response, not human viewing or network delivery. No HTTP route or Flutter implementation is introduced.

A trusted server `read_gate(school_id)` must explicitly return `True` before and after I/O and before returning bytes. It is separate from upload entitlements: disabling upload capability does not erase or prevent otherwise authorized reads of retained records. An unwired/denying read policy closes the route. The product's unresolved commercial subscription-suspension read policy is not invented here; configuring and proving it remains an activation gate. A deployment must never allow clients to supply this callback.

Review and clearance capture hashes of the current principal, binding, operation and complete live authorization chains, including their row versions. Revocation, expiry, rebinding or catalog changes invalidate the prior authorization basis. A fresh independent read/review revision and clearance are then required. Even a harmless role label change conservatively invalidates the basis. Old history remains. Existing rejected links remain rejected regardless of later reviewer revocation; replacing the file is required. Arbitrary decision reversal/correction is a separate future workflow.

## Rejection and deadlines

Rejecting a required certificate invalidates the effective forward and returns the application to `PENDING_DOCUMENTS`. The administrator sees the current rejected kind and private reason through a scoped checked read, uploads a replacement and forwards a new bundle. Rejected links cannot be forwarded again. Reviews belong to a particular forward, so replacements require fresh independent review of the required bundle. Neither review nor replacement grants new grace: S7's original application-wide maximum of two School-local calendar months and shorter document due dates continue unchanged. Timely received files can be reviewed later. Automatic overdue application rejection is still a separate task.

Example: an admin uploads a birth certificate PDF and leaving certificate image. The principal opens the retained originals, verifies both and approves the document stage. If the birth date is unreadable, the principal rejects that certificate; the admin replaces it within the original deadline and forwards the bundle for fresh review.

## Validation and remaining gates

The CI runner installs S8 transactionally, injects a failure and proves rollback restores the S7 snapshot function and removes new sources. It reruns all 305 DB03 pgTAP assertions, 220 frozen Foundation assertions, existing service/PDF integration and all 29 previous PostgreSQL schedules. Seven new response-boundary unit tests bring the service suite to 49. A new real Auth/worker/archive integration suite exercises actual PDF/image reads, independent decisions, rejections/replacements, downgrade reads, byte mismatch, quarantine during I/O, atomic outbox failure, immutable history, authority invalidation and bounded events. Four observed-block PostgreSQL schedules cover same-key review, quarantine, withdrawal and role revocation against review. Exact counts and observed runtime outcomes belong in PR #102; prepared tests alone are not acceptance.

Not included: full principal application approval/submission, Student creation, Finance/D1 dependencies, automatic deadline rejection, UI, HTTP deployment, executable migration activation, populated upgrades, production persistence/retention/recovery, commercial read-policy activation or broad cross-workflow lock/performance acceptance. The tested local archive remains one trusted host with permanent private retention; deployment and recovery evidence are still required.
