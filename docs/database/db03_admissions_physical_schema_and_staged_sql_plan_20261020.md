## 1. Fifteen-entity disposition — precise physical ownership

No sixteenth persisted evidence table is introduced in this pass. The previous optional `admission_handoff_stage_bindings` can be **omitted** if protected writers always bump the application/stage evidence epoch under the application anchor, and the consumer locks that anchor, checks the epoch **and re-evaluates every policy-stage head** under the same transaction. Epoch/digest alone is inadequate. If integrated D1 owners cannot implement reliable re-evaluation, a separately reviewed normalized binding table is required and the entity count increases to 16, not hidden inside a JSON blob.

Every table below belongs in `app_private`; PK `id uuid DEFAULT gen_random_uuid()`, required `created_at/created_by` (principal FK), protected history, FORCE RLS, no ordinary DELETE/TRUNCATE or direct authenticated/anon/service_role write. Mutable rows get server-maintained `row_version bigint NOT NULL DEFAULT 1 CHECK >0` and `updated_at`; immutable event rows use monotonic **domain revision** rather than fake business mutability. All FK deletes and updates RESTRICT. Physical indexes include PK indexes; list only additional search/unique indexes. Name and shape are **candidates** until approved/installed.

## 2. SQL constraints, effective intervals and trigger matrix (future installation contract)

**Shared types and rules:** `uuid` identifiers, `timestamptz` instants (use trusted server stamp), `date` academic/effective business day, `bigint` counters/revisions where declared; `CHECK (effective_until IS NULL OR effective_until>effective_from)`, with half-open `[from,until)`. `CHECK` validates row-local shape only; foreign keys **cannot** prove current policy stage, current Person row_version, or Finance truth. `UNIQUE` of predecessor prevents forks but not hidden cycles; require same-aggregate predecessor and prior revision via guarded trigger. No historical row UPDATE except explicitly one-way effective-bound/terminal metadata transition permitted by reviewed contract. No mutation after handoff consumed.

**PostgreSQL implementation cautions:** a partial unique index is not a deferrable constraint; design the single-row handoff terminal transition to avoid relying on its deferral. Do not change unique semantics with nullable composite fields accidentally; use separate partial predicate indexes. Where deferred FK/constraint triggers are used, require `SET CONSTRAINTS ALL IMMEDIATE` in positive and negative acceptance before rollback. No autonomous SQL exception-swallowing or side-effectful checks that forge approval evidence.

## 3. Authoritative lifecycle versus derived phases

Application authoritative source-node vocabulary from #79: `DRAFT,SUBMITTED,IN_PROGRESS,ACCEPTED,REJECTED,WITHDRAWN,CONSUMED`. `CANCELED` is **candidate SC-01**, not existing approved state. `REJECTED,WITHDRAWN,CONSUMED` are terminal in the proposed lifecycle; `CANCELED` would be terminal if approved. CONSUMED is final for Admissions—subsequent withdrawal/correction uses D1. `IN_PROGRESS` encompasses verification, test and interview without new application enums. `ENROLLMENT_READY` is derived fresh truth from application/policy/identity/offer/Finance/approval snapshots, not a persisted client flag. `HANDOFF_READY` is separate `admission_handoffs.state=READY`. Offer ISSUED/ACCEPTED/DECLINED/EXPIRED are independent #14 event-heads; fee clearance/waiver is independent #11 typed evidence-head.

**Proposed phase flow:** DRAFT → (verified Person) SUBMITTED + APPLICATION number → IN_PROGRESS (documents/assessments/approval+skips+exceptions) → ACCEPTED (final decision) → optional offer issue and accepted decision if published policy requires it → derived ENROLLMENT_READY → server-issued READY handoff + ADMISSION number → D1 single-transaction consumption → CONSUMED. **Conflict awaiting SC-01/02:** #79 describes ACCEPTED as requiring a final unused handoff in the **same acceptance transaction**, while the newer offer/readiness design allows ACCEPTED before READY. Two acceptable owner choices: **A (recommended)** distinguish accepted Admissions adjudication from terminal enrollment readiness and allow ACCEPTED before handoff, with guarded READY issuance; **B** make ACCEPTED only on final issue after offer and fee acceptance, making pre-handoff approved decision a separate typed phase. Neither choice is silently frozen.

Each state change in #13 has actor, authority snapshot, `expected_row_version`, previous/current state, immutable reason code, receipt and timestamp; all same-key commands are idempotent under Foundation receipt lock. Every identity rebind, stage outcome correction, offer decline/expiry, approval invalidation, fee reversal/waiver revocation, destination change or policy-eligibility change **invalidates dependent unconsumed readiness and READY handoff** atomically at accepted serialization point. Revocation after CONSUMED retains Student and invokes D1/Finance remediation, not Admissions deletion. A historical approved waiver does not override a *current* revoked/expired waiver; revalidation is compulsory.

## 5. Lock DAG, handoff consumption and receipt state machine

Frozen D1 prefix: `READ COMMITTED`; Foundation School auth `(71001,1)` **SHARED** → canonical command-key lock namespace `71002` → Principal/operation/workflow locks → D1 School/config/Student-ID allocator/policy/roll allocator → Person → Academic Class → Campus → Academic Year → Class Offering → Section Offering → child history. Final existing D1 school/roll prelock and allocator overrides, School-local date and retained roll history must be inspected in **assembled order**; do not call a stale earlier definition.

**Proposed DB-03 child aggregate rule:** Admission-only writers use a compatible Foundation prefix, School anchor, preidentified Person and relevant academic ancestry in approved order, then the application's `FOR UPDATE` row (sorted by UUID if multiple), then its typed history children. Re-read and re-authorize after waits. This *does not* approve the exact global rank of Admissions/Finance locks for a D1 writer; D1 may need pre-read immutable IDs without locks, collect all School/Person/destination anchors, lock in global order, then lock app/handoff and revalidate. No handoff writer may take an earlier D1 School lock after already locking an Admissions child if D1 uses reverse order. **SC-06 cross-owner DAG is OPEN**, especially Finance reversal interacting with D1 and Admissions.

```text
Admissions VERIFIED current app ACCEPTED + stages + offer + Finance/waiver
       |
       | trusted issuance (single transaction, receipt/number/issuer)
       v
    Handoff READY  --[amend/cancel/reverse/waiver revoke]--> INVALIDATED
       |
       | future D1 CREATE only; dual live permissions; exact source version;
       | School→allocator→Person→Academic, Finance fence, app/handoff locked;
       | capacity, first status, Student ID, PRIMARY enrollment, roll, receipt
       v
    Handoff CONSUMED [Student UUID + Foundation receipt, irreversible]
```

A READY→CONSUMED `UPDATE ... WHERE state='READY'` must affect **exactly one** locked row; defensive CHECK/trigger and partial UQ block second transition. `CONSUMED` cannot revert to READY and may not be invalidated. No new READY/CONSUMED handoff may coexist for that application, but an INVALIDATED revision may remain while a new READY revision references the **same** admission number ledger row (no premature number reuse). A crash before transaction COMMIT rolls back Student, school Student ID counter, enrollment, roll, receipt, audit/outbox and handoff state together; crash after COMMIT may drop response only. Exact same-key intent replay returns original result **after current actor authorization**, no side effects. Different-key competitor fails already consumed. Admission-only DB-03 work **must not** implement this D1 consumer.
