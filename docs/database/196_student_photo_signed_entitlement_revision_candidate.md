# Student Profile photo — real Ed25519 snapshot verification and local revision fence (quarantined)

Date: 2026-10-17. **Status: new security candidate; exact-head CI and independent review still required.** Baseline is frozen `main` `35a70c676a58ba2ad67031222b7626c637bcde0e` after PR #88. The governing architecture is [ADR-004](../decisions/ADR-004-storage-plan-entitlements.md) and [storage entitlement/purpose contract](../architecture/05_storage_entitlements_and_document_purposes.md); the prior [PR #88 freeze](195_student_photo_intent_entitlement_ci_merge_freeze.md) explicitly left cryptographic snapshot verification unimplemented.

## What this isolated slice actually implements

`tools/photo_validation/student_photo_signed_entitlement_candidate.py` is a **private, non-deployable Python test model**, independent of both the synthetic policy model and the Student SQL. It uses the pinned local CI `cryptography==46.0.4` Ed25519 verifier with **actual cryptographic signature verification**, not a caller-provided `signature_verified=True` flag. The included private signing keys are ephemeral and generated **inside tests only**; the repository contains no real control-plane key or credential.

A deliberately candidate-only version-1 JSON envelope carries four exact top-level keys: `alg`, `kid`, `payload`, `signature`. Verification signs a domain-separated deterministic canonical encoding of the protected `alg`, `kid` and payload; pins the selected Ed25519 public key and expected issuer; rejects unknown algorithm/key ID, invalid base64/signature, malformed/duplicate JSON keys and unsigned envelope extras. Payload requires exact schema fields: schema version, issuer, school ID, project ID, monotonically increasing revision, plan-definition-version reference, typed Boolean effective capability map, subscription state, issued/effective/expiry timestamps. Explicit `storage.student_photo.upload: true` with `ACTIVE` subscription is required for a positive **local prerequisite**. Unknown purposes and a broad `storage.*` name never imply student photo entitlement. No real billing catalog or plan pricing is created.

Finite **candidate test bounds only**: 8,192 maximum encoded envelope bytes; 300-second maximum snapshot age and lifetime; 60-second maximum trusted local cache freshness; zero candidate clock skew. These are **NOT approved production TTL, refresh intervals, clock-skew policy or propagation SLAs**. Time is supplied by a trusted test harness, **not verified against a production monotonic server clock**. Future-effective, expired, incorrectly typed, wrongly audienced, overly old or conflicting-revision assertions deny without exposing internals.

The per-school/project **local SQLite** rehearsal uses `BEGIN IMMEDIATE` around monotonic revision acceptance and an append-only-in-purpose local audit event row. Its persistent high-water revision, accepted fingerprint, expiry, freshness and invalidation flag survive creating a new Python instance on the **same file**; signed downgrades/suspensions also raise the high-water mark. An identical signed revision may be rechecked but **cannot extend freshness**; a conflicting same-revision payload or an older revision denies. Trusted local push invalidation blocks new use and cannot be cleared by replaying the same revision; only a strictly higher authenticated revision may reactivate it. A short-lived local entitlement prerequisite `require_current` refuses expired/stale/inactive/invalidation cases. It does not issue an upload intent or modify any file or Student record.

## Explicitly limited assurances

SQLite transactional serialization is **only across connections using the same local file**. It is **not shared across 200+ school backends, multiple hosts or regions**, and a `require_current` check is **not serialized with a protected file-finalization transaction**. An untrusted caller can choose the SQLite path, public key, school/project arguments and clock if the module is exposed. Therefore a real service MUST source those from sealed deployment configuration and server-verified school/principal context, never from an uploaded blob, client JWT metadata or ordinary School setting; the candidate is not a security boundary when exposed to users. The canonical signed envelope is a **custom trial protocol, not a reviewed interoperable deployment standard**.

The following remain mandatory before enabling any Student photo upload or photo SET:

1. Production-approved signed snapshot protocol/key trust rotation; real control-plane issuance, signed delivery, finite owner-approved clock and freshness settings, durable trusted distributed revision/high-water/cache activation, audit controls, revocation propagation across instances, recovery/repair and expiry handling including future-effective staged activation. In this slice future-effective snapshots deny rather than stage.
2. A genuine private authenticated Student-specific intent service with one-time durable intent consumption, current Principal/scope/module/photo-purpose grants, actual Student PRIMARY placement/owner and school/Campus binding. Do not substitute local cryptographic entitlement for independent domain authorization; do not promote the synthetic dataclasses from PR #88 to trusted claims.
3. Transaction-ordered entitlement finalization and true multi-instance contention/race evidence, real purpose-bound file worker, stored exact decoder-sanitized bytes and measured hash, protected `PENDING → VALIDATED → AVAILABLE` transition, retention/quarantine/forensics and separately accepted Student photo DIRECT/P1 APPLY semantics.
4. Security review of the candidate envelope, encoding, stored-state tamper resistance, key rotation, dependencies, operational isolation and temporal policy before production implementation.

## Regressions and release discipline

The new `tools/photo_validation/tests/test_student_photo_signed_entitlement_candidate.py` exercises eleven unittest scenarios with **real ephemeral Ed25519 signatures** and a temporary SQLite file: signature/key/algorithm tampering, duplicated JSON and noncanonical assertions, strict schema/school/project/type checks, future/expired timestamps and finite bounds, durable reopen, invalidation, signed suspension, downgrade/anti-rollback and same-revision-conflict resistance, no-freshness-extension replay, and **two local SQLite connections** racing revisions. None simulates a genuine cross-host backend cluster or real Student photo finalization. The dedicated photo workflow installs pinned cryptography **only inside local CI** and runs the eleven tests alongside existing 11 decoded-image and 9 synthetic-intent tests; Foundation, D1 draft-static and D1 local runtime remain independent required PR gates.

**Freeze remains unchanged:** 31/35 protected change operations accepted; Issue #67 OPEN, Student Profile photo SET DENY by default, D1 Migration 10 `.sql.draft`, 34 relations/228 fragments/97 permissions/322 scope alternatives/36 contracts unchanged, no hosted Supabase deployment, no public endpoint or grant.

**Simple example:** The SaaS control plane signs an entitlement for School A / Project A. Changing the JSON school, capability or expiry without its signing key fails verification. A valid new signed revision that suspends photo upload blocks new use; replaying an older still-permissive signature cannot bring photo upload back. This is a local unit-test model, not a real upload service.
