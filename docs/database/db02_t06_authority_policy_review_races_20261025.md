# DB-02 T06 — authenticated change/APPLY versus Foundation authority

Eight disposable two-backend cases use distinct verified Auth Principals and an exact `(71001,1)` PostgreSQL advisory blocking dependency. A freshly reset local database, frozen Foundation migrations, unchanged D1 `.sql.draft` chain and singleton School fixture isolate each case. All production operation, permission and route changes are confined to this disposable fixture.

DIRECT REPLACE is blocked behind an owner-held Foundation EXCLUSIVE authorization lock while the School ALL grant, assignment scope or role is revoked, or the global P1 route changes from DIRECT to APPROVAL. Once the owner commits, the authenticated command must fail without a policy successor, allocator, receipt or outbox event. The opposite ordering lets the authenticated command commit with its SHARED Foundation lock first; the owner revocation waits on that exact backend, then commits, leaving one valid policy success and no duplicate effects.

For APPROVAL APPLY, the fixture creates a genuine requester B SUBMIT and independent reviewer A APPROVE against a frozen global P1 UUID and exact old policy. The approved request is still inert. The owner holds EXCLUSIVE authorization and retires the reviewer's permission grant, retires the reviewer's dedicated role, or replaces the global APPROVAL P1 version with another APPROVAL version. The authenticated requester APPLY waits on that holder, rechecks after the commit and durably INVALIDATES the request with one terminal REJECTED apply receipt. It creates no policy successor, allocator, application or changed event. The old source/pool and prior SUBMIT/REVIEW history remain retained.

All revocation and P1 mutations are owner-only CI fixtures, not claims of a public security-admin API. The raced DIRECT, SUBMIT, REVIEW and APPLY calls use only protected authenticated entry points. T06 does not authorize hosted deployment, migration activation, merge or independent security signoff.
