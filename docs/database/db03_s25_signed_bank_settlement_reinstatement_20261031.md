# DB03 S25 — cryptographically signed bank settlement and independent reinstatement

**31 October 2026 · review-only source.** Stacked on S24 [PR #188](https://github.com/yunusyosaf399/edusync_saas_school_app/pull/188); parallel monthly fee/scholarship [PR #102](https://github.com/yunusyosaf399/edusync_saas_school_app/pull/102) stays untouched.

## Explicit trust and deployment boundary

Uploaded parent slips, Finance return reports, S23 ledger reviews and S24 independently reviewed private bank documents **do not establish authoritative bank settlement**. S25 introduces an isolated `finance_admission_bank_signers` trust registry and `finance_admission_bank_settlement_attestations` with an HMAC-SHA256 signature validated **in PostgreSQL against a 32-byte private, school-scoped signing key**. Bank keys are accessible **only** to the private schema owner; even the dedicated authenticated worker cannot SELECT, INSERT, rotate or replace a key, and `anon`, `authenticated`, and `service_role` have no access. Every accepted attestation includes the exact School, Campus, Applicant, reported return, original `ADM-` payment, signing-key ID, unique bank event UUID, trace, decision, full payment minor-unit amount, currency and current epoch. A signature over the complete canonical JSON array must match in constant-sized cryptographic digest; freshness is limited to ten minutes either side of the worker's clock and signer activation/expiry/revocation are checked. A bank event UUID can be used only once per signer; each reported return has at most one immutable attestation. No plaintext signing key is returned in any receipt, audit event, outbox or response.

**The repository intentionally provisions zero actual bank keys or school operations.** A single clearly synthetic signing key exists only in a disposable CI fixture to verify the cryptographic contract. Real banking-source trust is unavailable until bank-provided credentials are independently authenticated, securely provisioned by a privileged operator, rotated/revoked under audited controls, and a production-grade event-delivery gateway is connected. A test-signed event is never represented as genuine Saudi banking evidence.

## Separation of authority

The guarded bank event issuer `app_private.db03_record_signed_bank_settlement(...)` is accessible only to `schoolos_file_login`, under a real fresh JWT and a live single-chain campus `ACCOUNTANT` permission `finance.admission.payment.bank.settlement.record`. The actor must differ from the S22 original reporter and S14 payment issuer. The command locks School → Campus → Academic Year → Applicant → Return → Official Payment → signer, requires existing reviewed S23 ledger and S24 private documentary evidence, verifies current signer HMAC, applies idempotency and produces one immutable attestation plus exactly one receipt/audit/outbox. An outcome is either `BANK_CONFIRMS_RETURN_SETTLED` or `BANK_CONFIRMS_NO_RETURN`. The first remains permanently unavailable for reinstatement. Both outcomes leave the applicant on the S22 reconciliation hold until separate Finance action.

The distinct `app_private.db03_reinstate_disproven_bank_return(...)` requires an **independently authenticated fourth Finance officer** with a separate live campus `ACCOUNTANT` permission `finance.admission.payment.return.reinstate`, different from the bank attestor and return reporter/issuer. The source must be an authentic signed `BANK_CONFIRMS_NO_RETURN` event, with a still-valid signer and clean documentary contradiction review. A document explicitly marked `DOCUMENT_SUPPORTS_RETURN` is a reconciliation conflict and cannot be silently overridden. The reinstatement command rechecks the original event's HMAC, signing-key status, attestation receipt/audit/outbox, school/campus/version/Finance scope and locks; app must remain in DRAFT and not have been forwarded. It creates one append-only release approval and **exactly one reinstatement per historical S22 reversal** with exact amount/lineage. No existing bank receipts, S20 allocations, S22 reversals, or assessments are altered. Competing requests for the same return serialize and only one credit release is allowed.

The private S25 snapshot overlay shows signed-event count, restored exact minor units, remaining return holds and current/historical effective allocations. Unresolved or bank-confirmed returned funds remain `BANK_RETURN_RECONCILIATION_REQUIRED`; when every reported return was proven not to occur **and** separately reinstated, the original S21 funding state returns, but always `clearance_issued=false`. **Legacy S22 allocation insertion remains fenced even after a favorable reinstatement**; accepting new funds against revised assessments requires another controlled reconciliation release design. This S25 scope does not implement a bank refund, payout, re-assessment, new allocation, Principal approval, or Student creation.

## Disposable acceptance

The new four-file inactive proposal, synthetic local-only banking trust and fourth independent Auth principal, 23 pgTAP privilege/contract checks and intentionally failed DDL rollback rehearsal are integrated into DB03 CI. End-to-end signed-bank tests must prove wrong-person/wrong-applicant denial, forged signature and out-of-window events denied, exact replay, duplicate event, confirmed return never reinstated, separate reviewer release, two-backend race, zero-allocation release, correctly restored net snapshot, original history intact, authorization revocation and no clearance. Historical S14–S24 tests and DB08/static must remain green. **No hosted migration or production key activation.**
