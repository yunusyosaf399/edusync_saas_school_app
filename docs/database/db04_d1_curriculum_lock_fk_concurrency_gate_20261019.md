## 2. Reconciled effective-D1 lock order (2026-10-20) and corrected DB-04 candidate

### 2.1 Historical inversion and supersession

The **2026-10-19 source state** allowed an Enrollment END operation to lock Student before its Roll history trigger tried to lock School. A proposed Curriculum School→Student command could then produce an E→School→Curriculum→Student→E wait cycle. This was a **source-derived possible deadlock**, never an executed DB-04 failure.

**2026-10-20 D1 sources supersede the relevant function bodies:** `effect37_02_db01_end_source_prelock` first added the School→stored source policy IDs (UUID ascending)→exact allocator IDs (UUID ascending) prelock before Student. **`effect40_02_school_local_roll_consumers` is the later, effective replacement of `app_private.d1_enrollment_end_lock_context`**; it retains that lock prefix and changes a specific current-source date comparison to `app_private.d1_roll_business_date(path.school_id)`. The Roll history trigger `effect30_33` still takes School/Policy/Allocator during Roll UPDATE; in an authorized END using that final lock context those rows were prelocked before Student. **This resolves the previously documented END School-after-Student path at the source-code contract level**, not as independently proven DB-04 runtime acceptance.

MOVE's effective `d1_enrollment_move_lock_context` is updated by `effect39_01_enrollment_move_roll_union`: it first discovers source/destination ancestry without row locks, locks School, re-discovers, locks **all retained source and date-effective destination policy rows in UUID order**, then both exact allocator-pool rows/unions in UUID order, and only afterwards calls `d1_enrollment_move_lock_context_base` which locks Student, source Enrollment and academic path. `effect39_02` and `effect39_03` route DIRECT, SUBMIT and APPLY through this context before their destination-only recheck; `effect39_04` repairs narrow Workflow internal EXECUTE, `effect39_05`/`effect39_06` repair operation-scoped reviewer/application reads. Earlier effect26 function-body observations remain historical. Subject ARCHIVE and Class/Section Offering actions still take School before academic/Subject row locks in inspected base draft.

**Caveats:** These are ordered draft definitions, not permission to activate Migration 10. Although D1 tests documented for END (#114) and MOVE (#115 and composed stack) exercise real local two-session waits, they **do not include DB-04 tables/commands**. School-wide policy/allocator prefix semantics depend on the final source release. Any future D1 replacement changing this ordering must trigger DB-04 re-review.

### 2.2 Proposed common lock hierarchy; one conservative School-first candidate

**[PROPOSED, not an approved physical or authorization decision]** Use a common prefix for **every Curriculum mutating command**, including Student-selection APPLY:

1. Existing Foundation `(71001,1) SHARED` authority gate, canonical per-command `(71002,key)` receipt/advisory fence, verified Principal/approved workflow request-step sequence; never invent shared Foundation grants.
2. Derive School and affected Student/academic/Subject identifiers by non-locking ancestry discovery. Lock **`app_private.school_profiles(id) FOR UPDATE` FIRST among mutable domain parents** and verify the still-authoritative School/context.
3. For a Student election **there is no roll allocation operation**: do not lock/modify roll-policy or allocator rows, but do take the School anchor **before** Student. Then lock Student `FOR UPDATE`, followed by the accepted source Enrollment `FOR UPDATE` and complete expected immutable source snapshot, then sorted D1 Academic Class→Campus→Academic Year→Class Offering→Section Offering→Subject ancestors. Revalidate source Enrollment and all usable states after waits. D1 Enrollment has **no `row_version`**; use Student `row_version` and exact Enrollment columns.
4. For publication, revision replacement or Section offering changes: School → sorted D1 Academic/Subject ancestors → DB-04 version/applicability/group/offering lineage. **Publication must never acquire a Student or source Enrollment row late**; reject impact on existing selections unless a separately approved Student-scoped protocol handles it.
5. For both publication and election, resolve and lock the exact shared **DB-04 curriculum definition/revision/applicability fence** in deterministic rank after D1 ancestors; publication validates impacted accepted elections, election validates unchanged revision digest, group count and published interval after waiting. For first publish/zero-applicability, use the already-existing definition/root and a database non-overlap backstop.
6. Lock DB-04 selection lineage after parent/fence; collect multiple Student IDs and D1 source/destination IDs up front if a future approved command spans more than one. **No hidden DB-04 trigger may acquire an earlier-ranked School/D1 lock after later ranks**. Review implicit FK `KEY SHARE` and deferred constraint/receipt triggers in the final DDL.

**Why revise the previous Student-without-School candidate?** The existing D1 END/MOVE code now consistently prelocks School **before** Student. A School→Student Curriculum election aligns with those writers and with D1 Subject/archive academic commands. The old no-School route is no longer necessary to avoid the specific END inversion and has not been independently proven safe for all cross-domain FK triggers. A School-first choice is intentionally conservative (serializes school-wide writes and may reduce throughput); performance and concurrency improvement requires its own audited redesign rather than assuming no School lock.

**Boundary:** This is **static compatibility reasoning only**. It does *not* establish absence of reverse waits from D1 deferred triggers/other domains. Before authorizing SQL: inspect final assembled ownership/trigger calls and use genuine two-session tests, especially when approval workflows/receipt triggers run. If any D1 producer still locks Student before School, **STOP** and reopen L-01; do not patch D1 from DB-04.

## 4. Effective-time fencing and publication vs Student choice

**[PROPOSED] Publication** acquires School and Academic/Subject parents, then immutable DB-04 revision/applicability anchor. Before finalizing, it queries impacted accepted selection intervals **without locking Students**, evaluates whether replacement would orphan a choice at any relevant Student/Enrollment segment, and either rejects or relies on a **separate approved** transition operation. No optimistic “notify students then fix later”; historical Exams keep previously observed snapshots. It stamps immutable content digest + recorded publication time and dated applicability; no past row rewrite. If multiple sections affected, acquire their Class/Section/Subject identifiers in defined type/UUID order.

**[PROPOSED] Selection** locks School first, then Student + precise D1 Enrollment snapshot, Academic parents and the existing revision/applicability fence, then validates complete current permission + Subject/section state, eligibility and group cardinality **after waiting**. Its canonical intent binds current revision digest/expected selection head, no arbitrary client “purpose”. For accepted COMPULSORY, derive eligibility from rule+Enrollment; no fake Student selection row. For OPTIONAL/ELECTIVE, append accepted choice with retained supersession lineage. At source Enrollment END or MOVE, effective eligibility always intersects the *true D1* `[effective_from,effective_until)`, never follows a prior-year Student-choice row. If current D1 Enrollment ends before an accepted future choice, the effective read clamps to Enrollment and new changes deny; an explicit Student transition plan may later reconcile that pending choice, but must not rewrite it silently.

**[DERIVED] Publication–selection linearization:** because neither publication nor selection writes D1 canonical Enrollment, and publication never locks Student, both may converge on a **stable DB-04 applicability row**. Publish-first → selection wakes and rejects stale revision/context. Select-first → publish wakes and detects newly accepted potentially orphaned choice; reject unless reviewed transition covers it. In the zero-predecessor first-publication race, no selection can have previously valid applicability; exact definition/revision uniqueness and newly published coverage must be enforced at INSERT. This requires a real concurrency test and a proven commit-boundary digest check.
