### Key contradiction requiring implementation coordination

**The defensive persistent collision check is broader (all retained historic cross-Student rows) than the final automatic allocator's candidate scan (excludes superseded rows).** Consequently the current code does **not** consistently *choose* safe values despite a later rejecting guard. A DB-01 correction can make this problem observable by creating superseded allocations; DB-02 policy handoff can make it recur across revisions. This mismatch is not a claim that SQL currently allows theft (the guard denies it); it is a guaranteed source of possible candidate/guard disagreement. The design must require matching predicates and actual contention tests before runtime approval.

**Additional significant lineage conflict:** the proposed DB-01 `origin_allocation_id = source.origin_allocation_id` is not a universal invariant from frozen SQL. In persistent origin creation, the original source has `origin_allocation_id=NULL`; on first correction, preserving NULL can keep source of the corrected current number discoverable via `supersedes_id`. But later persistent placement uses `origin_allocation_id` pointing at latest unsuperseded prior row, not necessarily immutable first-ever allocation. Thus `origin_allocation_id` is a **carry-forward provenance link**, not necessarily one fixed root ID. Audit same-Student chronology and resulting `d1_guard_crossrow` logic before choosing how descendants refer to that provenance. Do not overwrite its meaning with `supersedes_id`.

## 3. Concrete four-head chronology plus Enrollment MOVE

Example uses **persistent mode**, source policy P1 (r1), Student A, Enrollment E1 in Class Offering C1, and distinct server dates. All old rows stay retained. The proposed correction operation is **not executable**; table is expected contract if approved.

| Business date | Operation | Allocation (new ID) | Effective range after operation | predecessor/origin | Numeric |
|---|---|---|---|---|---|
| 2026-09-01 | authenticated INITIAL placement E1 | R0 | [Sep 01, Oct 02) | `supersedes=NULL; origin=NULL` | 12001 |
| 2026-10-02 | CORRECT #1 | R1 | [Oct 02, Oct 07) | `supersedes=R0; origin=NULL` **candidate** | 12007 |
| 2026-10-07 | CORRECT #2 | R2 | [Oct 07, Oct 12) | `supersedes=R1; origin=NULL` **candidate** | 12011 |
| 2026-10-12 | CORRECT #3 | R3 | [Oct 12, Oct 15) | `supersedes=R2; origin=NULL` **candidate** | 12013 |
| 2026-10-15 | authorized MOVE E1→E2, Section C1-A→C1-B | R4 | [Oct 15, infinity) | `supersedes=NULL; origin=R3` per latest-head persistent carry-forward pattern | 12013 |

R0…R4 remain immutable in identity, number and §effective_from§; R0…R3 only acquire their **one-way exclusive** §effective_until§ and §ended_at/ended_by§. E1 ends Oct 15, E2 begins Oct 15; R3 ends at the same time; R4 begins at boundary. Correction does not change Enrollment placement. There is exactly one effective allocation for each Enrollment at any supported business date; after MOVE only R4 is open. A replay of CORRECT #1 after MOVE must prove durable R0→R1 and the original receipt without demanding R1 still be open, and must reauthorize.

**Timeline caveat:** dates above are explanatory historical illustration, not requests to backdate corrections today. Under DB-01's proposed current-date-only RC-03, the three corrections occur on separate actual server dates. The first correction is impossible when source started that same day, because ending the source would violate `effective_from < effective_until`. Same-day repeated correction is intentionally unsupported by that recommendation. This is a **real usability/product decision**, not solved by using multiple timestamps within a DATE column.

### Potential defect at origin/correction source boundary

The first correction may leave `R1.origin_allocation_id = NULL`. In a later placement, `R4.origin_allocation_id=R3` carries latest accepted number and cross-row origin validator requires earlier same-Student persistent row; this is supported in principle. However final trigger invariants also compare unsuperseded later persistent allocations and may reject any correction when an existing later Enrollment has a different accepted numeric; the first release should deny correction if later dependent allocations cannot be reconciled atomically. DB-02 must settle policy-switch ownership first.

## 6. Cross-domain contract and safe implementation sequence

1. **DB-02 owner** freezes RP-02/RP-03/RP-07: effective policy cutovers (including future Enrollment commitments), permanent persistent ownership across corrected-away historic values, returning to persistent mode, treatment of prior academic context and policy revision namespaces, and high-water initialization. PR #101 currently explicitly leaves these open.
2. **DB-01 owner** freezes RC-01…RC-08 separately. Proposed default is no reuse of any historic persistent number by another Student, conservative deny for ambiguous academic historic reuse, one-day correction and append-only successor history.
3. **Upstream Enrollment/allocator owner** reviews final installed `d1_enrollment_place_allocate_roll` and `d1_guard_crossrow`: remove candidate/guard mismatch under reviewed semantics; prove school/policy/allocator/Student lock order across placement, MOVE, END and correction. No DB-01 authority to change these shared SQL drafts in this branch.
4. **After approvals**, separately authorized implementation can add new DB-01-only SQL fragments: verified source/scope resolver → school/policy/allocator lock and number reservation → exact closure/append effect → result verifier → DIRECT typed receipt/event → P1 submit/review/apply/read, retaining existing Foundation engines/owners/RLS; no schema duplication or new grant vocabulary. Use existing I12–I14 before proposing indexes. Migration 10 remains draft-only.
5. Write dedicated positive/negative, correction-chain/policy-transition and C1–C8 two-backend tests in a separately owned implementation/test stream; retain suite #65 unchanged until owner-approved activation integration. Require exact-head static, local disposable D1 acceptance, Foundation frozen regression, genuine blocking and independent security review. **No remote Supabase or Migration 10 application.**

**Blocking compatibility conclusions:**
- **CONFIRMED** persistent automatic candidate predicate excludes superseded rows while cross-row guard protects them. Must align before enabling correction.
- **CONFIRMED** academic collision is interval/policy/Offering based, not universal lifetime reservation. Permanent/no-reuse academic ownership requires a *new explicit decision*.
- **NOT PROVEN** final integrated MOVE prelocks policy/allocator before Student; mandatory final call-graph and two-backend verification needed.
- **UNRESOLVED** origin carry-forward after chains/policy switching and same-day correction restrictions require owner approval.
- **UNRESOLVED** policy replacement/return-to-persistent behavior is owned by DB-02 RP-02/RP-03/RP-07.

**Final gate: DB-01 BLOCKED BY ROLL POLICY DEPENDENCY.** This is an exact-source design gate only; no acceptance or implementation claim, no shared files changed.
