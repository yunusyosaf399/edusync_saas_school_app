## 2. Ownership, correction chain, namespace and temporal invariants (proposed)

**PS ownership is historical, not simply the latest head.** Recommended `H_PS(school,number)` = every retained `roll_allocations` for any `PERSISTENT_STUDENT` policy revision of that School with that `numeric_value`, regardless of closed, superseded, old Enrollment, or policy revision. A new Student B is denied a candidate N if **any row** in `H_PS(S,N)` is owned by A≠B. No Student can erase permanent ownership through correction. A particular Student may own several historic numbers after legitimate correction; each remains reserved to that Student (not necessarily the Student's currently displayed value). Source policy/allocator initialization and policy reentry RP-03 must enforce this identical rule. This is consistent with the broad final crossrow predicate and DB-02's **recommended** RP-03, but **owner approval is pending**.

**Two distinct graph edges:** for same Enrollment correction `Rn+1.supersedes_id = Rn.id`, source `Rn.effective_until = new.effective_from`, new UUID, unchanged immutable `enrollment_id/student_id/policy_revision_id`, `Rn` original numeric/created facts unchanged. The `origin_allocation_id` is a same-Student earlier persistent carry-forward reference for normal subsequent placement; the `supersedes_id` is the exact predecessor of a manual correction. **Recommended RC-04 conditional contract:** correction inherits source origin (NULL if original row has none); normal later MOVE uses the **latest unsuperseded persistent allocation** as the new Enrollment's `origin_allocation_id`, not a rewritten hard-coded root. Enforce `origin=NULL` for academic mode. Prior source can close only once; at most one successor may supersede an allocation. Guard verifies same Student and Enrollment through dynamic TG_ARGV and FK, but **command** must enforce source policy equality, exact boundary, current head, reason and result proof.

**Example for separate server business days** (not approval for backdated commands): E1/R0 [Oct 01,Oct 05) PS #12001, R1 [Oct 05,Oct 10) #12009 `supersedes=R0,origin=NULL`, R2 [Oct 10,Oct 15) #12011 `supersedes=R1,origin=NULL`, R3 [Oct 15,Oct 18) #12013 `supersedes=R2,origin=NULL`; MOVE Oct 18 closes E1 and R3 and creates E2/R4 [Oct 18,∞) #12013 `supersedes=NULL,origin=R3`. All R0–R4 remain retained. A new B cannot use historic #12001/#12009/#12011/#12013 under proposed permanent PS reservation. Three sequential **same-day** corrections are impossible with DATE history and the proposed positive interval restriction; that usability consequence is an explicit RC-03 decision.

**Academic namespace:** `(policy_revision_id,class_offering_id)` spans all Sections of that Offering. Cross-Student equality conflicts only when effective intervals overlap in the **current final guard**, not across all historical time. Same number in a different policy revision or Offering may be valid. DB-01 recommends *not promising permanent academic ownership* until owner expressly selects a reuse rule; its first release can simply reject historical reuse defensively, but a stronger rule than existing guard must be formally approved. Returning to a Section or Offering does not silently retrieve an earlier numeric component; the applicable policy+Offering/date must be checked, and a continuation/carry option requires separate RP-03/RC-02 agreement.

**Important policy-cutover blocker overlooked by a basic same-Enrollment correction:** if Student A's Enrollment remains active across a policy replacement, the old Roll's `policy_revision_id` can remain r1 while today's r2 is effective. The defensive trigger requires **successor Roll effective_from within its stored policy interval** (`effect30_32` 143–145). DB-01's proposed successor keeping r1 but starting today would therefore be **rejected** once r1 ended. Safe proposed first-release behavior: **deny `SOURCE_POLICY_NOT_EFFECTIVE_ON_CORRECTION_DATE`**, without rewriting historic Enrollment/Roll, unless DB-02 RP-02/RP-03 explicitly approves a typed cutover/migration policy and its constraints. Do not silently substitute r2 or relabel the numeric namespace in correction.

**Manual high-water candidate** (not implemented): under exact source School/policy/allocator row lock, validate `0 <= requested_numeric < 9223372036854775807` (plus owner-approved policy minimum); ensure equality/collision against all applicable history; update only `roll_allocator_states.next_value := GREATEST(next_value, requested_numeric+1)` **when needed**. Let M-row guard maintain version/timestamp; no `MAX()+1` allocator and never decrement. A high-water counter is only a candidate-generation mechanism, **not proof of uniqueness**. Counter, source close, successor insert, receipt/audit/event commit or roll back together. New revision pool initialization is **DB-02/DB-03 ownership**, not DB-01.

## 4. Corrected P1 DIRECT transaction — candidate exact steps

0. **Typed input v1**: immutable `student_id`, `expected_student_row_version`, `enrollment_id`, `expected_section_offering_id`, `expected_enrollment_effective_from`, `source_roll_allocation_id`, `expected_source_roll_effective_from`, `expected_source_policy_revision_id`, `expected_old_numeric_value`, `proposed_numeric_value`, nonblank restricted `reason`, `idempotency_key`; no client School, Campus, mode, origin, policy row version, authority or effective date. Freeze literal result code and typed RPC signature under RC-07. `expected_student_row_version` is a snapshot of Student core; do not manufacture a version field on immutable Roll row.
1. Begin `READ COMMITTED`; server compute verified individual actor; acquire Foundation advisory **SHARED `(71001,1)`** then existing `71002` idempotency namespace lock, verified Principal/operation contract/target and appropriate workflow locks in Foundation order. Require enabled `student.roll.correct` and permission. **Currently disabled: deny; do not run future steps now.** Build canonical *caller intent* hash with operation/version/all typed supplied fields/reason, and an immutable `effective_date_rule='SERVER_APPLY_DATE'`, but **do not hash volatile `CURRENT_DATE` as a dynamic value on every replay**, or next-day exact-key retries would falsely conflict. Persist actual effective date only when effect commits; submit-date and apply-date are distinct.
2. Terminal existing receipt: compare same Principal/operation/key/intended payload digest, validate durable original result via exact retained IDs/lineage and receipt state (no new mutation); **before returning any sensitive numeric/source fields**, recheck actor/participant current permission against a precisely frozen historical/current context disclosure rule under RC-07/RC-08. After MOVE/END the original Roll may be closed: historical result matching **must not demand successor still open**. If currently unauthorized, fail closed but preserve the retained successful receipt; changed-intent same-key denies.
3. For new effect, preflight discover School and immutable Enrollment ancestry, source policy/allocator ID and source Roll head, without considering an unlocked source snapshot authoritative. Compute complete affected row set; if discovered after higher lock, restart. Resolve one current P1 route for **source Campus**, require DIRECT and current ACS permission for exact ALL/CAMPUS/CLASS/SECTION scope, no FAMILY/teaching resolver bypass; capture exact active policy ID/version or equivalent revocation token from Foundation.
4. Acquire **School → exact source policy revision → exact source allocator** (and all relevant policy/allocator rows UUID-sorted if provenance dictates) **before Student**; lock Student; lock source academic parent hierarchy (`Academic Class → Campus → Academic Year → Class Offering → Section Offering`); finally Enrollment + current Roll row(s) in frozen child order. Every callback/FK/trigger must have no lower-order hidden lock acquisition. Re-select fresh School, source/policy, route version, live grants, effective dates and namespace after waits. Reject if source Section/Student/version/Enrollment start/Roll start/policy/old number differ, source not unique ACTIVE PRIMARY latest, source closed/superseded, Student ineligible, or policy/source Enrollment not effective on trusted business date.
5. Fix **trusted server business date at the locked apply statement**, according to RC-03 School-date/timezone owner decision; require `source.effective_from < boundary`, source current/Enrollment covers boundary, and `source.policy_revision.effective_from <= boundary < source.policy_revision.effective_until` (NULL upper unbounded), otherwise typed deterministic deny. If using SQL session `CURRENT_DATE`, ensure caller cannot select its effective timezone; exact school-local vs server-fixed date rule needs owner sign-off. A request approved yesterday does not automatically backdate today's effect.
6. Validate manual bigint against approved policy minimum and overflow; reject equal/current number, unsupported historical/scheduled dependents, any other-Student historic PS claim, academic existing interval conflict and retained same-Student lineage inconsistency. **All collision checks run after the same School/allocator locks as automatic issuance and policy writers**. Compute optional counter increase without writes yet.
7. Under protected executor, one-way **UPDATE only source** `effective_until=boundary,ended_at/ended_by` guarded by `source.id/enrollment_id/student_id/effective_until IS NULL` and `source.effective_from<boundary`; require exactly one row. **INSERT successor** with new UUID and unchanged source Student/Enrollment/policy, `numeric_value=proposed`, `effective_from=boundary`, `effective_until=NULL`, `supersedes_id=source.id`, `origin_allocation_id` per RC-04, private trimmed reason; maintain old business columns exactly. Counter increase (if needed) occurs in same transaction with only `next_value`. Recheck final deferred constraints at local test commit/IMMEDIATE gate.
8. Insert one existing Foundation typed `SUCCEEDED` receipt with result kind **pending RC-07 literal**, including source and successor exact IDs/old and new numbers in restricted allowed result binding, append minimized audit and **one selected `enrollment.roll_corrected`** outbox record (event chosen in retention #34, no raw reason/number in broad payload without disclosure review). Do not add `command_receipt_id` to `roll_allocations` or second receipt table. Return bounded result. Rollback the entire command on infra/constraint/deadlock failure; retry only whole same-key canonical intent.

**Concurrency result**: competing CORRECTs on same head: one closes/inserts; other waits School/allocator/Student then fails source-head freshness. Manual versus P0 issuance: one reserve/assigns first; second tests history after same locks and selects/rejects deterministically. No Student version bump solely for roll history unless explicitly approved (old Student `row_version` is an optimistic snapshot token, not child-history mutation counter).

## 6. Historical result replay after later CORRECT/MOVE/END

| Sequence | Retained proof required | Safe proposed behavior |
|---|---|---|
| C1 R0→R1, client loses ACK; no later operation | Existing fixed receipt, exact immutable `R1.supersedes_id=R0.id`, equal Student/Enrollment/policy, exact corrected number and `R0.effective_until=R1.effective_from` | Same principal/key/intent + live permission → return original result; no new UUID or counter/event. |

| C1 R0→R1 then MOVE E1→E2/R2 | C1 receipt → R0/R1; E1 retained ended; MOVE receipt → E2/R2 `origin=R1` in persistent mode | C1 historical ACK remains verifiable; no need E1 active; do not mutate E2 or duplicate C1 event. |
| C1 R0→R1 then END E1 | C1 proof immutable; END receipt refers same E1 with latest R1 and exclusive end | Return bounded original result only if actor remains currently authorized; do not reopen E1/R1. |
| Later revocation/campus move limits current actor | Original receipt/history remain durable | **Proposed conservative disclosure gate:** verify original actor/participant, current change or expressly authorized checked historical read and current exact target/School context, per explicit owner RC-07/08 rule; if none, deny replay disclosure but **do not erase or rewrite** earlier success. Define whether historical source Campus or current Student context qualifies; neither is silently frozen. |

**Invariant:** receipt "terminal" means the historical request's result remains valid, **not** that its successor Roll remains current. Validate a historical receipt via persisted immutable result shape, typed predecessor/successor linkage, closure boundary and successful receipt. Do not require `successor.effective_until IS NULL`, `source Enrollment ACTIVE`, `current Student row_version = old expected version` or current policy still r1. This is distinct from stale *new mutations*. Protect raw reason and unnecessarily sensitive number history under separately approved `student.roll_history.view`.
