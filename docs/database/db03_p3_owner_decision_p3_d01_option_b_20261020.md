# DB-03 Owner Decision — P3-D01 configurable admission document requirements (2026-10-20)

**APPROVED BY PRODUCT OWNER in this DB-03 conversation: Option B.** Each School can configure which document categories are mandatory for a given **published Admissions policy**. Examples: Grade 1 policy requires a birth certificate; Grade 10 policy requires a transfer certificate. The selected policy's exact document requirements, not one global fixed checklist, determine completion of DOCUMENT_VERIFICATION.

## Contract consequences (design-approved direction, NOT installed DDL)

1. Add one **Admissions-owned proposed entity #16**: `app_private.admission_policy_document_requirements`. It is a child of the precise `admission_policy_stages` row with `stage_kind='DOCUMENT_VERIFICATION'`, which belongs to an immutable published `admission_policy_versions` revision. Do not silently treat this as part of the prior 15-entity catalog.
2. **Candidate matrix:** `id uuid PK DEFAULT gen_random_uuid()`; `policy_stage_id uuid NOT NULL FK admission_policy_stages(id) ON DELETE/UPDATE RESTRICT`; `document_kind text NOT NULL` (approved controlled semantic registry); `requirement text NOT NULL CHECK IN ('REQUIRED','OPTIONAL')`; `ordinal integer NOT NULL CHECK >0`; `created_at/created_by` and draft-edit lineage consistent with the P1 stage contract. `UNIQUE(policy_stage_id,document_kind)`; `UNIQUE(policy_stage_id,ordinal)`; indexed `(policy_stage_id,ordinal)`. Candidate `OPTIONAL` flag, ordinal rules, kind registry and whether requirements differ by Campus/grade within a single policy remain engineering/product specifics **not approved just by Option B**.
3. The child roster is mutable only while the parent policy version is DRAFT; publication locks the roster together with stage configuration. A later policy change creates a new published version, preserving historical application snapshots and their original required kinds.
4. A DOCUMENT_VERIFICATION stage only reaches PASSED after every REQUIRED kind in its snapshotted published roster has a current, correctly scoped, VERIFIED Admissions document link whose **Foundation file_objects** source is AVAILABLE and correctly classified/purposed; document state and application evidence epoch must be revalidated. OPTIONAL kinds do not block completion. A configured `SKIPPED` stage is recorded SKIPPED, not PASSED, and does not automatically waive Finance or Person verification.
5. No unchecked JSON roster, client-chosen `required=true`, stored public document URL, duplicate `file_objects`, financial screenshot clearance or generalized stage bypass. Correct permission/scope, entitlement, PRIVATE-purpose validation, retention and independent review are separately required.
6. **Schema installation order:** P1 policy stage exists → add #16 in Admissions-owned new additive file at separately approved installation boundary → register document kind/purpose and publish-time validators after authorization/owner review → P2 application → P3 document link and stage outcomes; adapt final readiness. The previous #08/#10 and #15 catalogs retain their numbering for continuity.
