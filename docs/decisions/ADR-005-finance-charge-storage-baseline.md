# ADR-005 — Finance charge storage baseline

Date: 27 October 2026. Status: implemented in an inactive candidate for disposable validation; production activation and financial business commands remain open.

Requirements: master §§30–36, AGENTS Finance/history rules, database completion matrix, and the approved 21 October Admissions Finance clarification. This is an engineering storage decision under the owner's database-first instruction. It does not set a school's commercial policy.

Finance owns currency-unit definitions, fee categories, stable fee-rule identities, immutable price revisions and assessed gross charges. Admissions does not own a parallel ledger. These are real Finance source tables, independent of Admissions installation. They do not issue payment, discount, settlement or clearance evidence.

Store money as exact integer minor units in unconstrained PostgreSQL `numeric` with an explicit integer and range CHECK: zero through 10^24−1 inclusive. Avoid a numeric scale typmod that silently rounds fractional input before checking. No floating point or PostgreSQL `money`. Currency code and minor-unit scale are explicit immutable configuration (0–6 supported fractional digits); no currency or precision is seeded or inferred from the user's location. The bound is a technical representation limit, not a fee approval threshold. Amount display divides by 10^scale; no percentage, tax, exchange, proration or rounding policy is selected here. Currency code format alone does not validate a real ISO currency. A future configured command must validate the School's selected supported currency and precision before accepting it; production configuration is not enabled in this baseline.

A stable rule fixes School, Campus, AcademicYear, category, currency units and frequency. Price changes append a numbered predecessor-linked revision. Historical assessments refer to their exact rule and revision and retain the original gross amount. This first slice represents one explicit full-price fee occurrence; quantities, concessions, discounts, adjustments and reversals are separate future financial facts. A zero configured price is representable, but is not evidence of a waiver or Finance approval.

Each assessment references the canonical Foundation Person, allowing a pre-Student charge. No fake Student or admissions clearance identifier is introduced. A future typed application/Person/terms binding will connect Admissions to actual Finance sources. Selecting applicable class/student rules and freezing authorized commercial terms remain separate work.

Currency definitions, categories, rule identities, price revisions and charges reject UPDATE, DELETE and TRUNCATE. No correction API exists yet; new revisions preserve old prices, and existing assessed facts await a separately authorized adjustment/reversal protocol. Category renaming/retirement and rule closure will need retained lifecycle evidence rather than destructive edits. Owner/migrator DDL is outside normal application authorization.

All five private tables have forced RLS, schema-owner-only policies and no runtime/client grants. Triggers are invokers with fixed search paths. There are no security-definer business entry points, Finance permission seeds, credentials or enabled writers. Owner-written disposable fixtures demonstrate structural constraints only. Later commands must add exact current permissions, scope, workflow approval, replay/version checks and atomic receipt/audit/outbox before any operational use. This avoids prematurely inventing commercial authority or granting broad table DML.

Consequences: historical charges are reconstructible and exact; duplicate assessment keys, exact same-rule/person/period repeats and repeated one-time assessments are constrained by PostgreSQL. Overlapping or differently labelled custom periods, assessment selection, price publication/effective precedence and concurrent current-authority/clearance fences still require protected commands and acceptance. This is a completed storage baseline, not a completed Finance module or production-ready ledger.
