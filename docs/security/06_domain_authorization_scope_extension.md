# D1B3A — additive domain authorization scope storage

**Design only, from clean HEAD `c93516f00f1d45de7d12a118b738a6d8887168b4`.** This is a future migration-10 contract, not installed SQL, a grant seed, a change to frozen migrations 1–9, or permission to deploy. The 34 D1 relations remain those in the [catalog](../database/27_domain_package_01_physical_catalog.md). Foundation identity, complete grants, authorization fencing, FORCE RLS and historical evidence remain authoritative.

## Installed boundary and compatibility

The deployed `app_private.permission_scope_contracts.scope_kind` and `app_private.assignment_permission_scopes.scope_kind` allow only `ALL`, `CAMPUS`, `OWN`, `ASSIGNED`. A scope row stores its assignment/grant/role/permission/contract chain, `scope_kind`, `resolver_key`, optional `campus_id`, validity and revocation. It has no Class Offering, Section Offering or Subject target columns. The installed `app_private.has_complete_grant(text,text,uuid)` evaluates `ALL/DIRECT`, `CAMPUS/DIRECT` (including an ALL alternative) and `OWN/SELF_PRINCIPAL` only. It does not evaluate D1 CLASS, SECTION, SUBJECT or teaching ASSIGNED. That was a deliberate domain deferral, not a Foundation defect. Its signature, Foundation results, callers and all 220 frozen tests stay behavior-compatible. In particular, D1 `OWN` resolvers must not be treated as `SELF_PRINCIPAL` by the old helper.

Future D1 evaluators are private, fixed-purpose routines. They reuse the **whole** live assignment → role-permission grant → matching enabled permission-scope contract → same assignment/grant/scope row chain, with the installed checks for principal/context, role/permission state, validity, revocation and a single evaluation instant. A selected permission contract determines which scope kinds/resolvers are supported for that permission and action; D1B3B will freeze exact codes and support sets. Every candidate is evaluated as one complete chain. A role's permission from one chain cannot be paired with another chain's target scope. A compatible alternative binding can allow; its ingredients cannot be mixed with another. Existing `has_complete_grant` stays unchanged externally; a shared internal implementation may be refactored later only with proven Foundation behavior equivalence.

## Additive physical shape on existing Foundation relations

The future effective `scope_kind` vocabulary is exactly `ALL`, `CAMPUS`, `CLASS`, `SECTION`, `SUBJECT`, `OWN`, `ASSIGNED`. `FAMILY` is **not** a physical scope kind: it is a principal/relationship path evaluated by `OWN` + `D1_FAMILY_CHILD`. No generic target kind/ID, JSON, array or text IDs are introduced.

Extend `permission_scope_contracts`' kind and resolver-class checks: `ALL/CAMPUS/CLASS/SECTION/SUBJECT` require `resolver_key='DIRECT'`; `OWN/ASSIGNED` require a non-`DIRECT` resolver key. An unknown or disabled resolver is deny, never a wildcard. The installed composite parent key `(id,permission_id,scope_kind,resolver_key)` continues to bind each assignment scope to its exact enabled contract. Existing `SELF_PRINCIPAL` remains a valid Foundation OWN resolver; D1B3B registration will name only reviewed D1 resolver keys. No role label is a resolver.

Add **nullable UUID** columns only to `app_private.assignment_permission_scopes`: `class_offering_id → app_private.class_offerings(id)`, `section_offering_id → app_private.section_offerings(id)`, `subject_id → app_private.subjects(id)`. Each FK is `ON DELETE RESTRICT ON UPDATE RESTRICT`. No D1 table is reshaped for grant convenience. The existing `campus_id` FK stays intact. These four target columns have this exact row-local presence contract (no implicit target in any other column):

| `scope_kind` | `resolver_key` | `campus_id` | `class_offering_id` | `section_offering_id` | `subject_id` | Meaning |
|---|---|---|---|---|---|---|
| ALL | DIRECT | NULL | NULL | NULL | NULL | Eligible school-project records only, subject to every other gate. |
| CAMPUS | DIRECT | present | NULL | NULL | NULL | Exactly that Foundation Campus. |
| CLASS | DIRECT | NULL | present | NULL | NULL | Exactly that campus/year **Class Offering**, not generic `academic_classes.id`. |
| SECTION | DIRECT | NULL | NULL | present | NULL | Exactly that Section Offering; Class/Campus/Year derive through its parent. |
| SUBJECT | DIRECT | NULL | NULL | present | present | Exactly that **Section Offering + Subject** pair, not all uses of a Subject catalog label. |
| OWN | non-DIRECT reviewed key | NULL | NULL | NULL | NULL | Relationship resolver; no direct target stored. |
| ASSIGNED | non-DIRECT reviewed key | NULL | NULL | NULL | NULL | Effective assignment resolver; no assignment ID stored in the scope row. |

Future migration 10 must install a deterministic row-local CHECK that accepts **only** these seven mutually exclusive shapes and replaces the old kind/campus-only shape checks without weakening existing rows. NULL handling must not make an invalid disjunct pass as UNKNOWN. It must reject, for example, CAMPUS+Section, CLASS+Campus, SECTION+Subject, SUBJECT without Section, OWN+Campus and ASSIGNED+Class. The existing immutability guard must additionally freeze all three new target IDs after insert. A change means revoke/retain the old binding and create a new reviewed binding, not retarget history. The existing scope-overlap guard currently compares `campus_id` only; its future identity comparison must include **all** typed target columns with NULL-safe equality, alongside assignment/grant/contract and the same half-open validity/revocation rules. Otherwise unrelated Class/Section/Subject targets could be falsely conflated or duplicate target intervals accepted. Existing ALL/CAMPUS/OWN/ASSIGNED behavior must be regression-proven.

## Ancestry, administration and locking

The row-local CHECK proves presence, not ancestry. Protected security administration plus a restricted defensive validator must verify that a CLASS ID is a valid D1 offering; SECTION resolves to its stored Class Offering; SUBJECT's Section Offering and Subject catalog belong to the same school. Campus/Year derive from D1 parents; do not duplicate them in the scope row. CAMPUS continues its Foundation contract. Missing, inconsistent or archived-for-new-use targets deny. Immutable D1 ancestry and `RESTRICT` FKs preserve historical target identity; target lifecycle changes still recheck whether new operations are allowed.

Creating, revoking or changing a Foundation scope/contract is **authority administration** and takes the Foundation `(71001,1)` **EXCLUSIVE** advisory authorization lock before overlap or current-grant validation. `schoolos_access_executor` remains the reviewed administration boundary unless a separately documented incompatibility is found. A D1 domain executor cannot grant itself scope. Conversely, Teacher assignments, eligibility, Enrollment and Family child links are business facts: they take the D1B2 **SHARED** authorization lock and typed aggregate locks, and never clone or mutate Foundation grants as a side effect. The existing D1B2 Foundation prefix and sorted typed-row lock hierarchy remain unchanged.

## Evaluator and execution boundary

An allow result requires a verified current principal, complete live same-chain grant, enabled compatible contract, exact typed stored target ancestry, effective domain relationship where required, target state, field/disclosure class, and workflow state. ALL does not override a required assignment or field gate. Domain relationships, Employee campus affiliation, Department, Designation, qualification/specialization and Emergency Contact grant nothing by themselves. Unknown kind/key, disabled contract, missing target, broken ancestry, ambiguous intervals or resolver exception deny; never broaden to ALL or silently fall back from SUBJECT to CAMPUS.

Pure private D1 evaluators should be owned by `schoolos_authz_reader` (NOLOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOBYPASSRLS). It needs narrowly granted SELECT **columns** and nonrecursive role-specific SELECT RLS policies on the exact D1 resolver-input relations, not blanket sensitive-data access. The [resolver matrix](07_domain_authorization_resolver_matrix.md) names those inputs. No authenticated direct EXECUTE on arbitrary permission/Student/Employee/Class/Section/Subject/principal evaluator, and no authenticated direct SELECT of private grant or target inputs. Checked read surfaces and protected commands call fixed internal predicates; `app_private` remains unexposed.

Dependency direction is checked read/command → D1 evaluator (`schoolos_authz_reader`) → Foundation grant inputs plus narrow D1 resolver inputs. Input-table RLS policies must be simple role-specific read predicates that do **not** call the evaluator or depend on authenticated caller table privileges. Preserve FORCE RLS, avoid recursion, and test as a non-owner. Shared evaluator reuse must not create a helper/policy cycle.

## Cross-boundary creation and indexes

Migration 10, only if separately authorized, creates `subjects`, `class_offerings`, `section_offerings` in D1's reviewed order **before** altering the already-existing Foundation `assignment_permission_scopes`; then it adds the three typed FKs and revised checks/guards. This is a cross-boundary authorization ALTER/FK after D1 target creation, not a new D1 relation or D1 inter-table cycle. Activation of D1 permissions follows structural installation and non-owner checks.

Proposed authorization-extension B-tree access paths, separate from D1B2's **47 D1 secondary indexes**: one target-first `class_offering_id` lookup for CLASS dependency/revocation work; one target-first `(section_offering_id,subject_id)` lookup for SECTION and exact SUBJECT dependency/revocation work (its Section prefix serves SECTION; no separate Subject-only index without a demonstrated query); retain existing assignment/permission/grant/contract and interval indexes for complete-grant lookup. Evaluate a narrower stable non-NULL predicate for each new target-first path at D1C; query plans and FK/revocation scans must validate selection. The existing campus target index remains. These are indexes on **one existing Foundation relation**, not additions to the 47 D1 relation indexes.

Future non-owner tests must cover old ALL/CAMPUS/OWN SELF_PRINCIPAL, mixed-chain/FAMILY safety, all target-shape rejections, same-year/campus/Section/Subject isolation, overlap on same versus distinct typed targets, unknown/disabled keys, no direct internal EXECUTE/SELECT, EXCLUSIVE administration lock and D1 command inability to change grants. No executable test is added in D1B3A.
